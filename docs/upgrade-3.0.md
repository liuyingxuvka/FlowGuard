# Moving from FlowGuard 2.x

Historical 3.x migration guide. For the current execution boundary and default workflow, use [the 4.0 guide](upgrade-4.0.md). In particular, the former diagnostic/shard paths and effectful sensor replay described for 3.x are not current interfaces.

Version 3 replaces `.home(...)` and custom `(case, function)` adapters with source anchors. This is an incompatible SDK/input change. The map, archived original words, rule predicates, literal rows, sources, supersession, conflict checks, exhaustive partitions, liveness mutations and joint lower witnesses remain. Other projects can keep using their pinned 2.x tag until they migrate; a FlowGuard release does not change their dependency.

1. Keep original words and original data unchanged. Preserve each rule, row and independent expected result. Inventory the old bindings before removing them.
2. Use `python -m flowguard anchor draft module:function`. Confirm the proposed name, meaning and units. Put the comment above the actual function. The function's parameters must match it. A missing function or inconsistent signature is red; an unknown input domain is grey.
3. For a verified pure judgment, reference its sensor with `anchor="NAME"` on the existing rule. Every source function with that name must agree, and each is checked against the rule. Give genuinely different judgments different anchor names; qualified `module:qualname` references disambiguate comparison and distinct declarations. Do not copy an adapter's answer calculation into a new helper.
4. For an effectful function, name an ordinary project test in `calibrated_by=tests/test_file.py::test_name`. Its original assertions and cleanup must pass, and an unchanged-input observation must agree before replacement inputs count. A test that never reaches the target, unstable output or an ambiguous invocation is not a verified binding.
5. When the outcome is an effect after a call, retain the ordinary test that prepares and exercises it. A test event exposes logical inputs; production event/sensor/state anchors expose actual readings. Connect these with a small `flow` and a `Relation` referencing the existing rule. The engine derives the input binding. `Read` selects literal fields, explicit occurrences and fixed lossless views; it cannot calculate a policy answer. A call alone does not establish successful completion, current-file identity or persisted bytes.
6. Keep verified `uses` relations. The derived scenario binding supplies lower witnesses through the original joint-combination algorithm, including nested uses. A `Node` can reference a registered child Flow with one explicit end-reading Rule; the child must pass source, finite, runtime and state checks for that same invocation before its output is used. Missing, ambiguous or cyclic child references stay grey. A Rule contract alone does not prove its surrounding process graph. Source constraints still use `structure_rule` and the generated Map.
7. Replace intentional different-policy declarations with sourced `distinct` between rules or differently named anchors. The old distinct adapter has no execution path. Compare actual anchors with `python -m flowguard compare A B`.
8. Run affected checks, the complete suite in an environment outside the project, and CI for the exact commit. Compare every old row and known counterexample. A former adapter-only green must become red or grey. Remove the old binding after its replacement is checked.

The [local guide](../.agents/skills/flowguard/references/rules.md) contains the executable two-copy example and the four-element flow API. Model only useful complex paths, roughly ten nodes per layer. Source-path analysis is limited: definite bypasses are red; unsupported control or an edge not exercised by tests stays grey. A small finite model is not exhaustive execution of an application's filesystem, network or concurrent behavior.

`check` and ordinary pytest report changed outcome classes, at most ten plus totals. This information alone does not fail tests. Expensive, coupled or unclosed automatic comparisons defer to explicit checking; they are not silently treated as unchanged. Existing red and grey findings remain visible in concise output; `show --full` expands metadata.

## Default use in 3.x (historical)

Keep status, original words, code navigation and checks of existing bound decisions as the default. Anchor an old judgment before a relevant edit when it needs a rule. Behavior comparisons and small flow models remain available for focused repeated judgments and cross-session paths; ordinary edits use ordinary code and tests.

In the small optional-use comparison, each group passed 44/44 hidden checks and left zero measured unintended classes. Total observed wall time was 1652.849 seconds for the tool group and 1462.206 for control (1.130380 times). Equal correctness required at most 0.9 times the cost; the alternative required at least one fewer unintended class and cost at most 1.2 times control. Neither criterion was met. Complete simple-task cost was unknown, and tokens and fees were not recorded. This result sets the narrow default; it does not establish general productivity or token savings. Future trials should use independent hidden checks on repeated judgments and cross-session paths.

## 3.x diagnosis (retired in 4.0)

The 3.x `--diagnose` option recorded timed stages and activated anchor events separately from ordinary checks. That recorder and its JSONL outputs are retired in 4.0. Complete checks still stream original pytest output, and current CI explicitly uses `check --all --deep`.

The 3.x built-in `CHECK_PIPELINE` graph and nested-session timing identities are also retired. Current optional `show`/`watch` views use the same ordinary anchor runtime and historical SQLite entry. Historical logs do not prove the current source. Finite-model checks, observed paths and reading relations remain separate findings; arbitrary concurrent processes sharing a project cache are outside that guarantee.

Do not convert saved trace digests or caches into evidence for the new API. Rebuild generated maps and check records from unchanged original inputs. `.flowguard/models/` is untouched by this migration; there is no compatibility executor for the removed adapter API. Syntax maps remain available for Python, JS/TS, C/C++ and C#; executable anchors in this release are Python only.
