# Intent guide

The canonical API guide and executable two-anchor example are in [the skill's local reference](../.agents/skills/flowguard/reference.md). The skill installer copies that reference with SKILL.md, so the first rule does not depend on retrieving a web page or guessing the API.

Run ordinary pytest with the plugin enabled. After pytest's summary the plugin prints one block, also with `-q`, `--no-summary` and after an interrupt. Its first line counts each kind and FlowGuard's own seconds and names the baseline: `FlowGuard 4.3 (since a1b2c3d): 1 red, 1 changed; 0.3 s` (`since HEAD a1b2c3d` where HEAD stands in for a task start, `since --flowguard-base X` for an explicit one, X as it was given, such as `since --base HEAD` for `check --static --base HEAD`, `no baseline: nothing compared` outside Git, `since a1b2c3d, 2 commits before HEAD` once later commits count as this task's change). Each further line is `kind: what -> step`, of the kinds `red`, `before`, `known`, `known fixed?`, `changed`, `impact`, `loosened` and `not compared`, in that order; a `deprecated` notice for a feature or spelling the project uses goes to stderr once per process, after the block. FlowGuard's own deprecated leads print no notice; `show --last` keeps them. red, loosened and known fixed? lines are listed in full; the others share ten lines: three changed, two known or before lines (known first) and one line counting the rest, two impact, one not compared line that sums them up, and `+N more: python -m flowguard show --last` for the changed and impact lines left out. A line keeps at most 200 characters besides its paths and names at most three places; a path is shortened to its file name, or to the shortest end of it that no other file of the repository has. `python -m flowguard show --last` prints the last run's first line and every line with its details (the rule's source sentence, its other steps, what each copy answered), the number of findings an `act = "ignore"` entry covered, the deprecated features the run used and the deprecated leads. FlowGuard fails a run only for a red line. Rules, source comments and small models preserve useful decisions; there is no task-modeling ceremony.

Grey is not a pass. A grey intent item has its own pytest outcome: `U` with `-q`, `UNVERIFIED` with `-v`, `N unverified` in the summary; the exit status does not change, and no warning, skip or xfail is used. In the block every grey item, and every comparison that was due but could not run sealed, is summed up in one `not compared` line whose reasons `show --last` lists. A changed function that can no longer run in the closed environment (a new write, a result that is not JSON, a function that became a generator or coroutine) is `not compared` with its reason and fails nothing; there is no lost observation any more. `check --all` fails a grey rule or Flow (a one-line template included) whose source quotes the owner's words, unless `[unverified]` in `.flowguard/ledger.toml` lists it by name (`NAME = "reason"`, at least eight words; `[unverified]` is deprecated and goes in 5.0); the session brief counts such a template among its rules. A Flow item (`NAME[flow]`) runs after the ordinary tests and the other intent items, and is judged on their anchor events and on its lower rules' contracts from their items: a green Flow passes, a red one fails, unwalked declared edges keep it unverified. With `--junitxml` a grey item carries the testcase property `flowguard_outcome=unverified`, and a red that no test carries (an inconsistent copy, a broken pair, a source, the ledger) is the failed testcase `flowguard::session`, whose message carries the block's first line and lines. These session verdicts need every test in one pytest process: with pytest-xdist workers (`-n 2`, `--dist` with `--tx`) the plugin stops with a usage error before any test runs, because the xdist controller does not read a red found in a worker; run without `-n`, or with `-n 0`.

`check --deep` explicitly adds decision-site probes and mutation-survival checks. Default tests and checks do not claim mutation adequacy. `check --all --deep` runs all intent items and ordinary tests in CI, with live pytest output; a partial or non-deep collection cannot substitute. Publication requires one complete successful CI run on the exact main commit, with all three supported unsharded platforms and their required execution steps. There is no observation subprocess, nested pytest session, shard aggregator or separate diagnostic pipeline.

The shortest source comment is `# flowguard: same NAME`; full comments with parameters, units and a result declaration remain valid, and so does the 4.2 spelling `sensor NAME`, with a deprecation notice. During the tests FlowGuard records, of every function marked `same` and every function this change edited (its body, a top-level binding it reads, or a same-file function it calls at any depth) or that imports a constant this change altered, the JSON arguments and result of its real calls: the first 20 distinct calls per function and process, after which the function is unwrapped. Nothing is replayed inside a test, so a test's results, its doubles and its coverage are those of a run without FlowGuard. After the tests the session compiles the function's source, with the same-file functions it calls, under the file name `<flowguard-sealed>` into globals that hold only `abs all any bool dict divmod enumerate filter float frozenset int isinstance len list map max min range repr reversed round set sorted str sum tuple zip`, the built-in exceptions, `math`, `decimal.Decimal` and `datetime`'s `date`, `datetime` and `timedelta`, whose `now`, `today` and `utcnow` refuse. A name it lacks makes the function `not compared` with the name (`uses unavailable binding RATE`). Module-level constants are read from the source, never run: literals, arithmetic on literals and earlier constants (`FACTOR = 10 ** DECIMALS`), and a literal constant imported from another module of the project (`from X import NAME`, or `import X` and `X.NAME`, X found by the importing file's own import root, never an installed package) when nothing in X's top level can change it. The audit hook and the watchdog stay around each sealed run. The baseline version runs from the baseline source the same way, a moved file from its old path. A difference on a recorded input is a `changed` line with the first differing input, the old and the new value and how many inputs differ (`changed: label (fees.py:15): (days=3) was 'on time', now 'late'; 1/2 inputs differ -> if you meant it, say so`); the same exception in both versions is `not compared`, never unchanged. Not compared: decorated, async and generator functions, methods, defaults that are not literals, arguments or results that are not JSON. A comparison is due only for such a function and for a name with two or more copies (a project in a subfolder of its Git repository is compared like one at the top), so a lone unchanged `same` function whose calls are not JSON is never listed. A `calibrated_by=tests/test_file.py::test_name` binding names one real ordinary test, including a parameter ID when relevant: the call that test made in its ordinary run is the context, the requested inputs are put in place and the source runs sealed. A named test that did not run, or whose call is not JSON, leaves the item not compared; one that did not pass is red. A scenario is read from the anchor events of its test's one run, so only the input it ran with is compared.

`show NAME` displays anchor parameters, result distributions and citing rules, or a model's node/edge counts and missing or invalid paths; `show rules`, `show rule.<id>` and `show known.<id>` list `.flowguard/rules.toml` and `.flowguard/known.toml` with each source's state, the intent rules citing a rule, an entry's sites and what the last run said of its finding. Old observations are labelled historical and become stale after source changes. `try`, `watch`, `model draft` and `anchor draft` still run with a deprecation notice and go in 5.0; `try NAME days=4` records only the real call. These commands are not extra default steps.

The brief from `python -m flowguard` has at most eight lines (the baseline, the first rules of `rules.toml`, the open `known.toml` entries by urgency, the structure count and what the last run left) and remembers the current task's baseline commit: it records HEAD only when no baseline is recorded or the recorded one is not an ancestor of HEAD (another branch, rewritten history) or not in the repository, so commits made during a task keep its baseline and what the task changed stays reported; the brief then says how many commits the baseline lies before HEAD. On a detached HEAD (a tag or an older commit looked at during a task, a bisect step) the brief neither moves nor records a baseline and says so; back on the branch the task's commits are still reported. Every pytest session with the plugin, `check` and `check --static` record HEAD only when no baseline is recorded and HEAD is a branch, so a project that runs only `init` and pytest records one at its first run on its branch (a fresh clone in CI compares that first run with its HEAD, as before). A session that only collects tests (`--collect-only`, IDE discovery) and a run on a detached HEAD (a tag or an older commit checked out, a bisect step, a CI checkout) record nothing: they compare with HEAD. They never move a recorded one, not even when HEAD does not descend from it: a run on an older commit, another branch or a bisect step compares with the task start, and back on the task's branch its commits are still reported. Only the brief and `new-task` move it, and they say why. A run without a Git commit records nothing, nor does a run with `--flowguard-base` or `--base`, which name their own. `python -m flowguard new-task` starts the next task: HEAD becomes the baseline, also on a detached HEAD, then it prints the brief; when the start it replaces lies commits before HEAD, it says those commits are no longer compared and how to compare them once (`python -m pytest --flowguard-base OLD`; in a project whose tests npm runs and pytest finds none of its own besides FlowGuard's sentinel, `python -m flowguard check --static --base OLD`). The CI fragment `init` writes runs `check --all --deep`, or there `check --static --base` with the merge base of HEAD and `origin/main` (a CI checkout is a detached HEAD, whose task start is HEAD itself); its comment says to replace `main` when the default branch has another name. Rule 1 of the block `init` writes starts each task with it. `check --base COMMIT` (pytest's `--flowguard-base COMMIT`) explicitly changes the comparison baseline of one run; an empty one, as a failed `$(git merge-base ...)` gives, is refused (exit 2, pytest's usage error 4), never read as no baseline. The first line of pytest, `check`, `check --static` and vitest says `since a1b2c3d` for a recorded baseline, with its distance once HEAD lies commits after it (`since a1b2c3d, 2 commits before HEAD`: until `new-task` runs, the commits of earlier tasks count as this task's change), and `since HEAD a1b2c3d` where HEAD stands in because none is recorded (a detached HEAD included). A recorded commit the repository lacks (a shallow clone, history rewritten and collected, a cache copied from another clone) compares nothing: pytest, `check` and `check --static` print a first line that names it with the next step (`since a1b2c3d, not in this repository: nothing compared; run python -m flowguard new-task`), even with no source change, and `ledger check` prints the same line first; the brief on a branch or `new-task` records HEAD (on a detached HEAD the brief records nothing and says so). The vitest side records nothing, so its runs before the task's first `check --static` (which `flowguard.static.test.mjs` runs), pytest or brief compare with HEAD and say `since HEAD`; its first line gives a recorded start's distance from HEAD as pytest's does, and with a recorded commit the repository lacks it names that commit in its first line and compares its same-name copies as pytest does without a baseline. A rule cites only its relevant original words or authority document; preserve those bytes once with `req add`, never an AI's interpretation or plan. See [the 4.0 migration](upgrade-4.0.md) for removed interfaces.

## Where rule fields come from

A rule bound to an anchor (`anchor="NAME"`) reads its fields, in this order:

1. The anchor's input parameters: the rule's own items run the anchor on each case class of the rule (`NAME[module.function:cells]`) and on its literal rows (`NAME[module.function:rows]`); no scenario test is needed.
2. Values hidden in the context, read on the anchor with one `fields` clause: `# flowguard: same FEE fields days=(today - hire.due).days member=customer.is_member`. Each `name=expression` is a Python expression over the function's own parameters and its module's names; it runs to the next top-level `name=`, so spaces, calls, strings and `==` stay inside it. On every call a test reaches, the expressions are evaluated in the closed environment of the comparison with that call's recorded arguments, never in the test: the environment has no connection and reads no attribute of a record, so a field read from a database or a record leaves the rule's item unverified with the first field it could not read, and an explicit write in a field is refused before it runs. The rule is then computed on parameters and fields together and compared with that call's outcome. The rule's `cells` item checks every such call, its `rows` item each literal row a call reached; a row no call reached, or a field that cannot be read, is grey (unverified) with the field's name and error; a disagreement is red with the rule's source sentence. A partial run without the rule's items still reports a red call at the end. `fields` combines with the parameter list, the `;` context separator and `calibrated_by=` in either order: `# flowguard: same FEE(today; db, hire) calibrated_by=tests/test_fees.py::test_fee fields days=(today - hire.due).days`; with `calibrated_by` only that test's calls count, and the test is not rerun. A field may not repeat a parameter's name; event and data-owner anchors take no `fields`; a malformed clause is red at its line with the way to write it. Mutation-survival checks (`--deep`) need a directly callable anchor and stay grey for `fields`.
3. When neither is possible (the outcome appears after the function returns, or the function writes), keep a scenario test and a small flow: an event anchor's `calibrated_by=` names the scenario test and a `Relation` connects its readings to the rule.

Two static leads, deprecated in 4.3 and printed only by `show --last` under `deprecated leads (5.0)`, cover a requirement that changed while its rule did not: the rule still holding the replaced value (see Owners and copies), and `ACCEPT copies at orders.py:preview_accept changed; rule WINDOW is unchanged` when a function this change touches (its body, a constant it reads or a function it calls) is a rule's anchor or a same-name copy and the change does not touch that rule's file; the line names both next steps (a changed need: store the new words, then change the rule; otherwise confirm the code change). `show RULE` lists the case classes the rule gives no result for (`undecided: rule RID has no result for N classes`); when no rule of its decision decides them and a rule there says `total=True`, they are red. `req add` ends with the reminder that a lasting requirement becomes a rule in the intent folder citing the stored id.

## Fallback ledger

`.flowguard/ledger.toml` lists every handler that can end without raising, the same way an owner's handler-list test does. A key is `file:function:caught` (`<module>` outside functions, `BARE` for a bare `except`); its `count` must equal the code's, its `reason` says what the handler does and why it may stay in at least eight words, and its `rule = { file = "...", text = "..." }` quotes a sentence that file must still contain. A handler that raises on only one branch counts. A new, missing or vanished handler, a changed count or a sentence no longer in its file is red in ordinary pytest (the sentinel test fails and the closing FlowGuard lines print the entry to copy). Bare `except`, `except Exception`/`BaseException`, `contextlib.suppress` under any alias, warning filters, `return`/`break`/`continue` inside `finally` and an `__exit__` that may return true cannot be listed. `python -m flowguard ledger init` records the current handlers as legacy (`rule = "旧账"`); legacy entries may only shrink against the baseline commit and the init record, so only new handlers are reported. `check --all` and `check --static --all` list the legacy entries of production code (outside tests and archives) whose handlers do not hand the error on, by how the body ends: it returns or assigns a substitute value, only logs, or is empty (not listed: a handler that raises on some path, or that ends in other work without returning or assigning a value, such as `res.status(500).json(...)` or `show_error(message)`; in JS/TS a returned answer counts as that work too when it is method calls made one on another directly on a parameter named `res`, `reply`, `response` or `ctx` of an enclosing function, the last of them `json`, `jsonp`, `send`, `sendStatus`, `sendFile`, `download`, `end`, `redirect`, `render`, `text` or `html`, with an argument somewhere unless it ends in `end()` or `send()`, also under `await` or `void`: `return res.status(500).json(...)`, `return void res.status(500).json(...)`, `return reply.code(500).send(...)`, `return res.end()`; every other returned or assigned value is a substitute, a response value included: `return res.text()`, `return res.headers.get(name)`, `return ctx.get('user')`, `return res.status(500)`, a call on a local such as `const res = await db.query(...)`, `return new Response(...)`, `return Response.json(...)`, `return NextResponse.json(...)`, Koa's `ctx.body = ...`, a Hono context under its usual name `c`, and in Python every `return` with a value, `return JSONResponse(...)` included); review them one by one. It refuses when the project already keeps its own handler-list test: keep one of the two. `python -m flowguard ledger check` lists every difference without running tests. The scan covers every mapped source file; `[tool.flowguard.ledger] paths` and `exclude` narrow it. Files whose reader supplies no handler facts, or that do not parse, are listed as not checked.

## Owners and copies

One judgment or one field has one owner. `# flowguard: same NAME ref` above a function (4.2: `owner NAME`) makes it the reference its same-name `# flowguard: same NAME` copies (4.2: `sensor NAME`) are compared with. The copies run in the closed environment on the recorded inputs, then each with every number the copies use, then the ±1 neighbours of both, kept once and cut at 64 inputs (a place for each number is kept before the recorded inputs are cut, and what the cut leaves out is named in the not compared line). Each input is judged on its own against the copies' task-start versions: copies that agreed on it and differ now are red there, and the next step names the copies to bring back to the reference (`red: same ACCEPT: on days=4: the reference orders.py:accept returns False, orders.py:preview_accept returns True -> make orders.py:preview_accept agree with the reference`); copies that already differed on it are `before`, or `known` when a `known.toml` entry names `same:NAME`; an input the task-start code could not run is not compared. Without a reference the red names what each copy answered and leaves the choice (`red: same FEE: on days=5: fees.py:late_fee returns 4, fees.py:preview_fee returns 6 -> decide which copy is right, then make the other agree`; of four or more copies three are named and the others counted): decide which copy is right and make the others agree, or rename the ones that should differ. Parameters correspond only by name: a copy with other names writes `# flowguard: same NAME(days=overdue_days)`, nothing is matched by position or type. Copies that return different forms compare a projection, written without a colon: `-> result[0]` or `-> result.ok`; `-> name: type` stays an output declaration. A copy that uses `math` runs sealed with it; agreement on these inputs is a sample, not a proof.

Deprecated in 4.3 and removed in 5.0: `check` also runs unregistered look-alikes of each reference (same number of simple parameters, and a similar 3-gram body shape or a shared number other than 0, 1, -1 and 2) on the reference's classes, in the closed environment, and groups them: copy (equal on every representative), forked copy (similar structure, at least half equal), similar (a shared number only); unrelated look-alikes are not listed, and a candidate that cannot be imported or run is listed as unclear with its reason. It prints the candidate count and time. A new function that copies a reference registered at the baseline commit is an `impact` line, since automatic structure checks are never red. A changed function whose old version agreed with unchanged look-alikes is a deprecated lead that names them and the comment to copy; once registered, the same-name check makes a new disagreement red.

A field's writers are listed with `# flowguard: writers hires.reserved shop/store.py:reserve` (4.2: `owner hires.reserved writers=...`, still read) (`// flowguard: writers Employee.organizationalUnitId transferEmployee` in TS/JS). Writes come from the map: Python attribute assignments (matched by name when no class binds them), SQL `INSERT`/`UPDATE`/`DELETE` in Python string literals and TS/JS raw SQL, and Prisma client writes; a write row carries the literal value it writes when the source spells one. A write outside the writers that this change adds is red in pytest and `check`; older ones are the old ledger, listed by `check --all` and `show NAME`. Without a baseline commit nothing counts as new.

A field's pairs are written `# flowguard: together Employee.orgUnitId CentralEmployee.orgUnitId[=value] except=src/import.ts:import_rows(reason)` (4.2: `owner Employee.orgUnitId with=CentralEmployee.orgUnitId alone=import_rows(reason)`, still read). Each write of the field must also write each partner (with that value, when given) in the same operation: the writing function's callers three levels up, then everything they call three levels down (a caller that writes one field through one helper and its partner through another is one operation; JS/TS calls are resolved by name inside the caller's package, the folder of its nearest `package.json`; from production code the way up does not enter test files); a function listed in `except=` may write it alone, with its reason and the owner's yes (adding one is a `loosened` line), and a test's own fixture write is not held to the pair. A Prisma field given `undefined` or `void 0` (also `{ set: undefined }` and `{ increment: undefined }`, likewise `decrement`, `multiply`, `divide`, or `data.field = undefined` on a local data object) is no write, since Prisma leaves it as it is, so it neither holds a pair nor counts anywhere else; `null` is a write. A name that holds `undefined` (`const level = undefined; { level }`) still counts as a write. `on=update` after the partners holds only the writes that change an existing row (`update`, `updateMany`, upsert's update branch, SQL `UPDATE`, an attribute assignment): `// flowguard: together Employee.sapReference Opportunity.responsibleSapNumber on=update` asks every renumbering to carry the references along, while a function that creates an employee is not held; `on=create` holds only the writes that make a row (`create`, `createMany`, upsert's create branch, a nested create, SQL `INSERT`). Its red names the limit (`(updates only)`, `(creates only)`). The current registration is also applied to the task-start code: a missing partner is red when this change adds the write or makes the operation lose the partner (a helper that stops writing it, a call removed), and `before` when the code already missed it, also for a pair registered during the task; without a baseline nothing is new. A partner written in the trigger's own function holds the pair only for the same record (the same call, a call without `where`, or a `where` by the same text on the same model); a partner written only in one branch or a conditional spread holds it only under the trigger's condition; a module-level callback such as a route handler is an operation of its own. `check --all` lists every one. `show Model.field` names the fields at least half of the field's writing functions also write, with the writers that leave each out, as partner candidates to copy once the owner says they change together (a reference, never a red). Write rows read the value an enum member, a module constant or each branch of `a if c else b` folds to (in TS/JS also each branch of `c ? a : b` and the fallback of `x ?? 'v'`, which the value gate judges); `row['status'] = ...` is a write of the key `status`, and a class-body default belongs to its class. One value gate checks every readable write of a declared field against its set, wherever the write is: a `# flowguard: states Class.field = a | b` comment, a `states(...)` declaration, or an enum annotation (`status: RunStatus`, plus `None` when the annotation allows it). Copy discovery also runs the strings and numbers the compared functions' own code spells (an alias table's keys too), so two copies with different tables fork. Copies are grouped by their first difference in a fixed order; the header says which values were compared, not whether callers reach them.

Static leads, deprecated in 4.3 and listed only by `show --last`, need no comparison: an old value this change replaced that other decisions still spell (any field name; also members of tuple and dict constants), a rule in `tests/intent/` whose predicate or literal rows still hold it, a function whose old body an unchanged function still has, a label spelled a new way (case, spaces and punctuation aside) next to existing spellings of the same kind in production code (an UPPER_SNAKE code, words with spaces, a key or id, each after its leading `/`, `--` or `.`, group only with their own kind; a spelling only tests use does not count). Two declarations of one name (an enum, `X = Literal[...]`, a TS union alias) with different members are an automatic structure check instead: `impact` when this change makes them differ, `before` when it touches an old difference. A changed unit (days to seconds) is a known miss. Leads only report what this change adds.

## Map checks without tests and structure problems

`python -m flowguard check --static` runs the map checks alone, without pytest, and prints them as an ordinary test run ends: the fallback ledger, writes outside a data owner, registered pairs, values outside a declared set, deletes that leave restricting children, columns one description of a table lacks, new label spellings, old values still spelled elsewhere and unchanged look-alikes of a changed function. It reports what this change adds against the task baseline (or `--base`) and exits 1 on red; `--all` also lists the old ledger, after what this change adds. Its lines share the block's budget, and `python -m flowguard show --last` prints them all (`--leads` is a deprecated way to print them without the budget). Ordinary pytest with the plugin runs the same checks, with the same TS/JS owners, whenever the change touches a mapped file, a TS/JS, Prisma or SQL file as well as a Python one. In TS/JS the value gate reads the enums of the Prisma schemas the generator uses (each `schema.prisma`, and a file or folder a `package.json` names in `"prisma": {"schema": ...}` or a script's `--schema`, or the `schema:` of a `prisma.config.ts` beside it, reading every `package.json` from the schema's nearest package up to the repository root; the config is read without its comments, as a string, a quoted key or `path.join`/`path.resolve` of string literals after `__dirname`, and a variable there names nothing; a `schema.sqlite.prisma` template only describes; several Prisma files in one folder of which at most one has a datasource, none repeating another's model or enum, are one schema split into files, all in use when one is, their enums, models and datasource read together, while schema files and provider templates side by side, each with its own datasource, stay apart; a package whose Prisma files name none of these is judged by each of them, for the models no schema in use defines and for the writes of that package and of packages whose Prisma files do not define that model, each enum a set of its own (one for the files that spell it alike), and its red lines say so; a Prisma file under a `docs` folder is an archive, neither in use nor guessed), SQL `CHECK (col IN (...))` sets (the latest in a migrations folder; SQL under a `docs` folder is an archive and left out), both when a field has both, and interface, class or object-type members annotated with a closed string union or `(typeof X)[number]`/`[keyof typeof X]` of an `as const` array or object; it judges Prisma `data` values against the database sets (by the schema in use of the write's own package that types the field with an enum, the nearest package defining the model: another schema of that package that lacks the field (a client that reads other columns) or a template without a client of its own that types it as text (SQLite's `role String`) neither judges it nor stands in the way, and when no schema of the package types it with an enum no enum judges it; a package with none by the first schema in use by path whose enum types the field; an object typed from one schema's client output by that schema, by no enum when its field is none; when two schemas in use of that package type the field with different enums, or one that writes a client of its own (`output = ...`, another database) types it as text, a write that does not name its client, `prisma.x.create` or a type from `@prisma/client`, is judged by neither), and `Name.KEY` members of such objects, class field initializers, `this.f = ...` and objects written as `const x: T = {...}`, `satisfies T` or `as T` against the TS type's own sets (a typed object is of the type its own file declares under that name, an interface, class or type alias at the top of the file, else of the one in the module it imports the type from by a relative path, and only a set that declaration gives the member judges it: each component's `interface Props` judges its own objects, and one whose member is `variant: string` judges none; an object of neither is judged by the member's set when it has one, not at all when the declarations' sets differ; a TS type is not the Prisma model of its name, unless the file imports it from the Prisma client: `import type { Item } from '@prisma/client'`, also as `{ Item as Row }`, as `P.Item` of `import * as P` or `Prisma.Item` of `import { Prisma }`, or from the folder a mapped schema's `generator` block writes the client to with `output = "..."`, by a relative path or, for a folder inside `node_modules` (`../../node_modules/.prisma/central-client`), by the package name after it (`.prisma/central-client`) from the files under the folder that holds that `node_modules`; an output folder is read before the generic `@prisma/client`, `.prisma/client` and `generated/prisma` spellings, and a schema in use owns it over a provider template with the same generator block; the red names the model's field; ## The vitest execution side (minimal)

For a vitest project `init` also writes `flowguard.vitest.mjs` (it finds Python the same way) and adds two lines marked `flowguard: vitest` to `vitest.config.*` or `vite.config.*`: an import and `flowguard()` as the first plugin, or a new `vitest.config.mjs` when there is none. Delete the two lines (or the generated config) to undo. A CommonJS config is left alone and the two lines to add are printed; a jest project gets `check --static` only. ## Relation templates

`from flowguard.intent import precedes, guarded_by, transitions, checks` writes one relation per line; each is an ordinary Flow checked by the existing flow checks. `precedes("SAVED", "PUBLISHED")`: in a test, publishing comes after a save. `guarded_by("PERMISSION_OK", "UPDATE_RECORD")`: every update has its own permission check before it. `transitions("Job.status", new={"saved"}, saved={"published"})`: the allowed changes of a field whose values the existing `# flowguard: states` comment declares. `checks("FEE", "FEE_CASE", days="arg.days")`: rule FEE checked on a scenario test's own arguments. Observed disallowed paths are red; unobserved declared edges and transitions stay unverified. These templates are deprecated and go in 5.0. Copies use `same NAME` and `same NAME ref`, and a single writer uses `writers`, so there is no copy or `single_writer` template. `model draft NAME` also prints template lines from observed paths, grouped by the flow each test starts.

## Generated source queries

The base installation maps Python. The seven foreign readers are frozen optional additions: install the `languages` extra to map JS/JSX, TS/TSX, C, C++ and C#. Grammars load only when their source language is present; unavailable grammars are reported explicitly. Python has the full executable behavior anchors; TS/JS has the minimal vitest execution side described above. Foreign syntax supports navigation and explicit source checks; it does not execute the application or replace a compiler. Dynamic calls, macros, overloads and external/build-dependent bindings remain unknown with reasons.

For example, if an agreed `architecture.md` says `Literal assignments to retry_limit use only 0, 1 or 2.` and the file is listed in `[tool.flowguard].authority_docs`, a small Python-only source constraint can live with the component that owns this field:

```python
from flowguard.intent import structure_rule

@structure_rule("RETRY_LITERALS", source='doc architecture.md "Literal assignments to retry_limit use only 0, 1 or 2."')
def RETRY_LITERALS(graph):
    return [write for write in graph.assignments(language="python")
            if write["field"] == "retry_limit" and write["value"] not in (0, 1, 2)]
```

This checks the declared literal assignments, not computed keys or every runtime write. A source predicate returns violating rows/nodes, rather than a boolean or a copied implementation. A newly written policy remains green*, not independent authority. Use the source scope the actual requirement specifies; removing languages or files to obtain green changes the claim.

`graph.capabilities()` exposes actual languages/files, parser errors, available grammars and supported queries. `graph.query_coverage()` reports the queries this handle actually served and any unavailable or failed source scope. `functions()` tracks nodes, assignments and keys are tracked, and `calls(include_reads=True)` also requests symbol-read coverage. `nodes(file=...)` and `language="python"` make an intentional source boundary explicit. Foreign handlers, literal sets, test discovery and full symbol reads are not yet implemented. A structure rule using unavailable coverage, failed parsing, or no source query is grey. Each structure check has its own scope; direct library users can call `reset_query_coverage()` before a separate predicate.

The shared cache is invalidated by source changes, reader/grammar versions and project parser configuration or compilation-option content. Unsupported configuration, dependencies outside mapped roots and unresolved bindings stay unknown; cached syntax is not evidence of successful compilation or execution.

Fingerprints help find changed code and possible moves. They do not establish cross-language equivalence or prove behavior merely because names or shapes match.

## Use hierarchy only when it removes repetition

An upper behavior rule can declare `uses=[LOWER]`. A scenario relation connects actual lower and upper readings; the engine derives the logical-input binding and supplies verified joint witnesses. Lower sources and anchors must pass too; explicit deep checks additionally require mutation liveness. Joint checks combine all verified lower inputs, through nested uses, instead of changing one lower input at a time. Closed boolean/enum domains can have complete finite coverage. Open domains use supported partition representatives and report that boundary; they are not enumerated value by value.

Keep behavior decomposition in those actual uses relations and source constraints in `structure_rule` at their owner. Neither requires a whole-application model, a separate hierarchy format, or modeling the current development task.

Source anchors replace the old `.home` decorator. The [3.0 guide](upgrade-3.0.md) describes that older input migration; [4.0](upgrade-4.0.md) changes the execution boundary. A complex flow has only nodes, edges, existing state transitions and existing-rule reading relations. `model draft NAME` starts from real observed paths rather than repeating the implementation.

A `Node(..., model="CHILD_FLOW", phase="return")` can consume a registered child Flow's output. The child exports one existing Rule through an explicit `Relation(..., actual=Read("end"), on="end")` at a terminal return/raise node; the parent names that same source anchor and phase. Its Rule contract and joint witnesses still apply, and the child graph's finite and runtime checks must also pass on the same observed invocation batch. Deleting an internal save cannot leave that parent green merely because the exported boolean stayed unchanged. A test-entry Flow can supply the existing ordinary-test scenario binding separately from the production graph.

Each exported event needs one declared production start call in the child graph. Its matching return can be the export; nested check/save calls remain steps inside that start. Different invocations retain separate event scopes and share only coverage accounting. Missing or multiple exports, unregistered Flow objects, cycles, unavailable source identities and unobserved model edges remain grey. There is no fixed ten-layer depth cap; keep each layer near ten meaningful nodes so it is understandable. Finite state spaces are fully explored without a default fixed state cap. A same-named Rule or saved green metadata does not verify a child graph.

Default Flow verdicts cover observed anchor paths and the declared finite model. Unexecuted source routes remain unverified; an observed green does not prove that the source has no other route. Static path analysis is frozen and is not run by the engine; its direct SDK helpers remain available for their narrower explicit source scope.
