# Intent guide

The canonical API guide and executable two-anchor example are in [the skill's local reference](../.agents/skills/flowguard/reference.md). The skill installer copies that reference with SKILL.md, so the first rule does not depend on retrieving a web page or guessing the API.

Run ordinary pytest with the plugin enabled. After pytest's summary the plugin prints one block, also with `-q`, `--no-summary` and after an interrupt. Its first line counts each kind and FlowGuard's own seconds and names the baseline: `FlowGuard 5.0 (since a1b2c3d): 1 red, 1 changed; 0.3 s` (`since HEAD a1b2c3d` where HEAD stands in for a task start, `since --flowguard-base X` for an explicit one, X as it was given, such as `since --base HEAD` for `check --static --base HEAD`, `no baseline: nothing compared` outside Git, `since a1b2c3d, 2 commits before HEAD` once later commits count as this task's change). A session that ended before its selected tests had all run (an internal error, an interrupt or a collection error, `-x`, `--maxfail`, `pytest.exit`) says so before the time, with the exit the shell sees and how many of the selected ordinary tests gave an outcome: `FlowGuard 5.1 (since a1b2c3d): 0 red; run ended early (exit 3): 2 of 3 selected tests ran, the rest not checked; 0.1 s`; a finished run, and one that only collects or sets up, has no such note. Each further line is `kind: what -> step`, of the kinds `red`, `before`, `known`, `known fixed?`, `changed`, `impact`, `loosened` and `not compared`, in that order. A `known` line names the sites of its entry this change touches and how many sites the entry has, then an `ask` entry's question (`known: known.percent-scale at capacity.service.ts:capacityService.updateCalendarEntry (1 of 12 sites): Which scale does the database store for PERCENT rows, 0..1 or 0..100? -> asked the owner on 2026-11-15; no answer yet`); every site when the change touches none (`--all` lists such entries too). When the change also touches the finding the entry names, the known line comes from that finding and names the finding's places this change touches, a place being one of the entry's sites that the change touches, with their count (`known: known.fee-copies at fees.py:preview_fee (1 of 2 places): ...`), and every place of the finding when it touches none of them. red, loosened and known fixed? lines are listed in full; the others share ten lines: three changed, two known or before lines (known first) and one line counting the rest, two impact, one not compared line that sums them up (naming a function by its own name, not by the agreement it is marked with: `not compared: 2 functions: can_view (scope.py:2) and visible_projects (scope.py:6) (no baseline source)`; in a vitest run whose map checks did not report, their item is a line of its own before it), and `+N more: python -m flowguard show --last` for the changed and impact lines left out. A line keeps at most 200 characters besides its paths and names at most three places (the not compared line never cuts through an item: its reasons give way first, and its items are counted when they leave no room; a single item keeps its name and place, and its own text gives way before its place after its reasons; a line whose subject, places and step alone leave no room within 200, as a copies line's, keeps its words); a path is shortened to its file name, or to the shortest end of it that no other file of the repository has. `python -m flowguard show --last` prints the last run's first line and every line with its details (the rule's source sentence, its other steps, what each copy answered) and the number of findings an `act = "ignore"` entry covered. It keeps one last run per slot and prints each, newest first, with the full version of the FlowGuard that ran it: pytest, `check` and `check --static` share one slot, and each vitest package has its own (`FlowGuard 5.1.0 last run: vitest web/ at 2026-11-23 08:21:55`), so a pass in `api/` never replaces a red of `web/`. A slot whose package folder no longer holds a vitest or vite config is not read. Under a pytest run's header comes pytest's own outcome, `pytest: exit 1, 1 failed, stopped early (-x)` (errors, `--maxfail=N`, an interrupt or a `pytest.exit` too): the block's `0 red` counts agreements, not tests. The static test inside a vitest run keeps nothing of its own; the vitest preparation notes the run's start in its package's slot and the run's report replaces the note, so a run killed before it reports (an outer timeout) says `a vitest run of web/ started at T did not report; the lines below are from the run at T0` above that package's earlier lines. Last come what the brief counts besides these lines: the intent results' reds, and each failed test it keeps from that test's last run, with its outcome, when it ran and whether the last pytest run selected it (`tests/test_a.py::test_x: failed (call) at ...; not selected by the last pytest run, at ...`). FlowGuard fails a run only for a red line. Rules, source comments and small models preserve useful decisions; there is no task-modeling ceremony.

An `impact` line of a function whose set of written fields changed counts the other writers of its first field and that field's or model's readers, and says of a field the function no longer writes what the code shows. While it still writes that model with data whose fields the reader cannot see (a spread, a parameter, SQL that names no columns), the field may be among them: `update writes AbsencePhase.? where it wrote endDate, share, startDate (fields not visible: phase is a parameter)`. When a function it calls through a call the map resolved (an import, a lexical binding, the Python store's links; never a name alone) writes the field now, one line says so for both, `set_default's writes of Prefs.model moved to _apply, which it calls (model.py:7)`, naming the helper's other resolved callers (`; other callers of _apply: load, reset`); the helper's own `now writes` line is left out when every field it newly writes is one the caller wrote at the task start, and `show --last` keeps what it said, the call (with its line in JS/TS: the map keeps a Python call's function, not its line) and the other callers. A call the map does not resolve links nothing: each function keeps its line. Otherwise the line says `no longer writes`, and adds `now deletes Assignment (assignments.ts:9)` when the function deletes rows of that field's model and did not at the task start.

Grey is not a pass. A grey intent item has its own pytest outcome: `U` with `-q`, `UNVERIFIED` with `-v`, `N unverified` in the summary; the exit status does not change, and no warning, skip or xfail is used. In the block every grey item, and every comparison that was due but could not run sealed, is summed up in one `not compared` line whose reasons `show --last` lists. A changed function that can no longer run in the closed environment (a new write, a result that is not JSON, a function that became a generator or coroutine) is `not compared` with its reason and fails nothing; there is no lost observation any more. `check --all` fails a grey rule or Flow whose source quotes the owner's words, and nothing exempts it: the `[unverified]` section of `.flowguard/ledger.toml` that did was removed in 5.0 (see Fallback ledger). A Flow item (`NAME[flow]`) runs after the ordinary tests and the other intent items, and is judged on their anchor events and on its lower rules' contracts from their items: a green Flow passes, a red one fails, unwalked declared edges keep it unverified. With `--junitxml` a grey item carries the testcase property `flowguard_outcome=unverified`, and a red that no test carries (an inconsistent copy, a broken pair, a source, the ledger) is the failed testcase `flowguard::session`, whose message carries the block's first line and lines. These session verdicts need every test in one pytest process: with pytest-xdist workers (`-n 2`, `--dist` with `--tx`) the plugin stops with a usage error before any test runs, because the xdist controller does not read a red found in a worker; run without `-n`, or with `-n 0`.

`check --deep` explicitly adds decision-site probes and mutation-survival checks. Default tests and checks do not claim mutation adequacy. `check --all --deep` runs all intent items and ordinary tests in CI, with live pytest output; a partial or non-deep collection cannot substitute. Publication requires one complete successful CI run on the exact main commit, with all three supported unsharded platforms and their required execution steps. There is no observation subprocess, nested pytest session, shard aggregator or separate diagnostic pipeline.

The shortest source comment is `# flowguard: same NAME`; full comments with parameters, units and a result declaration remain valid. FlowGuard 5.0 removed the 4.2 spellings (`sensor NAME`, `owner NAME` above a function, `owner A with=...`, `alone=f(reason)`, `owner A writers=...`): each is red at its line, nothing of it is read, and its step is the 4.3 comment to write instead (`red: comment app.py:1: sensor was removed in 5.0 -> write # flowguard: same LIMIT`). A 4.2 bare name in `alone=` or `writers=` meant the function of that name in any file, so the rewrite names each such function, another file's as `path:function`; an `owner NAME` on no function is told to write `same NAME ref` above the function it names, or to delete the comment. Such a line binds nothing, but what a change loosened compares the agreement its step states, at the task start and now: written as its step says it loosens nothing, while deleting the line, dropping a partner or adding a writer or an `except=` is a `loosened` line, as for its 4.3 rewrite. pytest, `check` and `check --static` print the same rewrite, for a JS/TS comment too, and the block prints the comment to write with its whole paths. During the tests FlowGuard records, of every function marked `same` and every function this change edited (its body, a top-level binding it reads, or a same-file function it calls at any depth) or that imports a constant this change altered, the JSON arguments and result of its real calls: the first 20 distinct calls per function and process, after which the function is unwrapped. Nothing is replayed inside a test, so a test's results, its doubles and its coverage are those of a run without FlowGuard. Calls are recorded through a stub compiled from the function's text, read again in each test. When the file no longer holds the bytes FlowGuard's import finder loaded (another agent or a test saved it during the run), or the text at the line where the function's code starts (its first decorator's) no longer defines that function, the function keeps its own code in that test and is `not compared` (`not compared: area (source of app/mod.py changed on disk after import) -> not a failure`; for a module another loader read, `source of app/mod.py no longer holds area at line 5`); the probes and mutants `check` compiles from a function's text are refused the same way. After the tests the session compiles the function's source, with the same-file functions it calls, under the file name `<flowguard-sealed>` into globals that hold only `abs all any bool dict divmod enumerate filter float frozenset int isinstance len list map max min range repr reversed round set sorted str sum tuple zip`, the built-in exceptions, `math`, `decimal.Decimal` and `datetime`'s `date`, `datetime` and `timedelta`, whose `now`, `today` and `utcnow` refuse. A name it lacks makes the function `not compared` with the name (`uses unavailable binding RATE`). Module-level constants are read from the source, never run: literals, arithmetic on literals and earlier constants (`FACTOR = 10 ** DECIMALS`), and a literal constant imported from another module of the project (`from X import NAME`, or `import X` and `X.NAME`, X found by the importing file's own import root, never an installed package) when nothing in X's top level can change it. The audit hook and the watchdog stay around each sealed run. The baseline version runs from the baseline source the same way, a moved file from its old path, on a recorded call only where that call fits it: each value goes to the parameter of its name, a parameter the baseline lacks is left out where the call left it at its constant default (`over(x)` that became `over(x, strict=False)` is compared on `over(3)`), and every required parameter of the baseline has a value. Any other call is `not compared` (`not compared: person_label (labels.py:1) (parameters differ from the baseline) -> not a failure`, and `show --last` adds `was person_label(record), now person_label(kind, record)`), never a `changed` line of the `TypeError` the old version raised for an input it was not written for; a parameter only renamed counts as another one. A difference on a recorded input is a `changed` line with the first differing input, the old and the new value and how many inputs differ (`changed: label (fees.py:15): (days=3) was 'on time', now 'late'; 1/2 inputs differ -> if you meant it, say so`). A dict result, or a list of dicts as long as before, says which keys changed instead of its whole JSON, whose middle the block's 200 characters would cut away: `changed: parseSnapshotConfig (snapshot.ts:1): (text='{"version":4}') now adds demandPeriodConvention='legacy-half-open' (3 other keys equal); 3/3 inputs differ`, with `removes KEY` and `changes KEY from 1 to 2`, nested keys as paths (`summary.total`, `rows[1].b`, `[0].value` of a list), at most three keys named and the others counted (`2 more keys differ`); keys are compared by their JSON, as the whole values are. `show --last` prints each differing input once: the line's input on the line, with its full values under it (`in full: was {...}, now {...}`), and every other input in the detail, with its keys and full values. The same exception in both versions is `not compared`, never unchanged. Not compared: decorated, async and generator functions, methods, defaults that are not literals, arguments or results that are not JSON. A comparison is due only for such a function and for a name with two or more copies (a project in a subfolder of its Git repository is compared like one at the top), so a lone unchanged `same` function whose calls are not JSON is never listed. A `calibrated_by=tests/test_file.py::test_name` binding names one real ordinary test, including a parameter ID when relevant: the call that test made in its ordinary run is the context, the requested inputs are put in place and the source runs sealed. A named test that did not run, or whose call is not JSON, leaves the item not compared; one that did not pass is red. A scenario is read from the anchor events of its test's one run, so only the input it ran with is compared.

## Where rule fields come from

A rule runs only Python functions: one bound to a TS/JS function is red (`... is not Python: a rule runs only Python functions`), and TS/JS copies are compared by `same` alone. A rule bound to an anchor (`anchor="NAME"`) reads its fields, in this order:

1. The anchor's input parameters: the rule's own items run the anchor on each case class of the rule (`NAME[module.function:cells]`) and on its literal rows (`NAME[module.function:rows]`); no scenario test is needed.
2. Values hidden in the context, read on the anchor with one `fields` clause: `# flowguard: same FEE fields days=(today - hire.due).days member=customer.is_member`. Each `name=expression` is a Python expression over the function's own parameters and its module's names; it runs to the next top-level `name=`, so spaces, calls, strings and `==` stay inside it. On every call a test reaches, the expressions are evaluated in the closed environment of the comparison with that call's recorded arguments, never in the test: the environment has no connection and reads no attribute of a record, so a field read from a database or a record leaves the rule's item unverified with the first field it could not read, and an explicit write in a field is refused before it runs. The rule is then computed on parameters and fields together and compared with that call's outcome. The rule's `cells` item checks every such call, its `rows` item each literal row a call reached; a row no call reached, or a field that cannot be read, is grey (unverified) with the field's name and error; a disagreement is red with the rule's source sentence. A partial run without the rule's items still reports a red call at the end. `fields` combines with the parameter list, the `;` context separator and `calibrated_by=` in either order: `# flowguard: same FEE(today; db, hire) calibrated_by=tests/test_fees.py::test_fee fields days=(today - hire.due).days`; with `calibrated_by` only that test's calls count, and the test is not rerun. A field may not repeat a parameter's name; event and data-owner anchors take no `fields`; a malformed clause is red at its line with the way to write it. Mutation-survival checks (`--deep`) need a directly callable anchor and stay grey for `fields`.
3. When neither is possible (the outcome appears after the function returns, or the function writes), keep a scenario test and a small flow: an event anchor's `calibrated_by=` names the scenario test and a `Relation` connects its readings to the rule.

`show RULE` lists the case classes the rule gives no result for (`undecided: rule RID has no result for N classes`); when no rule of its decision decides them and a rule there says `total=True`, they are red. `req add` ends with the reminder that words setting a continuing rule go into `.flowguard/rules.toml` as a `[rule.<id>]` entry whose `source` quotes the stored id and its words. With `--offer FILE --picked TEXT` (and `--selected` for a pick made without typing) it stores the owner's pick among options the agent offered as one `choice` record of the same archive: his reply in `R2.md`, the options as the agent's words in `offers/R2.md`, the picked option texts and the reply's kind in the sidecar; its reminder names `R2 picked "<words of the picked option>"`, and for a typed reply also `R2 "<his exact words>"`. A `picked` source holds only for words that occur exactly in an option he picked, the option itself in the stored options; it is judged at the baseline with that commit's sidecar, reply and options, as a request source is.

## Fallback ledger

`.flowguard/ledger.toml` lists every handler that can end without raising, the same way an owner's handler-list test does. A key is `file:function:caught` (`<module>` outside functions, `BARE` for a bare `except`); its `count` must equal the code's, its `reason` says what the handler does and why it may stay in at least eight words, and its `rule = { file = "...", text = "..." }` quotes a sentence that file must still contain. A handler that raises on only one branch counts. A new, missing or vanished handler, a changed count or a sentence no longer in its file is red in ordinary pytest (the sentinel test fails and the closing FlowGuard lines print the entry to copy). Bare `except`, `except Exception`/`BaseException`, `contextlib.suppress` under any alias, warning filters, `return`/`break`/`continue` inside `finally` and an `__exit__` that may return true cannot be listed. `python -m flowguard ledger init` records the current handlers as legacy (`rule = "旧账"`); legacy entries may only shrink against the baseline commit and the init record, so only new handlers are reported. `check --all` and `check --static --all` list the legacy entries of production code (outside tests and archives) whose handlers do not hand the error on, by how the body ends: it returns or assigns a substitute value, only logs, or is empty (not listed: a handler that raises on some path, or that ends in other work without returning or assigning a value, such as `res.status(500).json(...)` or `show_error(message)`; in JS/TS a returned answer counts as that work too when it is method calls made one on another directly on a parameter named `res`, `reply`, `response` or `ctx` of an enclosing function, the last of them `json`, `jsonp`, `send`, `sendStatus`, `sendFile`, `download`, `end`, `redirect`, `render`, `text` or `html`, with an argument somewhere unless it ends in `end()` or `send()`, also under `await` or `void`: `return res.status(500).json(...)`, `return void res.status(500).json(...)`, `return reply.code(500).send(...)`, `return res.end()`; every other returned or assigned value is a substitute, a response value included: `return res.text()`, `return res.headers.get(name)`, `return ctx.get('user')`, `return res.status(500)`, a call on a local such as `const res = await db.query(...)`, `return new Response(...)`, `return Response.json(...)`, `return NextResponse.json(...)`, Koa's `ctx.body = ...`, a Hono context under its usual name `c`, and in Python every `return` with a value, `return JSONResponse(...)` included); review them one by one. It refuses when the project already keeps its own handler-list test: keep one of the two. `python -m flowguard ledger check` lists every difference without running tests. The scan covers every mapped source file; `[tool.flowguard.ledger] paths` and `exclude` narrow it. Files whose reader supplies no handler facts, or that do not parse, are listed as not checked. The ledger's `[structure]` and `[unverified]` sections, which 4.3 announced for removal, were removed in 5.0: a ledger that still has one gets one red input line naming it and what replaces it, and what it holds is not read. `[structure]` decisions become `known.toml` entries (`python -m flowguard known add NAME --act leave --why TEXT`, or `--act ignore`; see Map checks without tests and structure problems); nothing replaces `[unverified]`: restore the rule's observability so it is checked again.

## Owners and copies

One judgment or one field has one owner. `# flowguard: same NAME ref` above a function makes it the reference its same-name `# flowguard: same NAME` copies are compared with. The copies run in the closed environment on the recorded inputs, then each with every number the copies use, then the ±1 neighbours of both, kept once and cut at 64 inputs (a place for each number is kept before the recorded inputs are cut, and what the cut leaves out is named in the not compared line). Each input is judged on its own against the copies' task-start versions: copies that agreed on it and differ now are red there, and the next step names the copies to bring back to the reference (`red: same ACCEPT: on days=4: the reference orders.py:accept returns False, orders.py:preview_accept returns True -> make orders.py:preview_accept agree with the reference`); copies that already differed on it are `before`, or `known` when a `known.toml` entry names `same:NAME`; an input the task-start code could not run is not compared. Without a reference the red names what each copy answered and leaves the choice (`red: same FEE: on days=5: fees.py:late_fee returns 4, fees.py:preview_fee returns 6 -> decide which copy is right, then make the other agree`; of four or more copies three are named and the others counted): decide which copy is right and make the others agree, or rename the ones that should differ. Parameters correspond only by name: a copy with other names writes `# flowguard: same NAME(days=overdue_days)`, nothing is matched by position or type. An input one copy takes and another cannot be given (a parameter that copy lacks, or a required one the input leaves out) is not run on that copy, whose `TypeError` would be no answer; the copies are red as copies that take different parameters, `red: same PROJECT_SCOPE: scope.py:can_view(user, project) and scope.py:visible_projects(user, projects) take different parameters -> check whether these are copies of one decision, then correct the code or the marks` (a boolean check of one project and a list projection of projects are not copies of one decision), and `before: same PROJECT_SCOPE disagreed at task start: ...` where every copy took these parameters at the task start. `check` says the same of copies whose declared parameters differ. Copies that return different forms compare a projection, written without a colon: `-> result[0]` or `-> result.ok`; `-> name: type` stays an output declaration. A copy that uses `math` runs sealed with it; agreement on these inputs is a sample, not a proof.

`check` also runs the unregistered look-alikes of each reference (same number of simple parameters, and a similar 3-gram body shape or a shared number other than 0, 1, -1 and 2) on the reference's classes, in the closed environment. A look-alike with a similar structure that answers as the reference on at least half of them, but not on all, is a diverged copy: a `copies:NAME` finding, never red (`impact` when this change adds or edits the copy, `before` when it touches one the task started with, every one with `--all`). A new function that copies a reference registered at the baseline commit is an `impact` line, since automatic structure checks are never red. A function marked `same NAME` that this change edits, whose old version agreed with unchanged look-alikes on every representative while the new one differs, is red as `changed-alone:NAME`, which names those copies. 4.3 also listed each group of look-alikes, the candidates that could not run, the candidate count and time, and the look-alikes an unmarked changed function left behind, as leads only `show --last` printed; 5.0 removed those leads.

A field's writers are listed with `# flowguard: writers hires.reserved shop/store.py:reserve` (`// flowguard: writers Employee.organizationalUnitId transferEmployee` in TS/JS). Writes come from the map: Python attribute assignments (matched by name when no class binds them; each element of a tuple or list target, nested ones too, a starred element and a `for` or `with ... as` target is a write of its own, which takes the value at its place only from a right side of the same length: `self.state, self.code = 'stop', 0` writes `state` with `'stop'` and `code` with `0`, `self.a, self.b = pair()` and a loop target write no value), SQL `INSERT`/`UPDATE`/`DELETE` in Python string literals and TS/JS raw SQL, and Prisma client writes; a write row carries the literal value it writes when the source spells one. A write outside the writers that this change adds is red in pytest and `check`; older ones are the old ledger, listed by `check --all` and `show NAME`. A writer's own callbacks (the arrow function it passes to `$transaction`) write for it, and a test's own write is a fixture, not held to the agreement, as it is not to a pair. ## Removed in 5.0

`precedes`, `guarded_by`, `transitions`, `checks`, `Transition` with `flow(..., transitions=)`, `distinct`, `structure_rule` with `allow`, and `pytest.mark.rule` are gone. An intent file that imports or calls one is refused before it runs: its `load` line is red at that file and line and says what to write instead, for example `red: load order_rules.py:1: precedes was removed in 5.0 -> declare the order as flow(ID, source=..., nodes=[Node(...), ...], edges=[...]); until then none of its file is checked`; a name the file reaches only when it runs, such as `api.distinct(...)`, gives the same line, in pytest, `check` and the vitest report alike. A test marked `pytest.mark.rule` is a red `marker` line at the test. Copies that are meant to differ are recorded with `python -m flowguard known add copies:NAME --act ignore --why TEXT` once `python -m flowguard check --all` lists them (`check --static` runs no copy discovery); two rules of one `decides=` key must agree unless one `overrides=` the other. Copies use `same NAME` and `same NAME ref`, and a single writer uses `writers`.

The commands `anchor draft`, `model draft`, `try`, `watch` and `compare` and the options `show --draft`, `show --gaps`, `check --since`, `check --leads`, `req add --kind glossary` and `req add --kind adoption` were removed too: a use exits 2 before any project file is read, with one line on stderr such as `flowguard: try was removed in 5.0 -> python -m flowguard new-task, check or show NAME`. `req add --kind request`, 4.3's default, is still accepted and changes nothing. The ledger's `[structure]` and `[unverified]` sections (see Fallback ledger) and the 4.2 comment spellings (see above) are red lines that name their replacement. The deprecation notices 4.3 printed on stderr and the `deprecated features used` line of `show --last` went with the features they announced: 5.0 reports what it removed as a red line or a usage error, never as a notice. The [5.0 notes](upgrade-5.0.md) give each removal with its line, its replacement, a valid example and a rejected one.

## Generated source queries

The base installation maps Python. The seven foreign readers are frozen optional additions: install the `languages` extra to map JS/JSX, TS/TSX, C, C++ and C#. Grammars load only when their source language is present; unavailable grammars are reported explicitly. `[tool.flowguard] exclude = ["translations/*.ts", ...]` lists files the map never reads, beside its own defaults (`.flowguard/`, `.git/`, `__pycache__`, `node_modules/`, `dist/`, `build/`, `.venv/`, minified JS); the patterns are paths from the project root, `**` crossing folders and `*` one folder name. One decision (`store.mapped`) picks what the map reads, what changed against the task baseline and what is read at that baseline, so a listed file is never parsed, also when it differs from the baseline, and its reader need not be installed (Qt Linguist `.ts` catalogues are XML, not TypeScript); a source inside an interpreter or dependency environment (a folder with `pyvenv.cfg`, `site-packages`) is left out the same way. A change of pyproject.toml runs the map checks in pytest too. When it takes files out of the map, each `same`, `together` and `writers` agreement their baseline versions held is a `loosened` line: `loosened: same RATE removed from app/b.py:rate (its file is now excluded by [tool.flowguard] exclude) -> name it in your report; loosening an agreement is the owner's decision`. A Python file's agreements are its baseline facts; a JS/TS file's are read from its `//` comment lines as text, without its grammar, so a `same` there is named by its line (`same RATE removed from web/b.ts:2`) and a comment after code on its line is not read. An included file whose reader is not installed stops `check --static` with exit 2 and its text (`flowguard: web/a.ts: typescript reader unavailable: missing tree-sitter -> pip install "flowguard[languages] @ git+https://github.com/liuyingxuvka/FlowGuard.git", or list it in [tool.flowguard] exclude`). In pytest the same error, and any other that stops the map checks (Git, the cache), is one red line after pytest's own summary, `red: map checks: web/a.ts: typescript reader unavailable: ...` with that step, in JUnit XML the `flowguard::session` case; the tests' own outcome stays and the run exits 1. `show --last` adds that the map checks did not run, and, when the map could not be built as the session began, that the functions the change edits that no flowguard comment names, and the files that import a constant it changes, were not compared. Python has the full executable behavior anchors; TS/JS has the minimal vitest execution side described above. Foreign syntax supports navigation and explicit source checks; it does not execute the application or replace a compiler. Dynamic calls, macros, overloads and external/build-dependent bindings remain unknown with reasons.

`graph.capabilities()` exposes actual languages/files, parser errors, available grammars and supported queries. `graph.query_coverage()` reports the queries this handle actually served and any unavailable or failed source scope. `functions()` tracks nodes, assignments and keys are tracked, and `calls(include_reads=True)` also requests symbol-read coverage. `nodes(file=...)` and `language="python"` make an intentional source boundary explicit. Foreign handlers, literal sets, test discovery and full symbol reads are not yet implemented. Each check has its own scope; direct library users can call `reset_query_coverage()` before a separate query.

The shared cache is invalidated by source changes, reader/grammar versions and project parser configuration or compilation-option content. Unsupported configuration, dependencies outside mapped roots and unresolved bindings stay unknown; cached syntax is not evidence of successful compilation or execution. Several FlowGuard runs may use one cache at once (the checks of two packages, a vitest run beside `check --static`). A build reads the files and plans against the map in one read transaction, parses the files that changed with no transaction open, and takes the write lock only to plan once more against the map as it then is and write what still differs: a file another run wrote with the same bytes meanwhile is left as it is, a file saved again since the parse is parsed again under the lock, and a map that already holds the files takes no write lock. So one run waits for another's write, never for its parse. Every connection, reader or writer, waits up to 30 s for another run's lock; a write that has waited 5 s says so once on stderr, `flowguard: waiting for .flowguard/cache/map.sqlite (another FlowGuard run is writing it; 5 s so far, at most 30 s)`, and a wait that runs out stops with sqlite's error and its text.

Fingerprints help find changed code and possible moves. They do not establish cross-language equivalence or prove behavior merely because names or shapes match.

## Use hierarchy only when it removes repetition

An upper behavior rule can declare `uses=[LOWER]`. A scenario relation connects actual lower and upper readings; the engine derives the logical-input binding and supplies verified joint witnesses. Lower sources and anchors must pass too; explicit deep checks additionally require mutation liveness. Joint checks combine all verified lower inputs, through nested uses, instead of changing one lower input at a time. Closed boolean/enum domains can have complete finite coverage. Open domains use supported partition representatives and report that boundary; they are not enumerated value by value.

Keep behavior decomposition in those actual uses relations. It requires no whole-application model, separate hierarchy format, or model of the current development task.

Source anchors replace the old `.home` decorator. The [3.0 guide](upgrade-3.0.md) describes that older input migration; [4.0](upgrade-4.0.md) changes the execution boundary. A complex flow has only nodes, edges and existing-rule reading relations.

A `Node(..., model="CHILD_FLOW", phase="return")` can consume a registered child Flow's output. The child exports one existing Rule through an explicit `Relation(..., actual=Read("end"), on="end")` at a terminal return/raise node; the parent names that same source anchor and phase. Its Rule contract and joint witnesses still apply, and the child graph's finite and runtime checks must also pass on the same observed invocation batch. Deleting an internal save cannot leave that parent green merely because the exported boolean stayed unchanged. A test-entry Flow can supply the existing ordinary-test scenario binding separately from the production graph.

Each exported event needs one declared production start call in the child graph. Its matching return can be the export; nested check/save calls remain steps inside that start. Different invocations retain separate event scopes and share only coverage accounting. Missing or multiple exports, unregistered Flow objects, cycles, unavailable source identities and unobserved model edges remain grey. There is no fixed ten-layer depth cap; keep each layer near ten meaningful nodes so it is understandable. A flow's finite model is its graph, each node one state, and it is fully explored without a default fixed state cap; an invariant over a state field stays unverified. A same-named Rule or saved green metadata does not verify a child graph.

Default Flow verdicts cover observed anchor paths and the declared finite model. Unexecuted source routes remain unverified; an observed green does not prove that the source has no other route. Static path analysis is frozen and is not run by the engine; its direct SDK helpers remain available for their narrower explicit source scope.
