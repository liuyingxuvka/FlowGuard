# Intent guide

The canonical API guide and executable two-anchor example are in [the skill's local reference](../.agents/skills/flowguard/references/rules.md). The skill installer copies that reference with SKILL.md, so the first rule does not depend on retrieving a web page or guessing the API.

Run ordinary pytest with the plugin enabled. Its default output compares supported old/new behavior, checks same-name sensors, and reports violated independent rules. The closing block names its baseline commit (`FlowGuard（相对任务开始 a1b2c3d）`) and prints four kinds in this order: every red (`红`), with the places of one rule or owner on one line, its source sentence and the next step to copy on the indented lines below; then changed outcomes and paths (`变`), leads (`线索`) and an unverified summary (`未验证 N 项（不是通过）`). Those last three share at most ten lines; names and places are never shortened, an unchanged point is not printed (with `--flowguard-base` it is, as `比较：… 变 0 类` after every change line, and its overflow reads `比较：另 N 项没有变化：…`), and repeated grey reasons are merged and counted. A run without a source change prints nothing unless a constraint fails or the recorded task start is not in the repository, which one title line names. Rules, source comments and small models preserve useful decisions; there is no task-modeling ceremony.

Grey is not a pass. A grey intent item has its own pytest outcome: `U` with `-q`, `UNVERIFIED` with `-v`, `N unverified` in the summary; the exit status does not change, and no warning, skip or xfail is used. An anchor or rule whose baseline code the same call can still replay, while the current code turns it grey (a new write, a result that is no longer simple data, or a function that became a generator or coroutine, whose first entry in the test supplies the arguments), is a lost observation and fails the run. Either restore the observation at the line the output names, or list the anchor or rule under `[unverified]` in `.flowguard/ledger.toml` (`NAME = "reason"`, at least eight words). Without a baseline commit (CI) nothing can be lost. `check --all` fails a grey rule or Flow (a one-line template included) whose source quotes the owner's words, unless `[unverified]` lists it by name; the session brief counts such a template among its rules. A Flow item (`NAME[flow]`) runs after the ordinary tests and the other intent items, and is judged on their anchor events and on its lower rules' contracts from their items: a green Flow passes, a red one fails, unwalked declared edges keep it unverified. With `--junitxml` a grey item carries the testcase property `flowguard_outcome=unverified`, and a red that no test carries (a lost observation, an inconsistent copy, a new structure problem, the ledger) is the failed testcase `flowguard::session`, whose message is the closing block. These session verdicts need every test in one pytest process: with pytest-xdist workers (`-n 2`, `--dist` with `--tx`) the plugin stops with a usage error before any test runs, because the xdist controller does not read a red found in a worker; run without `-n`, or with `-n 0`.

`check --deep` explicitly adds decision-site probes and mutation-survival checks. Default tests and checks do not claim mutation adequacy. `check --all --deep` runs all intent items and ordinary tests in CI, with live pytest output; a partial or non-deep collection cannot substitute. Publication requires one complete successful CI run on the exact main commit, with all three supported unsharded platforms and their required execution steps. There is no observation subprocess, nested pytest session, shard aggregator or separate diagnostic pipeline.

The shortest source comment is `# flowguard: sensor NAME`. Confirm the proposed meaning and units after `anchor draft module:function`; full comments remain valid. Simple input parameters can be varied, while context objects remain supplied by the actual test. A call-site replay (the current code, the baseline code swapped in, the original-value recheck) runs under a guard, in the replaying thread and only while the replayed call runs: an audit hook, installed with the first replay, refuses file writes, deletions, directory and extended-attribute changes, processes, signals, threads and network access before they happen, and wrappers refuse `threading.Thread.start`, `os.mkfifo` and `os.mknod` (and `_thread.start_new_thread` on Python 3.11), which raise no audit event. sqlite3 connections in the arguments and in the module state the function reads, at any depth, hold a `SAVEPOINT` and a read transaction (nothing can be backed up into them), are `query_only` and refuse writing statements and Python-defined SQL functions and aggregates; afterwards they return to the savepoint and are checked with `total_changes` and their callbacks. A connection opened during the call through `sqlite3.connect` is protected the same way; one opened through a name bound before the replay (`from sqlite3 import connect`) is refused before it opens. A refusal voids the replay with the project line that caused it, also when the replayed code catches it; a replay that runs longer than the copy-discovery timeout or recurses too deeply is void too, and its reading is grey until the replay has completely finished. Log records made in a replayed call are dropped, the `random` module's state is restored, and the original-value recheck runs at least one clock tick after the first call. Arguments are replayed on deep copies. Not replayed: an argument that cannot be copied or that deepcopy returns as itself, a generator, an open file, a csv reader or writer, a function or bound method, a logger, a queue or executor, a sqlite3 Blob, a socket, another database driver, a sqlite3 connection with a Python authorizer, progress handler, trace callback or row factory (an authorizer cannot be read back; `sqlite3.Row` is native), the same in the module state the function and its project helpers read (functions and loggers there are fine), and anything larger than 10 000 objects. A connection with Python SQL functions, aggregates or collations is replayed: a function or aggregate is refused when a replayed statement calls it, while a collation runs again (a known miss). The static check stops only explicit writes: `global`, assignments and mutating calls on module state (module and class attributes and local aliases of module state included), module state passed to a standard function that changes it (`heapq`, `bisect.insort`, `next`, `list.append(...)`), and a change to a sqlite3 connection the replay shares with the test (`close`, `create_function`, `backup`, `row_factory = ...`), also in the project helpers it calls; reads, dates and `.days` replay. Known misses: a write by a C extension or into a file or connection the guard cannot see, a wrapped function bound to another name before the replay (`from os import mkfifo`), in-memory effects of project operators or callbacks, an SQL function or collation added to, or a `close` of, a shared connection where the static check cannot follow (the replay is void; the function stays, the connection stays closed), output to `sys.stdout`, warnings, other libraries' global random state, and a function that rounds the clock to a coarser step itself. A `calibrated_by=tests/test_file.py::test_name` binding names one real ordinary test, including a parameter ID when relevant. Scenarios reuse that collected session and fresh function fixtures; unavailable shared-scope or ambiguous context stays grey.

Optional views use the same runtime and historical cache. `show NAME` displays anchor parameters, result distributions and citing rules, or a model's node/edge counts and missing or invalid paths. Old observations are labelled historical and become stale after source changes. `try NAME days=4` explores an exact input; `--grid` prints every evaluated representative without claiming that unknown partitions are complete. `watch -- python app.py` runs Python normally, records anchors and checks the loaded models. `model draft NAME` proposes existing Flow nodes and edges from recorded paths; it does not invent required paths, transitions or relations. These commands are not extra default steps.

The brief from `python -m flowguard` fits ten lines and remembers the current task's baseline commit: it records HEAD only when no baseline is recorded or the recorded one is not an ancestor of HEAD (another branch, rewritten history) or not in the repository, so commits made during a task keep its baseline and what the task changed stays reported; the brief then says how many commits the baseline lies before HEAD. On a detached HEAD (a tag or an older commit looked at during a task, a bisect step) the brief neither moves nor records a baseline and says so; back on the branch the task's commits are still reported. Every pytest session with the plugin, `check` and `check --static` record HEAD only when no baseline is recorded and HEAD is a branch, so a project that runs only `init` and pytest records one at its first run on its branch (a fresh clone in CI compares that first run with its HEAD, as before). A session that only collects tests (`--collect-only`, IDE discovery) and a run on a detached HEAD (a tag or an older commit checked out, a bisect step, a CI checkout) record nothing: they compare with HEAD. They never move a recorded one, not even when HEAD does not descend from it: a run on an older commit, another branch or a bisect step compares with the task start, and back on the task's branch its commits are still reported. Only the brief and `new-task` move it, and they say why. A run without a Git commit records nothing, nor does a run with `--flowguard-base` or `--base`, which name their own and keep it in the command their lead-overflow line prints (pytest's `--flowguard-base X` as `check --static --base X --leads`). `python -m flowguard new-task` starts the next task: HEAD becomes the baseline, also on a detached HEAD, then it prints the brief; when the start it replaces lies commits before HEAD, it says those commits are no longer compared and how to compare them once (`python -m pytest --flowguard-base OLD`; in a project whose tests npm runs and pytest finds none of its own besides FlowGuard's sentinel, `python -m flowguard check --static --base OLD`). The CI fragment `init` writes runs `check --all --deep`, or there `check --static --base` with the merge base of HEAD and `origin/main` (a CI checkout is a detached HEAD, whose task start is HEAD itself); its comment says to replace `main` when the default branch has another name. Rule 1 of the block `init` writes starts each task with it. `check --base COMMIT` explicitly changes the comparison baseline of one run. The title of pytest, `check` and `check --static` says `相对任务开始` for a recorded baseline, with its distance and the next task's step once HEAD lies commits after it (`FlowGuard（相对任务开始 a1b2c3d，HEAD 之前 2 个提交；新任务先运行 python -m flowguard new-task）`: until `new-task` runs, the commits of earlier tasks count as this task's change), and `相对 HEAD` where HEAD stands in because none is recorded (a detached HEAD included). A recorded commit the repository lacks (a shallow clone, history rewritten and collected, a cache copied from another clone) compares nothing: pytest, `check` and `check --static` print one title line that names it with the next step (`FlowGuard（记下的任务开始 a1b2c3d 不在这个仓库里：不比较改前改后；先运行 python -m flowguard new-task）`), even with no source change, and `ledger check` prints the same line first; the brief on a branch or `new-task` records HEAD (on a detached HEAD the brief records nothing and says so). The vitest side records nothing, so its runs before the task's first `check --static` (which `flowguard.static.test.mjs` runs), pytest or brief compare with HEAD and say `相对 HEAD`; its report's title gives a recorded start's distance from HEAD as pytest's does, and with a recorded commit the repository lacks it prepares nothing and names that commit. A rule cites only its relevant original words or authority document; preserve those bytes once with `req add`, never an AI's interpretation or plan. See [the 4.0 migration](upgrade-4.0.md) for removed interfaces.

## Where rule fields come from

A rule bound to an anchor (`anchor="NAME"`) reads its fields, in this order:

1. The anchor's input parameters: the call-site replay computes the rule on every replayed class, no scenario test is needed.
2. Values hidden in the context, read on the anchor with one `fields` clause: `# flowguard: sensor FEE fields days=(today - hire.due).days member=customer.is_member`. Each `name=expression` is a Python expression over the function's own parameters and its module's names; it runs to the next top-level `name=`, so spaces, calls, strings and `==` stay inside it. On every call a test reaches, the expressions are evaluated with that call's arguments before the real call, and again with each replayed class's arguments; the evaluation is a guarded execution like the replay itself (the static explicit-write check at the comment's line, the audit hook, the sqlite savepoint and authorizer, copied arguments), so a database read stays observable and a write is refused. The rule is then computed on parameters and fields together and compared with that call's outcome. The rule's `cells` item checks every such call, its `rows` item each literal row a call reached; a row no call reached, or a field that cannot be read, is grey (unverified) with the field's name and error; a disagreement is red with the rule's source sentence. A partial run without the rule's items still reports a red call at the end. `fields` combines with the parameter list, the `;` context separator and `calibrated_by=` in either order: `# flowguard: sensor FEE(today; db, hire) calibrated_by=tests/test_fees.py::test_fee fields days=(today - hire.due).days`; with `calibrated_by` only that test's calls count, and the test is not rerun. A field may not repeat a parameter's name; event and data-owner anchors take no `fields`; a malformed clause is red at its line with the way to write it. Mutation-survival checks (`--deep`) need a directly callable anchor and stay grey for `fields`.
3. When neither is possible (the outcome appears after the function returns, or the function writes), keep a scenario test and a small flow: an event anchor's `calibrated_by=` names the scenario test and a `Relation` connects its readings to the rule.

Two static leads cover a requirement that changed while its rule did not: the rule still holding the replaced value (see Owners and copies), and `STANDING 的副本 x.py:f 改了，规则 STANDING 没改` when a function this change touches (its body, a constant it reads or a function it calls) is a rule's anchor or a same-name copy and the change does not touch that rule's file; the line names both next steps (a changed need: store the new words, then change the rule; otherwise confirm the code change). `show RULE` lists the case classes the rule gives no result for (`没表态`); when no rule of its decision decides them and a rule there says `total=True`, they are red. `req add` ends with the reminder that a lasting requirement becomes a rule in the intent folder citing the stored id.

## Fallback ledger

`.flowguard/ledger.toml` lists every handler that can end without raising, the same way an owner's handler-list test does. A key is `file:function:caught` (`<module>` outside functions, `BARE` for a bare `except`); its `count` must equal the code's, its `reason` says what the handler does and why it may stay in at least eight words, and its `rule = { file = "...", text = "..." }` quotes a sentence that file must still contain. A handler that raises on only one branch counts. A new, missing or vanished handler, a changed count or a sentence no longer in its file is red in ordinary pytest (the sentinel test fails and the closing FlowGuard lines print the entry to copy). Bare `except`, `except Exception`/`BaseException`, `contextlib.suppress` under any alias, warning filters, `return`/`break`/`continue` inside `finally` and an `__exit__` that may return true cannot be listed. `python -m flowguard ledger init` records the current handlers as legacy (`rule = "旧账"`); legacy entries may only shrink against the baseline commit and the init record, so only new handlers are reported. `check --all` and `check --static --all` list the legacy entries of production code (outside tests and archives) whose handlers do not hand the error on, by how the body ends: it returns or assigns a substitute value, only logs, or is empty (not listed: a handler that raises on some path, or that ends in other work without returning or assigning a value, such as `res.status(500).json(...)` or `show_error(message)`; in JS/TS a returned answer counts as that work too when it is method calls made one on another directly on a parameter named `res`, `reply`, `response` or `ctx` of an enclosing function, the last of them `json`, `jsonp`, `send`, `sendStatus`, `sendFile`, `download`, `end`, `redirect`, `render`, `text` or `html`, with an argument somewhere unless it ends in `end()` or `send()`, also under `await` or `void`: `return res.status(500).json(...)`, `return void res.status(500).json(...)`, `return reply.code(500).send(...)`, `return res.end()`; every other returned or assigned value is a substitute, a response value included: `return res.text()`, `return res.headers.get(name)`, `return ctx.get('user')`, `return res.status(500)`, a call on a local such as `const res = await db.query(...)`, `return new Response(...)`, `return Response.json(...)`, `return NextResponse.json(...)`, Koa's `ctx.body = ...`, a Hono context under its usual name `c`, and in Python every `return` with a value, `return JSONResponse(...)` included); review them one by one. It refuses when the project already keeps its own handler-list test: keep one of the two. `python -m flowguard ledger check` lists every difference without running tests. The scan covers every mapped source file; `[tool.flowguard.ledger] paths` and `exclude` narrow it. Files whose reader supplies no handler facts, or that do not parse, are listed as not checked.

## Owners and copies

One judgment or one field has one owner. `# flowguard: owner NAME` above a function makes it the reference its same-name `# flowguard: sensor NAME` copies are compared with, class by class; a difference is red, and its next step names the copies to bring back to the owner. Without an owner the red counts what each copy answered on the first differing input and leaves the choice: decide which copy is right, make the others agree, or rename the ones that should differ and write `distinct`. Parameters correspond only by name: a copy with other names writes `# flowguard: sensor NAME(days=overdue_days)`, nothing is matched by position or type. Copies that return different forms compare a projection, written without a colon: `-> result[0]` or `-> result.ok`; `-> name: type` stays an output declaration. Importing `math` does not make a numeric copy grey: when its classes cannot be read, fixed representative values (boundaries, halves, negatives, NaN and infinities) are all run, and agreement on them is reported as a sample, not a proof.

`check` also runs unregistered look-alikes of each function owner (same number of simple parameters, and a similar 3-gram body shape or a shared number other than 0, 1, -1 and 2) on the owner's classes, through the runtime's call-site replay with a watchdog timeout, and groups them: copy (equal on every representative), forked copy (similar structure, at least half equal), similar (a shared number only); unrelated look-alikes are not listed, and a candidate that cannot be imported or run is listed as unclear with its reason. It prints the candidate count and time. A new function that copies an owner registered at the baseline commit is red. A changed function whose old version agreed with unchanged look-alikes is a lead that names them and the owner comment to copy; once registered, the same-name check makes it red.

A data owner lists its writers: `# flowguard: owner hires.reserved writers=shop.store:reserve` (`// flowguard: owner Employee.organizationalUnitId writers=transferEmployee` in TS/JS). Writes come from the map: Python attribute assignments (matched by name when no class binds them), SQL `INSERT`/`UPDATE`/`DELETE` in Python string literals and TS/JS raw SQL, and Prisma client writes; a write row carries the literal value it writes when the source spells one. A write outside the writers that this change adds is red in pytest and `check`; older ones are the old ledger, listed by `check --all` and `show NAME`. Without a baseline commit nothing counts as new.

A data owner can also name its pairs: `# flowguard: owner Employee.orgUnitId with=CentralEmployee.orgUnitId[=value] alone=import_rows(reason)`. Each write of the field must also write each `with=` field (with that value, when given) in the same operation: the writing function's callers three levels up, then everything they call three levels down (a caller that writes one field through one helper and its partner through another is one operation; JS/TS calls are resolved by name inside the caller's package, the folder of its nearest `package.json`; from production code the way up does not enter test files); a function listed in `alone=` may write it alone, with its reason, and a test's own fixture write is not held to the pair. `on=update` after the `with=` list holds only the writes that change an existing row (`update`, `updateMany`, upsert's update branch, SQL `UPDATE`, an attribute assignment): `// flowguard: owner Employee.sapReference with=Opportunity.responsibleSapNumber on=update` asks every renumbering to carry the references along, while a function that creates an employee is not held; `on=create` holds only the writes that make a row (`create`, `createMany`, upsert's create branch, a nested create, SQL `INSERT`). Its red names the limit (`（只查修改）`, `（只查新建）`). A missing partner is red when this change adds the write or the rule; `check --all` lists every one. `show Model.field` names the fields at least half of the field's writing functions also write, with the writers that leave each out, as `with=` candidates to copy once the owner says they change together (a reference, never a red). Write rows read the value an enum member, a module constant or each branch of `a if c else b` folds to (in TS/JS also each branch of `c ? a : b` and the fallback of `x ?? 'v'`, which the value gate judges); `row['status'] = ...` is a write of the key `status`, and a class-body default belongs to its class. One value gate checks every readable write of a declared field against its set, wherever the write is: a `# flowguard: states Class.field = a | b` comment, a `states(...)` declaration, or an enum annotation (`status: RunStatus`, plus `None` when the annotation allows it). Copy discovery also runs the strings and numbers the compared functions' own code spells (an alias table's keys too), so two copies with different tables fork. Copies are grouped by their first difference in a fixed order; the header says which values were compared, not whether callers reach them.

Static leads need no replay: an old value this change replaced that other decisions still spell (any field name; also members of tuple and dict constants), a rule in `tests/intent/` whose predicate or literal rows still hold it, a function whose old body an unchanged function still has, a label spelled a new way (case, spaces and punctuation aside) next to existing spellings of the same kind in production code (an UPPER_SNAKE code, words with spaces, a key or id, each after its leading `/`, `--` or `.`, group only with their own kind; a spelling only tests use does not count), and two declarations of one name (an enum, `X = Literal[...]`, a TS union alias) with different members. A changed unit (days to seconds) is a known miss. Leads only report what this change adds.

## Map checks without tests and structure problems

`python -m flowguard check --static` runs the map checks alone, without pytest, and prints them as an ordinary test run ends: the fallback ledger, writes outside a data owner, registered pairs, values outside a declared set, deletes that leave restricting children, columns one description of a table lacks, new label spellings, old values still spelled elsewhere and unchanged look-alikes of a changed function. It reports what this change adds against the task baseline (or `--base`) and exits 1 on red; `--all` also lists the old ledger, after what this change adds. Leads share the ten-line budget; their overflow line names `--leads`, which prints every lead (`check --leads` too). Ordinary pytest with the plugin runs the same checks, with the same TS/JS owners, whenever the change touches a mapped file, a TS/JS, Prisma or SQL file as well as a Python one. In TS/JS the value gate reads the enums of the Prisma schemas the generator uses (each `schema.prisma`, and a file or folder a `package.json` names in `"prisma": {"schema": ...}` or a script's `--schema`, or the `schema:` of a `prisma.config.ts` beside it, reading every `package.json` from the schema's nearest package up to the repository root; the config is read without its comments, as a string, a quoted key or `path.join`/`path.resolve` of string literals after `__dirname`, and a variable there names nothing; a `schema.sqlite.prisma` template only describes; several Prisma files in one folder of which at most one has a datasource, none repeating another's model or enum, are one schema split into files, all in use when one is, their enums, models and datasource read together, while schema files and provider templates side by side, each with its own datasource, stay apart; a package whose Prisma files name none of these is judged by each of them, for the models no schema in use defines and for the writes of that package and of packages whose Prisma files do not define that model, each enum a set of its own (one for the files that spell it alike), and its red lines say so; a Prisma file under a `docs` folder is an archive, neither in use nor guessed), SQL `CHECK (col IN (...))` sets (the latest in a migrations folder; SQL under a `docs` folder is an archive and left out), both when a field has both, and interface, class or object-type members annotated with a closed string union or `(typeof X)[number]`/`[keyof typeof X]` of an `as const` array or object; it judges Prisma `data` values against the database sets (by the schema in use of the write's own package that types the field with an enum, the nearest package defining the model: another schema of that package that lacks the field (a client that reads other columns) or a template without a client of its own that types it as text (SQLite's `role String`) neither judges it nor stands in the way, and when no schema of the package types it with an enum no enum judges it; a package with none by the first schema in use by path whose enum types the field; an object typed from one schema's client output by that schema, by no enum when its field is none; when two schemas in use of that package type the field with different enums, or one that writes a client of its own (`output = ...`, another database) types it as text, a write that does not name its client, `prisma.x.create` or a type from `@prisma/client`, is judged by neither), and `Name.KEY` members of such objects, class field initializers, `this.f = ...` and objects written as `const x: T = {...}`, `satisfies T` or `as T` against the TS type's own sets (a typed object is of the type its own file declares under that name, an interface, class or type alias at the top of the file, else of the one in the module it imports the type from by a relative path, and only a set that declaration gives the member judges it: each component's `interface Props` judges its own objects, and one whose member is `variant: string` judges none; an object of neither is judged by the member's set when it has one, not at all when the declarations' sets differ; a TS type is not the Prisma model of its name, unless the file imports it from the Prisma client: `import type { Item } from '@prisma/client'`, also as `{ Item as Row }`, as `P.Item` of `import * as P` or `Prisma.Item` of `import { Prisma }`, or from the folder a mapped schema's `generator` block writes the client to with `output = "..."`, by a relative path or, for a folder inside `node_modules` (`../../node_modules/.prisma/central-client`), by the package name after it (`.prisma/central-client`) from the files under the folder that holds that `node_modules`; an output folder is read before the generic `@prisma/client`, `.prisma/client` and `generated/prisma` spellings, and a schema in use owns it over a provider template with the same generator block; the red names the model's field; a module of the project that re-exports the client's types is not followed). `new Set([...])` and the other named sets also feed "two declarations differ" (exported ones only), and so do the declarations of one database field: each Prisma schema's enum, templates included and archived files left out, each SQL description's CHECK and an exported JS/TS declaration named like that enum. A delete lists the NoAction/Restrict children (a relation without `onDelete` is Prisma's Restrict unless every key field is optional) that no function of the same operation deletes, nulls or counts, also inside `OR`; the operation is the deleting function's callers three levels up and what they call three levels down, JS/TS calls resolved by name. Tables the code never creates or updates rows in and Cascade/SetNull relations are left out, and so is a self relation whose parent key can be null (the relation field or one of its key fields optional: a tree's parent, also under a required tenant key) unless the delete removes one row, outside a loop, of a table whose rows the code creates with that self reference set. `init` with a `package.json` writes `flowguard.static.test.mjs` (vitest) or `flowguard.static.test.js` (jest; an ES module in a `"type": "module"` package whose scripts run jest under node's `--experimental-vm-modules` or not at all, else CommonJS, since jest without that flag loads every test as CommonJS), which finds Python through `FLOWGUARD_PYTHON`, the interpreter that ran `init` on this machine (recorded in the git-ignored `.flowguard/cache/python`, so no committed file names a machine path), then `python3`/`python`/`py -3`, prints the report and fails on red or when no Python can import FlowGuard. A test suite script (`test`, `test:...`, `unit`) that runs the runner on named folders only (`"test:unit": "vitest run tests/unit"`) would skip that file: `init` adds it to one such script and says so, `test` first, then `test:unit` (`test-unit`, `test_unit`, `unit`), other unit names, shorter names and the order of the file; nothing is added when any call of a test script already names the file (`./` too). Watch scripts (a name part `watch`, `--watch` or `--watchAll` unless set to `false`, `vitest watch`) and debug scripts (a name part `debug`, or a call that waits for a debugger: `--inspect-brk`, `--inspect-wait`) are never the one, nor a suite that reaches real databases and services: a part of its name (split on `:` `_` `-`) or a whole folder of a path it runs (split on `/`, so `src/db` but not `src/lazy-load`) is `int`, `it`, `e2e`, `db`, `database`, `smoke`, `acceptance`, `perf`, `performance`, `load`, `bench` or `benchmark`, or starts with `integration`; when nothing runs the file, `init` names the suites it left alone. `init` reads a call only when each of its options is one it knows to leave the files alone (reporters, workers, timeouts, coverage: `--reporter`, `--maxWorkers`, `--coverage`, `--ci`, jest's `-w`, `--reporters`, `--coverageReporters` and `--no-watchman`, vitest's `--no-color`, ...); a call with any other option (its own root, folder or config, a project, test names, a shard, changed files, ignore patterns, an option `init` does not know) may run any files, so `init` neither wires it nor counts it as running the file, and names it with the edit to make (`&& vitest run flowguard.static.test.mjs` at its end) when it is `test`, runs named paths, or when nothing runs the file. An option's value is never a path: the next word after a valued option (`--reporter dot`), after a prefixed option (`--coverage.include src`) and after vitest's `-u`/`--update` (`-u tests`), the last two kinds only when it is no option; after vitest's `--silent` only `true`, `yes`, `false`, `no` or `passed-only` (vitest 3.1 on refuse any other word there, and earlier versions read `--silent tests/unit` as a flag and a path); `true` or `false` after a flag, vitest's boolean prefixed options (`--coverage.enabled`, `--sequence.shuffle`) included; `true`, `yes`, `false` or `no` after a prefixed option vitest versions read differently (`--coverage.all` and the `--poolOptions` booleans, flags in vitest 3 that vitest 4 dropped, `--coverage.thresholds.autoUpdate`, a flag in vitest 3 and valued from 4, `--coverage.thresholds.perFile`, valued from 5, and vitest 5's `--coverage.excludeAfterRemap` and `--coverage.autoAttachSubprocess`), and a call that gives one of them another word is one `init` cannot read (vitest 3 runs `--coverage.all tests/unit` on tests/unit, vitest 4 on every file); every word after jest's `--reporters` or `--coverageReporters` up to the next option, also after `--reporters=default`; any other option written `--option=value` takes no further word. So `vitest run --coverage.include src` runs every file and stays as it is. The file goes at the end of the call, or right after its last path when its last option would take the file as its value (`vitest run tests/unit flowguard.static.test.mjs -u`, `... --silent`, `jest tests/unit flowguard.static.test.js --reporters=default`). The runner is also the file node starts it from (`node --experimental-vm-modules node_modules/jest/bin/jest.js`, `node node_modules/vitest/vitest.mjs`). The edit named for one script starts the runner the way that script's call does; the other lines start it as `vitest run` or `jest`, but jest runs the ES module test of a `"type": "module"` package only under node's `--experimental-vm-modules`, so there they start it the way the first script that has that flag does, with only its `cross-env`, its `NODE_OPTIONS` reduced to the flag, `node` with the flag and the runner (never its other settings, such as a database URL, or node flags, such as `--inspect-brk`), else as `node --experimental-vm-modules node_modules/jest/bin/jest.js`, and a call without the flag, which cannot load that test, counts as no call, and the call that runs it alone goes through `npx` only where the shell needs it. A script `init` cannot edit without touching the rest of the file is named with the replacement to make, and the next one is tried. vitest's `-w` watches. The line `init` prints names what runs the check: `npm test` only when the `test` script runs every file or names this one, else `npm run <script>`, never a watch or debug script or such a suite, or that it finds no script (or only those), with the edit to make; the suites it left alone are named only when nothing runs the file. A `package.json` that names no test runner (vitest or jest in its dependencies or scripts) gets no test. FlowGuard's own generated files take no part in the label leads. `init` registers the pytest plugin once: in `addopts` when `pyproject.toml` is pytest's configuration, else in the sentinel's `conftest.py`. It lists test files that import a FlowGuard module this version lacks (0.70's `flowguard.map.facts` bindings) with the `norecursedirs` line that keeps pytest out of their folder, and in an `AGENTS.md` written for FlowGuard 0.70 it replaces the 0.70 workflow sections with the rules block, updates the install line and the pinned statement (`Use FlowGuard **0.70.14**`) and then lists, unchanged and numbered as the file it wrote, every line outside the rules block that still names a command of FlowGuard 0.70 or 1.x (`flowguard read`, `flowguard change`, `map check`, `target start`, `flowguard status`, also after `py`, `python3.11` or `python.exe`; a ban names it too), 0.70's test launcher, a 0.70 install or a required 0.70, to reword or delete; a line that only explains 0.70 or its legacy files (which files are 0.70's and need no upkeep) is kept and not listed, and so is prose such as "a FlowGuard release alone".

## The vitest execution side (minimal)

For a vitest project `init` also writes `flowguard.vitest.mjs` (it finds Python the same way) and adds two lines marked `flowguard: vitest` to `vitest.config.*` or `vite.config.*`: an import and `flowguard()` as the first plugin, or a new `vitest.config.mjs` when there is none. Delete the two lines (or the generated config) to undo. A CommonJS config is left alone and the two lines to add are printed; a jest project gets `check --static` only.

When vitest loads its config, the generated file asks FlowGuard's Python module `flowguard.intent.vitest` to prepare; it runs one `git diff`: with no TS/JS change against the task baseline nothing is wrapped, unless same-name sensors disagreed in the last run: then every sensor is planned and compared again, until they agree or lose their anchors. Otherwise it plans, as pytest does, the module-level functions (`function f` and `const f = (...) =>`) marked `// flowguard: sensor NAME` and the functions this change edited, and caches the plan by the baseline commit (and whether it is a recorded task start or HEAD standing in) and the changed files. The plugin adds `f = wrap(f)` after each one; each distinct call is replayed on representative values from cells: the constants the function compares with (literals, constant names, `Obj.KEY` members, imported ones), the keys of the module tables it looks up (`LABELS[type]`), the actual value and its neighbours; same-name copies also run the fixed representatives. The baseline source is loaded beside the file as `<file>?flowguard-baseline`, so its relative imports resolve as before. After the tests Python reads the records and prints, as pytest does, the changed case classes (`变：`), same-name sensors that disagree and rules from `tests/intent/` that an observed call or replayed class violates (`红：`), and what stayed unverified. The case classes come from the compared constants and are not a proof of a complete partition. A disagreement names the replayed input closest to one a test actually used (`year=2025` beside the test's 2026, not a representative such as `year=0`) and what every copy answered there (`3 份：2 份得 52（…），1 份得 1（…）`), one red per name; its next step chooses no copy: decide which one is right and make the others agree, or give copies that should differ different names (TS has no `distinct`). Only the points of the package whose vitest runs are listed as not reached, one item per place. The plugin also adds FlowGuard's own vitest project (vitest 3.2 or later), run after the project's tests: its one test case, `FlowGuard execution side`, judges the records and fails on red, so the red is in vitest's results (JSON, junit) and not only in the exit status; a run whose path filters leave it out is judged after the tests as before.

A replay refuses file writes, processes, network (`net`, `http`, `https`, `fetch`) and threads before they happen; a refusal voids that replay and the real call still runs. A connection opened before the replay cannot be refused, so a function whose code or callees name a database client, or whose arguments hold one, is never replayed and stays grey with that reason. jest, CommonJS, class methods, default exports and promise results are not observed.

`check --all` and `check --static --all` end with the open structure problems by severity: values outside a declared set (one problem per set, named without line numbers; `values:NAME` is the set 4.1 gave that name, the one problem of each field in 4.1, by kind: a Prisma enum (of a schema in use before a guessed schema's), else the CHECK, else the TS type, the first by where it is declared within one kind; each further set of that name adds where it is declared: its schema (a schema folder by its name, `prisma/schema/`), a CHECK's description (the migrations folder, `values:Account.status:prisma/migrations/`, so a later migration that declares it again keeps the name, or the .sql file), the first TS file that declares the member with it (`values:Props.variant:src/Button.tsx`, also when its alias comes from another file) or the first file of a guessed set; so a 4.1 decision keeps closing the set it closed. The names are chosen on each run from the sets there are: a set added later that comes first takes `values:NAME`, and with it the decision recorded under that name, while the set that had it adds its place and its problem is open again under that name, as when an enum is added to a field that had only a CHECK or a TS type of the model's name, a schema in use or a CHECK description earlier by path is added, or a file earlier by path declares a type of that name with another set (`src/Alert.tsx` with its own `interface Props` beside `src/Button.tsx`); record the decision again under its new name), pair violations, columns between descriptions (each SQL description and Prisma schema once, a schema folder as one schema named by its folder, against the schema it describes: one the generator uses when one shares its tables; a SQLite rebuild `ALTER TABLE "new_t" RENAME TO "t"` is followed; a CREATE TABLE built at run time leaves the description lacking no table; a client schema in another package whose tables and columns all exist in the schema it reads is a projection; files under a `docs` folder are archives and describe nothing, and `[tool.flowguard] archives = ["path/**", ...]` replaces that default), deletes that leave children, delete rules that differ between two Prisma schemas of one database (a provider template that cascades or nulls where the schema in use refuses the delete, or either schema without a foreign key the other has: the table, its key columns and the parent table there, but no `@relation` from that table to that parent over them, while a table, column or parent table it lacks is left to the column check; relations are matched by their table, key columns and parent table as mapped, so a model or relation renamed under the same `@@map`/`@map` is still compared; a schema folder is one schema, named by its folder (`ondelete:prisma/schema.sqlite.prisma~prisma/schema/`); a second client schema with the same provider and datasource url as the one it pairs with reads that database, so its leaving a relation out is no missing key (a datasource without a url, as Prisma 7 writes it, takes the `datasource: { url }` of the `prisma.config.*` whose folder names the schema, in the config or the package.json, or, with a config that names no schema, holds it at `prisma/schema.prisma`; a url the config does not spell as `env('NAME')`, `process.env.NAME` or a string names none); a copy with the same provider and url that is no second client, such as the provider template a sync script copies onto `schema.prisma`, also reads so, and a foreign key it lacks is not reported, only the column check sees what it lacks; and a key whose columns differ between the two is compared by its tables and a shared column; a relation without `onDelete` has Prisma's default, SetNull only when every key field is optional, else Restrict; NoAction and Restrict count as one; every relation is listed, a change that adds some gets just those as a lead (a `@map` or `@@map` added to both schemas, or a model renamed under its `@@map`, adds none), and one that edits either schema touches the problem; ## Relation templates

`from flowguard.intent import precedes, guarded_by, transitions, checks` writes one relation per line; each is an ordinary Flow checked by the existing flow checks. `precedes("SAVED", "PUBLISHED")`: in a test, publishing comes after a save. `guarded_by("PERMISSION_OK", "UPDATE_RECORD")`: every update has its own permission check before it. `transitions("Job.status", new={"saved"}, saved={"published"})`: the allowed changes of a field whose values the existing `# flowguard: states` comment declares. `checks("FEE", "FEE_CASE", days="arg.days")`: rule FEE checked on a scenario test's own arguments. Observed disallowed paths are red; unobserved declared edges and transitions stay unverified. Copies use `owner`, `sensor` and `distinct`, and a single writer uses `owner ... writers=`, so there is no `same` or `single_writer` template. `model draft NAME` also prints template lines from observed paths, grouped by the flow each test starts.

## Generated source queries

The base installation maps Python. The seven foreign readers are frozen optional additions: install the `languages` extra to map JS/JSX, TS/TSX, C, C++ and C#. Grammars load only when their source language is present; unavailable grammars are reported explicitly. Python has the full executable behavior anchors; TS/JS has the minimal vitest execution side described above. Foreign syntax supports navigation and explicit source checks; it does not execute the application or replace a compiler. Dynamic calls, macros, overloads and external/build-dependent bindings remain unknown with reasons.

For example, if an agreed `architecture.md` says `Literal assignments to retry_limit use only 0, 1 or 2.` and the file is listed in `[tool.flowguard].authority_docs`, a small Python-only source constraint can live with the component that owns this field:

```python
from flowguard.intent import structure_rule

@structure_rule("RETRY_LITERALS", source='doc architecture.md "Literal assignments to retry_limit use only 0, 1 or 2."')
def RETRY_LITERALS(graph):
    return [write for write in graph.assignments(language="python")
            if write["field"] == "retry_limit" and write["value"] not in (0, 1, 2)]
```

This checks the declared literal assignments, not computed keys or every runtime write. A source predicate returns violating rows/nodes, rather than a boolean or a copied implementation. A newly written policy remains green*, not independent authority. Use the source scope the actual requirement specifies; removing languages or files to obtain green changes the claim.

`graph.capabilities()` exposes actual languages/files, parser errors, available grammars and supported queries. `graph.query_coverage()` reports the queries this handle actually served and any unavailable or failed source scope. `functions()` tracks nodes, assignments and keys are tracked, and `calls(include_reads=True)` also requests symbol-read coverage. `nodes(file=...)` and `language="python"` make an intentional source boundary explicit. Foreign handlers, literal sets, test discovery and full symbol reads are not yet implemented. A structure rule using unavailable coverage, failed parsing, or no source query is grey. Each structure check has its own scope; direct library users can call `reset_query_coverage()` before a separate predicate.

The shared cache is invalidated by source changes, reader/grammar versions and project parser configuration or compilation-option content. Unsupported configuration, dependencies outside mapped roots and unresolved bindings stay unknown; cached syntax is not evidence of successful compilation or execution.

Fingerprints help find changed code and possible moves. They do not establish cross-language equivalence or prove behavior merely because names or shapes match.

## Use hierarchy only when it removes repetition

An upper behavior rule can declare `uses=[LOWER]`. A scenario relation connects actual lower and upper readings; the engine derives the logical-input binding and supplies verified joint witnesses. Lower sources and anchors must pass too; explicit deep checks additionally require mutation liveness. Joint checks combine all verified lower inputs, through nested uses, instead of changing one lower input at a time. Closed boolean/enum domains can have complete finite coverage. Open domains use supported partition representatives and report that boundary; they are not enumerated value by value.

Keep behavior decomposition in those actual uses relations and source constraints in `structure_rule` at their owner. Neither requires a whole-application model, a separate hierarchy format, or modeling the current development task.

Source anchors replace the old `.home` decorator. The [3.0 guide](upgrade-3.0.md) describes that older input migration; [4.0](upgrade-4.0.md) changes the execution boundary. A complex flow has only nodes, edges, existing state transitions and existing-rule reading relations. `model draft NAME` starts from real observed paths rather than repeating the implementation.

A `Node(..., model="CHILD_FLOW", phase="return")` can consume a registered child Flow's output. The child exports one existing Rule through an explicit `Relation(..., actual=Read("end"), on="end")` at a terminal return/raise node; the parent names that same source anchor and phase. Its Rule contract and joint witnesses still apply, and the child graph's finite and runtime checks must also pass on the same observed invocation batch. Deleting an internal save cannot leave that parent green merely because the exported boolean stayed unchanged. A test-entry Flow can supply the existing ordinary-test scenario binding separately from the production graph.

Each exported event needs one declared production start call in the child graph. Its matching return can be the export; nested check/save calls remain steps inside that start. Different invocations retain separate event scopes and share only coverage accounting. Missing or multiple exports, unregistered Flow objects, cycles, unavailable source identities and unobserved model edges remain grey. There is no fixed ten-layer depth cap; keep each layer near ten meaningful nodes so it is understandable. Finite state spaces are fully explored without a default fixed state cap. A same-named Rule or saved green metadata does not verify a child graph.

Default Flow verdicts cover observed anchor paths and the declared finite model. Unexecuted source routes remain unverified; an observed green does not prove that the source has no other route. Static path analysis is frozen and is not run by the engine; its direct SDK helpers remain available for their narrower explicit source scope.
