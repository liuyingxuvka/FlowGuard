# FlowGuard: preserve verification evidence across a static follow-up

Reviewed on 2026-11-24 against [main `4d72073c`](https://github.com/liuyingxuvka/FlowGuard/commit/4d72073ce149d1a28a8d6d4c0dad2bdf39ba3658). Review only; no implementation, no local test run, and no new release requirement. This is a handoff for the next maintenance round, not an instruction to interrupt the current PEMEL Studio pass.

## What already works; do not redo it

The current version already separates Vitest package runs, records when a Vitest run starts but does not report, shows pytest's own verdict separately from the FlowGuard red count, and preserves individual failed tests not selected by subsequent pytest runs. See [the current changelog](https://github.com/liuyingxuvka/FlowGuard/blob/4d72073ce149d1a28a8d6d4c0dad2bdf39ba3658/CHANGELOG.md). `not compared` deliberately means no evidence, not a failed behavior. The existing by-path regression test explicitly requires an ordinary pytest success to stay successful even when FlowGuard reports unverified comparisons ([fixture](https://github.com/liuyingxuvka/FlowGuard/blob/4d72073ce149d1a28a8d6d4c0dad2bdf39ba3658/tests/intent_engine/test_session_finish.py)). Keep this contract; do not require every task to model all of its behavior or make every unverified item red.

## One candidate worth reproducing: a static look-up should not displace the runtime record

**Verified by reading current source, not by executing the two commands.** A normal pytest session writes its FlowGuard result, including pytest's own outcome, through [the plugin](https://github.com/liuyingxuvka/FlowGuard/blob/4d72073ce149d1a28a8d6d4c0dad2bdf39ba3658/flowguard/intent/plugin.py#L2083-L2089). A standalone `check --static` also [writes its result to `scope=REPO`](https://github.com/liuyingxuvka/FlowGuard/blob/4d72073ce149d1a28a8d6d4c0dad2bdf39ba3658/flowguard/intent/cli.py#L1953-L1963). [The cache](https://github.com/liuyingxuvka/FlowGuard/blob/4d72073ce149d1a28a8d6d4c0dad2bdf39ba3658/flowguard/intent/cache.py#L494-L526) keeps one full result per scope, so the second write replaces the first: `show --last` has the newest static report, not the previous pytest session report or its comparisons. The static report is correctly labeled; this is **lost evidence, not an incorrect exit code**. Individual failed-test history and retained intent results have their own paths and may still appear. Do not claim that all failed tests disappear.

Why it matters: a handoff through `show --last` should not force the next agent to reconstruct a dynamic run from terminal history solely because someone ran a quick static check afterwards. In particular, a zero-red static result cannot answer whether pytest finished or which runtime comparisons were actually made. This is the same class of evidence-separation problem that current code already solves for separate Vitest packages, not a request for a new dashboard or a comprehensive percentage.

### Minimal next step, acceptance, and stop rule

- After the current downstream round, reproduce on then-current main in one clean, isolated Python fixture. First produce a pytest report with a distinguishable outcome (e.g., a collection error) and capture `show --last`. Separately use a successful pytest fixture with one explicit runtime comparison if needed to check retention of nonfailure evidence. Run a standalone `check --static` that succeeds, then read `show --last` (and existing retained-test output) again. No need to alter downstream application code. Keep the actual status and baseline attached to each record.
- **Only if that loss reproduces and the downstream handoff needs the record:** keep the latest runtime result queryable alongside the latest standalone static result, or expose the existing independent equivalent if one is found. Reuse existing per-scope storage/rendering where possible. Keep bounded latest records, not a general run-history store. A subsequent real runtime run should supersede the previous runtime record; the newest static report should remain identifiable as static. Neither should imply the other passed. Preserve existing ordinary pytest verdicts, rule semantics, separate Vitest package records, and read compatibility with pre-existing cache records. Don't change the one-line daily pytest output just for this.
- If latest main already provides both pieces of evidence, or the loss has no demonstrated handoff cost, close this recommendation without changing code. Don't introduce a universal “critical rule” gate, global verified count, or new workflow state for this problem.

## What not to turn into work yet

- **Performance:** [the v5.0.1 PEMEL field notes](https://github.com/liuyingxuvka/FlowGuard/blob/a649c414df8afa6f73fef693865895da01c9699c/docs/field-notes/2026-11-23-pemel-studio.md#L795-L818) report roughly 38–239 s of FlowGuard time while suite sizes and the shared working tree changed. Real reason to measure, not a sound before/after benchmark or proof a specific cache needs redesign. If PEMEL still reports a cost after this round, compare repeat runs at a fixed commit, baseline and selected suite in an isolated worktree; keep results and coverage equal and identify the costly phase before proposing a change.
- **Onboarding:** the same notes report plugin-only use before `init` and independent rules. They also show successful later adoption; current `init` already checks/refreshes its setup. Do not add a wizard or new mandatory step without a reproducible remaining adoption failure.
- **Map search:** PEMEL already recorded the [lexical alias / exact match bug and a small repro](https://github.com/liuyingxuvka/FlowGuard/blob/a649c414df8afa6f73fef693865895da01c9699c/docs/field-notes/2026-11-23-pemel-studio.md#L287-L345); [current source still promotes shared-word hits](https://github.com/liuyingxuvka/FlowGuard/blob/4d72073ce149d1a28a8d6d4c0dad2bdf39ba3658/flowguard/intent/cli.py#L1433-L1445). Worth using that existing evidence if the team chooses to fix it, not worth opening a second task for it here.

The guiding test is the owner's [control-panel analogy (R25)](https://github.com/liuyingxuvka/FlowGuard/blob/4d72073ce149d1a28a8d6d4c0dad2bdf39ba3658/.flowguard/requests/R25.md): a sensor that wasn't read isn't a green light, and a static read should not erase the last real sensor reading. Keep ordinary product behavior unchanged ([R85](https://github.com/liuyingxuvka/FlowGuard/blob/4d72073ce149d1a28a8d6d4c0dad2bdf39ba3658/.flowguard/requests/R85.md)); honor the existing decision to collect downstream feedback before another broad round ([R107](https://github.com/liuyingxuvka/FlowGuard/blob/4d72073ce149d1a28a8d6d4c0dad2bdf39ba3658/.flowguard/requests/R107.md)).
