# FlowGuard v5.0.1 实际使用反馈

2026-11-17。来自一次 TypeScript 全栈应用的分组维护。每组先写测试，前后端分别跑完整 Vitest 和 FlowGuard，再提交。期间通过发布标签升级到 v5.0.1，保持了该组的比较基线。这里记录使用证据和下一步建议，方便后续独立复现。对照 [维护要求](../.flowguard/requests/R20261117_WORKFLOW_FEEDBACK.md)。

## 优先让连续测试更快，也更容易看懂进度

同一权限改动组的完整通过结果中，后端 293 个文件、3877 项测试。Vitest 报告 35.18 秒，FlowGuard 报告 72.1 秒。前端 233 个文件、2255 项测试。Vitest 报告 127.52 秒，FlowGuard 报告 66.4 秒。前一轮后端的 FlowGuard 为 99.6 秒。这些是各工具各自报告的时间，不能直接相加推算墙钟时间。另有一次观察到 Vitest 在打印 RUN 之前，Python prepare 已持续 91 秒。上述样本只能说明这次迭代的开销和等待感受，还需要独立测量判断耗时落在哪一段。

建议先在现有输出中提供一行可选计时，分开显示准备、静态检查和比较。再做一个无业务数据的双包样例，测量首次运行、相同文件再次运行、改动一个函数、改动共同依赖四种情况。若重复解析同一基线是热点，可用提交、解析器版本、配置、共享依赖和实际文件输入作为失效依据，复用已经验证的基线或准备结果。前后端共用项目时，保持各自实际执行记录的归属。

验收应同时观察速度及结果。热运行命中时减少准备时间。只改共同依赖也必须能复现已有红项。工作区有未提交改动、换基线或换工具版本时，测到正确失效。提速前后用一组本来会报红的用例核对结果。

## 让两个包的验证可以独立运行

此前同时运行前后端检查，遇到一次缓存锁竞争，未取得测试结果。当前做法是串行。这避免了此次冲突，多个包每组必须等两套检查累加。另有多个代理共享同一工作区，所有检查也集中交给一个代理，以避免混用最后一次运行结果。

建议先用同一临时仓库的两个 Vitest 项目并行复现，弄清冲突发生在写缓存、发布运行记录或其它阶段。考虑可共享的只读素材与每次运行独立的记录，依照实际冲突选择短临界区或隔离。锁忙时输出等待的是哪类操作和已等待多久，异常退出后的下一次运行要可自行恢复。验收包括两包并行时各自留下完整结论、一包被中断时另一包不受污染，以及下次运行仍能识别工作区和基线。不要用跳过检查的方式处理锁等待。

## 区分比较范围与通过证据

限定 Vitest 文件或名称的先行测试会输出 0 red 以及 `map checks did not report to this vitest run`。这对调试有价值，但并不等于完整检查通过。两端分别复验以后，`show --last` 只指最近一端。需要回到日志才能判断哪包实际跑了哪些检查、使用哪个基线。开启下一组任务时，提示还建议再比较上组一次，即使两端刚刚通过。CLI 首行显示系列版 5.0，核对安装的正式补丁版本则需查看包元数据。

建议在现有摘要或可选详细输出中把包名、基线、工具完整版本、静态检查是否运行、行为比较数和运行范围放在一起。把已有最后一次检查视图扩成可指定包的复验视图，优先复用当前记录。若上一组的结果可与提交前实际验证的文件内容对应，可显示这份证据；不能对应时再提示复验。测试名称过滤、跳过用例、未运行静态检查和过期结果各给出明确状态。验收样例应证明截断的先行测试不会被误读成完整通过，另一个包的失败也不会被最近一次通过覆盖。

## 把同一业务规则绑定到合适的证据

权限改动中曾把 `same` 放在调用前，或把返回布尔值的判断和返回记录的投影标成同一比较组。本组真实静态结果为红。这是有用的拒绝。这里本来要证明两个入口使用同一个范围所有者，和比较两份相同输入输出的纯函数有别。改为在实际调用路径上的同签名函数或规则上登记以后，检查通过。同组后端还有 120 个未比较项，包含对象方法未包装、导入绑定和新增函数缺基线等原因。单元测试仍在真实路由和服务入口验证授权与零写入。

建议在现有诊断中给出各标注的函数名、签名、输出类型及差异。若目标是保证路由和列表使用同一所有者，指出已有的调用或依赖检查能否表达，有哪些限制。先把最常见的三类未比较原因按受影响路径归类，例如新函数无基线、对象方法没有探针、依赖无法安全执行。优先用少量真实反例验证表达方式：删掉路由对所有者的调用必须能被发现，保持对不同形状的数据投影的支持，不执行有副作用的应用函数来补齐比较数。

## 保留目前最有价值的行为

项目硬删除时，需求转到另一个项目，却保留了旧项目的 PSP 元素引用。FlowGuard 的既有同写约定报红，暴露了单看界面容易漏掉的问题。补上事务级反例以后，重挂需求与清空旧引用改成一次写入。当天的 before、known 和影响提示还能把已有问题与本次改动分开。这类有明确代码位置和反例的报告值得保留。

建议研发顺序为先量出重复准备的成本，再解决并行运行与证据范围，随后改进规则绑定反馈。短周期维护的目标是让助手更早发现真实回归、把精力用在用户实际流程和约定上。发布版当前已修复此前遇到的基线目录读取问题，该历史问题不需要重复立项。
