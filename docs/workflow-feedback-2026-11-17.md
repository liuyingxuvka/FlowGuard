# FlowGuard v5.0.1 实际使用反馈

2026-11-17。来自一次 TypeScript 全栈应用的分组维护。每组先写测试，前后端分别跑完整 Vitest 和 FlowGuard，再提交。期间通过发布标签升级到 v5.0.1，保持了该组的比较基线。这里记录使用证据和下一步建议，方便后续独立复现。对照 [维护要求](../.flowguard/requests/R20261117_WORKFLOW_FEEDBACK.md)。

## 优先让连续测试更快，也更容易看懂进度

同一权限改动组的完整通过结果中，后端 293 个文件、3877 项测试。Vitest 报告 35.18 秒，FlowGuard 报告 72.1 秒。前端 233 个文件、2255 项测试。Vitest 报告 127.52 秒，FlowGuard 报告 66.4 秒。前一轮后端的 FlowGuard 为 99.6 秒。这些是各工具各自报告的时间，不能直接相加推算墙钟时间。另有一次观察到 Vitest 在打印 RUN 之前，Python prepare 已持续 91 秒。上述样本只能说明这次迭代的开销和等待感受，还需要独立测量判断耗时落在哪一段。

建议先在现有输出中提供一行可选计时，分开显示准备、静态检查和比较。再做一个无业务数据的双包样例，测量首次运行、相同文件再次运行、改动一个函数、改动共同依赖四种情况。若重复解析同一基线是热点，可用提交、解析器版本、配置、共享依赖和实际文件输入作为失效依据，复用已经验证的基线或准备结果。前后端共用项目时，保持各自实际执行记录的归属。

验收应同时观察速度及结果。热运行命中时减少准备时间。只改共同依赖也必须能复现已有红项。工作区有未提交改动、换基线或换工具版本时，测到正确失效。提速前后用一组本来会报红的用例核对结果。

### v5.1.0 静态检查在构建本地缓存时中止

使用已核对的官方 FlowGuard v5.1.0（修订 `bcc57bd00d38`），在应用提交 `d15a541826b3` 运行 `python -m flowguard check --static --base d15a541826b3748e6b6c65978fa1af62b6cfd01e`。`flowguard-v5.1.0-planning-static.log` 输出 `SQLite cache build failed: too many SQL variables; no partial build was accepted`，本次静态检查未完成。此前 G82 对应代码的后端完整运行在 v5.0.1 下通过 6,388 例，FlowGuard 报 `0 red`。两份结果分别记录各自的运行范围。

`flowguard-v5.1.0-cache-trace.log` 定位到 `flowguard/structure/store.py:719` 的 `_build`，它把整个 `list(snapshot)` 绑定到一次 `SELECT src, dst, kind FROM edge WHERE dst IN (...)`。旧版源码也有这条查询。升级改变工具摘要，原缓存的文件都进入重新解析范围，因而触发了该查询。旧版缓存文件约 617 MiB，已单独保留。本次只读核对在随附的 Python 二进制中看到 `MAX_VARIABLE_NUMBER=32766`，没有打开 SQLite 会话测量实际连接上限。

旧缓存保留在工作目录外。同一应用提交与官方 v5.1.0 使用空缓存重新运行后，`flowguard-v5.1.0-fresh-cache-static.log` 记录退出 0、`0 red; 59.1 s`。随后在不变的 HEAD 执行 `new-task`，`flowguard-v5.1.0-restored-baseline.log` 确认基线仍为 `d15a541826b3`。

复现可固定同一应用提交，分别使用空缓存和已有 v5.0.1 缓存，保持 `backend/.env` 不存在并清除 `DATABASE_URL`、`CENTRAL_DATABASE_URL`。一种可验证的修复是按 SQLite 连接的实际绑定上限分批查询，合并结果并保留原有去重和事务语义。诊断可显示失败阶段和绑定参数数量，继续拒绝不完整缓存。回归应同时覆盖空缓存、超过上限的旧缓存重建，以及未超过上限的增量刷新，并核对完成后的检查结果一致。

### v5.1.0 升级提示应先给出只读差异

应用基线 `ddcaaba02b19` 的 `v3-84-person-merge-command-new-task.log` 报告 `AGENTS.md holds a FlowGuard rules block that differs from the one FlowGuard 5.1 writes: python -m flowguard init rewrites it`。读取应用中标记的生成块，与发布修订 `bcc57bd00d38` 的 `PROJECT_RULES` 做逐行比较，只有第 7 条不同。新版补充了用 `req add --offer FILE --picked TEXT` 记录选择的办法。`init` 的实际代码还会写项目的 pytest 配置、哨兵、`.flowguard/ci.yml` 及适用的 npm 测试接线。应用保留原有接线，正式 v5.1.0 已通过第 83 组完整的后端 6,411 例和前端 3,641 例，两端 FlowGuard 均为 `0 red`。

建议从 `new-task` 的提示直接提供只读预览，显示生成块的具体差异和执行 `init` 会触及的文件。用同一个仅第 7 条不同的 npm 项目验收，预览应明确新增的选择记录说明和接线影响，凭运行前后的文件散列和比较基线核对只读性。托管会话提供的同名技能仍指向 `read`、`change`、`map` 和 `release`。该发布标签随附的技能指向 `new-task`、项目测试及 `show`。升级提示可同时指向同一标签的随附技能，便于核对当前引擎对应的指引。

### v5.1.0 精确模型查询先显示了同名测试 getter

应用组 G86 在基线 `a590483510d9` 用 `python -m flowguard show EmployeeCentralLink` 核对人员关联。`v3-86-preflight-EmployeeCentralLink.log` 的首项是测试替身里的 `get employeeCentralLink()`，接下来才是两份 Prisma 声明、SQL 表和读写计数。尾行提示 `--full` 会增加 5,194 行，其中 5,193 行只是词匹配。模型证据都存在，但开头和下一步提示会把维护者引向测试替身和大量宽泛匹配。

`g86-flowguard-show-repro.log` 在独立 Git 目录用正式 v5.1.0 复现。Prisma 定义 `model SampleLink { id String @id }` 并映射表名 `sample_links`。`tests/links.test.ts` 的 `fixtures` 对象有 `get sampleLink() { return { id: 'fixture' }; }`。查询 `SampleLink` 先显示 getter，查询 `sample_links` 先显示模型。`show tests/links.test.ts:fixtures.sampleLink` 准确定位 getter。即使显式查询 `show prisma/schema.prisma:SampleLink`，当前输出仍在模型前显示测试 getter。发布源码 `flowguard/intent/cli.py:1362` 给模型事实较高排序值，但 `:1442` 先输出单列的少量同名函数视图，绕过该排序。整个对照只读取源码和工具本地缓存。

建议让精确 Prisma 模型或 SQL 表匹配优先显示声明、映射和读写计数，再分组列出同名源码符号。显式限定 schema 路径时，首屏只显示该 schema 中的精确声明及相关结构事实。上述夹具可同时核对裸模型名、映射表名、限定 schema、限定 getter 四种查询。普通词匹配继续可在 `--full` 中展开，并与精确匹配分开计数。

G99 在应用基线 `b66efe8` 用正式 v5.1.0 查询限定字段。`v3-99-afterjson-show.log` 中，`show CentralChangeEvent.afterJson` 先列出声明和写入，余下 1,165 行，其中 1,065 行只是词匹配。`v3-99-deletedat-show.log` 中，`show CentralEmployee.deletedAt` 余下 5,585 行，其中 5,469 行只是词匹配。两次默认输出都截断了部分结构详情。实际可用 `show --last` 快速核对本次影响。`v3-99-backend-show.log` 直接列出了新增的 `afterJson` 写入位置、三个其他写入方和三个模型读取方。模型读取记录只能证明查询了该模型，字段是否被读取仍需源码证据。

建议为已识别的 `模型.字段` 提供只展开相关结构事实的选项，分别标明已确认的字段写入、字段未解析的模型写入、确认的字段读取及模型级读取。默认摘要可分别提示剩余结构详情和词匹配的数量，保留 `--full` 供广泛探索。用一个含同词无关符号、确切字段写入、未解析 Prisma 写入和模型级读取的夹具，核对结构查询能展开这些已知范围，并清楚标明证据的粒度。

## 让两个包的验证可以独立运行

此前同时运行前后端检查，遇到一次缓存锁竞争，未取得测试结果。当前做法是串行。这避免了此次冲突，多个包每组必须等两套检查累加。另有多个代理共享同一工作区，所有检查也集中交给一个代理，以避免混用最后一次运行结果。

建议先用同一临时仓库的两个 Vitest 项目并行复现，弄清冲突发生在写缓存、发布运行记录或其它阶段。考虑可共享的只读素材与每次运行独立的记录，依照实际冲突选择短临界区或隔离。锁忙时输出等待的是哪类操作和已等待多久，异常退出后的下一次运行要可自行恢复。验收包括两包并行时各自留下完整结论、一包被中断时另一包不受污染，以及下次运行仍能识别工作区和基线。不要用跳过检查的方式处理锁等待。

## 区分比较范围与通过证据

限定 Vitest 文件或名称的先行测试会输出 0 red 以及 `map checks did not report to this vitest run`。这对调试有价值，但并不等于完整检查通过。两端分别复验以后，`show --last` 只指最近一端。需要回到日志才能判断哪包实际跑了哪些检查、使用哪个基线。开启下一组任务时，提示还建议再比较上组一次，即使两端刚刚通过。CLI 首行显示系列版 5.0，核对安装的正式补丁版本则需查看包元数据。

建议在现有摘要或可选详细输出中把包名、基线、工具完整版本、静态检查是否运行、行为比较数和运行范围放在一起。把已有最后一次检查视图扩成可指定包的复验视图，优先复用当前记录。若上一组的结果可与提交前实际验证的文件内容对应，可显示这份证据；不能对应时再提示复验。测试名称过滤、跳过用例、未运行静态检查和过期结果各给出明确状态。验收样例应证明截断的先行测试不会被误读成完整通过，另一个包的失败也不会被最近一次通过覆盖。

V1-27 在同一基线 `007d67d` 观察到一处具体的摘要压缩问题。后端 `v1-27-backend-red.log` 用测试名称筛选，生成的静态用例未被选中，唯一 `not compared` 明确显示 `map checks did not report to this vitest run`。前端 `v1-27-frontend-red.log` 只选七个应用测试文件，同样没有运行静态用例，摘要却只显示 `4 items (only JSON data arguments and results are recorded, uses imported or mutable binding axios, or 1 other reason)`。两个运行都实际退出 1，均报告 `0 red`，原因来自各自的应用用例失败。前端另一轮 `v1-27-demand-frontend-focused.log` 实际退出 0、19 例通过，也只显示 9 项未比较的聚合原因。三轮都只能证明各自选中的测试范围。

源码在 `flowguard/intent/vitest.py` 把已接线但未汇报的静态入口放进普通 `not compared`，再由 `flowguard/intent/signals.py` 按频次和宽度压缩。建议在紧凑摘要中给静态检查保留独立状态，至少可见有无收到结果，有多项未比较时也能看到。最小验证用同一个已接线包跑两次，一次只有静态用例未运行，一次同时有四项其他未比较，确认两份摘要都能直接读到静态范围。补一次实际运行静态用例的对照，并保留原有红项与退出状态。

## 把同一业务规则绑定到合适的证据

权限改动中曾把 `same` 放在调用前，或把返回布尔值的判断和返回记录的投影标成同一比较组。本组真实静态结果为红。这是有用的拒绝。这里本来要证明两个入口使用同一个范围所有者，和比较两份相同输入输出的纯函数有别。改为在实际调用路径上的同签名函数或规则上登记以后，检查通过。同组后端还有 120 个未比较项，包含对象方法未包装、导入绑定和新增函数缺基线等原因。单元测试仍在真实路由和服务入口验证授权与零写入。

建议在现有诊断中给出各标注的函数名、签名、输出类型及差异。若目标是保证路由和列表使用同一所有者，指出已有的调用或依赖检查能否表达，有哪些限制。先把最常见的三类未比较原因按受影响路径归类，例如新函数无基线、对象方法没有探针、依赖无法安全执行。优先用少量真实反例验证表达方式：删掉路由对所有者的调用必须能被发现，保持对不同形状的数据投影的支持，不执行有副作用的应用函数来补齐比较数。

G80 提供了基线回放的参数错位对照。`v3-80-frontend-full.log` 的 3,641 例通过，FlowGuard 为 `0 red`。`v3-80-flowguard-frontend-show.log` 对 `businessPersonLabel` 的 7 个输入和 `createBusinessDraft` 的 4 个输入都报 `changed`。两者的首个参数由记录改为业务种类，原来的记录移到第二位，草稿函数的记录仍可选。回放把新调用的首个字符串交给旧函数，由此得到 `undefined [directory unavailable]` 和空白草稿。正常调用的接收对象标签和草稿由实际入口用例核对。建议在比较前验证同一输入能否绑定到两份签名。无法建立对应时标记 `not compared`，并列签名和冲突参数的位置。参数对应可证时继续报告真实输出差异。最小夹具可并列首位插入必填参数、尾部追加不影响原绑定的可选参数，以及签名相同但输出变化三种情况。

## 保留目前最有价值的行为

项目硬删除时，需求转到另一个项目，却保留了旧项目的 PSP 元素引用。FlowGuard 的既有同写约定报红，暴露了单看界面容易漏掉的问题。补上事务级反例以后，重挂需求与清空旧引用改成一次写入。当天的 before、known 和影响提示还能把已有问题与本次改动分开。这类有明确代码位置和反例的报告值得保留。

建议研发顺序为先量出重复准备的成本，再解决并行运行与证据范围，随后改进规则绑定反馈。短周期维护的目标是让助手更早发现真实回归、把精力用在用户实际流程和约定上。发布版当前已修复此前遇到的基线目录读取问题，该历史问题不需要重复立项。

### 把行为发现归给实际测试

真实组件的 Vitest 断言暴露了嵌套弹窗顺序、焦点圈定、输入控件先消费 Escape、忙碌弹窗阻止关闭和滚动锁恢复等缺口。后续运行还发现兄弟弹窗关闭后没有回到原触发按钮。截图用例也报了失败，其中两类来自测试对旧关闭按钮名称和同步回焦的预期。调整后的测试使用公共组件的名称，并等待同一个触发按钮重新获得焦点。同次 FlowGuard 的 0 red 只适用于其实际比较的内容。

建议允许维护者在约定下关联完整交互的 Vitest 用例。测试从触发按钮打开弹窗，检查焦点进入、叠上子层、编辑控件先处理 Escape、关闭最上层、返回原按钮。忙碌场景还需断言操作只执行一次，按键只作用在当前层。报告可分别列出用户行为测试结果和注释、所有者与代码的匹配结果。

### 标注迁移应解释为责任转移

`v1-28-ledger-check-1.log` 实际报告 3 red、50 unverified。三项红灯对应一次错误处理迁移。`EmployeeUtilizationView` 的记录数为 6，代码只剩 5。`AbsenceForm` 原记录 1 处，调用方现在把故障继续抛出。公共 `ConfirmDialog.confirm` 新增 1 处处理，接住两个调用方的失败并显示安全提示，保留重试和取消。

核对实际调用和用户失败路径后，把第一项计数改为 5，移除第二项迁出的记录，并为公共处理登记理由和成文规则。本次检查提供了三个核对位置。新提示、重试和取消的正确性仍需由对应行为用例复验。

工具可以在现有诊断中把旧位置的减少与共享处理的新增列为可能关联，展示计数和规则归属，交由维护者确认实际迁移和理由。本轮的收益是让错误处理的归属成为一项可核对的变更。
