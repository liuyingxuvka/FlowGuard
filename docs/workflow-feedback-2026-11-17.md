# FlowGuard v5.0.1 实际使用反馈

2026-11-17。来自一次 TypeScript 全栈应用的分组维护。每组先写测试，前后端分别跑完整 Vitest 和 FlowGuard，再提交。期间通过发布标签升级到 v5.0.1，保持了该组的比较基线。这里记录使用证据和下一步建议，方便后续独立复现。对照 [维护要求](../.flowguard/requests/R20261117_WORKFLOW_FEEDBACK.md)。

## 优先让连续测试更快，也更容易看懂进度

同一权限改动组的完整通过结果中，后端 293 个文件、3877 项测试。Vitest 报告 35.18 秒，FlowGuard 报告 72.1 秒。前端 233 个文件、2255 项测试。Vitest 报告 127.52 秒，FlowGuard 报告 66.4 秒。前一轮后端的 FlowGuard 为 99.6 秒。这些是各工具各自报告的时间，不能直接相加推算墙钟时间。另有一次观察到 Vitest 在打印 RUN 之前，Python prepare 已持续 91 秒。上述样本只能说明这次迭代的开销和等待感受，还需要独立测量判断耗时落在哪一段。

建议先在现有输出中提供一行可选计时，分开显示准备、静态检查和比较。再做一个无业务数据的双包样例，测量首次运行、相同文件再次运行、改动一个函数、改动共同依赖四种情况。若重复解析同一基线是热点，可用提交、解析器版本、配置、共享依赖和实际文件输入作为失效依据，复用已经验证的基线或准备结果。前后端共用项目时，保持各自实际执行记录的归属。

验收应同时观察速度及结果。热运行命中时减少准备时间。只改共同依赖也必须能复现已有红项。工作区有未提交改动、换基线或换工具版本时，测到正确失效。提速前后用一组本来会报红的用例核对结果。

## 让两个包的验证可以独立运行

此前同时运行前后端检查，遇到一次缓存锁竞争，未取得测试结果。当前做法是串行。这避免了此次冲突，多个包每组必须等两套检查累加。另有多个代理共享同一工作区，所有检查也集中交给一个代理，以避免混用最后一次运行结果。

建议先用同一临时仓库的两个 Vitest 项目并行复现，弄清冲突发生在写缓存、发布运行记录或其它阶段。考虑可共享的只读素材与每次运行独立的记录，依照实际冲突选择短临界区或隔离。锁忙时输出等待的是哪类操作和已等待多久，异常退出后的下一次运行要可自行恢复。验收包括两包并行时各自留下完整结论、一包被中断时另一包不受污染，以及下次运行仍能识别工作区和基线。不要用跳过检查的方式处理锁等待。

## 区分比较范围与通过证据

限定 Vitest 文件或名称的先行测试会输出 0 red 以及 `map checks did not report to this vitest run`。这对调试有价值，但并不等于完整检查通过。两端分别复验以后，`show --last` 只指最近一端。需要回到日志才能判断哪包实际跑了哪些检查、使用哪个基线。开启下一组任务时，提示还建议再比较上组一次，即使两端刚刚通过。CLI 首行显示系列版 5.0，核对安装的正式补丁版本则需查看包元数据。

建议在现有摘要或可选详细输出中把包名、基线、工具完整版本、静态检查是否运行、行为比较数和运行范围放在一起。把已有最后一次检查视图扩成可指定包的复验视图，优先复用当前记录。若上一组的结果可与提交前实际验证的文件内容对应，可显示这份证据；不能对应时再提示复验。测试名称过滤、跳过用例、未运行静态检查和过期结果各给出明确状态。验收样例应证明截断的先行测试不会被误读成完整通过，另一个包的失败也不会被最近一次通过覆盖。

## 把同一业务规则绑定到合适的证据

权限改动中曾把 `same` 放在调用前，或把返回布尔值的判断和返回记录的投影标成同一比较组。本组真实静态结果为红。这是有用的拒绝。这里本来要证明两个入口使用同一个范围所有者，和比较两份相同输入输出的纯函数有别。改为在实际调用路径上的同签名函数或规则上登记以后，检查通过。同组后端还有 120 个未比较项，包含对象方法未包装、导入绑定和新增函数缺基线等原因。单元测试仍在真实路由和服务入口验证授权与零写入。

建议在现有诊断中给出各标注的函数名、签名、输出类型及差异。若目标是保证路由和列表使用同一所有者，指出已有的调用或依赖检查能否表达，有哪些限制。先把最常见的三类未比较原因按受影响路径归类，例如新函数无基线、对象方法没有探针、依赖无法安全执行。优先用少量真实反例验证表达方式：删掉路由对所有者的调用必须能被发现，保持对不同形状的数据投影的支持，不执行有副作用的应用函数来补齐比较数。

## 保留目前最有价值的行为

项目硬删除时，需求转到另一个项目，却保留了旧项目的 PSP 元素引用。FlowGuard 的既有同写约定报红，暴露了单看界面容易漏掉的问题。补上事务级反例以后，重挂需求与清空旧引用改成一次写入。当天的 before、known 和影响提示还能把已有问题与本次改动分开。这类有明确代码位置和反例的报告值得保留。

建议研发顺序为先量出重复准备的成本，再解决并行运行与证据范围，随后改进规则绑定反馈。短周期维护的目标是让助手更早发现真实回归、把精力用在用户实际流程和约定上。发布版当前已修复此前遇到的基线目录读取问题，该历史问题不需要重复立项。

### 把行为发现归给实际测试

真实组件的 Vitest 断言暴露了嵌套弹窗顺序、焦点圈定、输入控件先消费 Escape、忙碌弹窗阻止关闭和滚动锁恢复等缺口。后续运行还发现兄弟弹窗关闭后没有回到原触发按钮。截图用例也报了失败，其中两类来自测试对旧关闭按钮名称和同步回焦的预期。调整后的测试使用公共组件的名称，并等待同一个触发按钮重新获得焦点。同次 FlowGuard 的 0 red 只适用于其实际比较的内容。

建议允许维护者在约定下关联完整交互的 Vitest 用例。测试从触发按钮打开弹窗，检查焦点进入、叠上子层、编辑控件先处理 Escape、关闭最上层、返回原按钮。忙碌场景还需断言操作只执行一次，按键只作用在当前层。报告可分别列出用户行为测试结果和注释、所有者与代码的匹配结果。

### 标注迁移应解释为责任转移

`v1-28-ledger-check-1.log` 实际报告 3 red、50 unverified。三项红灯对应一次错误处理迁移。`EmployeeUtilizationView` 的记录数为 6，代码只剩 5。`AbsenceForm` 原记录 1 处，调用方现在把故障继续抛出。公共 `ConfirmDialog.confirm` 新增 1 处处理，接住两个调用方的失败并显示安全提示，保留重试和取消。

核对实际调用和用户失败路径后，把第一项计数改为 5，移除第二项迁出的记录，并为公共处理登记理由和成文规则。本次检查提供了三个核对位置。新提示、重试和取消的正确性仍需由对应行为用例复验。

工具可以在现有诊断中把旧位置的减少与共享处理的新增列为可能关联，展示计数和规则归属，交由维护者确认实际迁移和理由。本轮的收益是让错误处理的归属成为一项可核对的变更。

这次 50 个语法未验证项还包含 `step1-overlay-consumers.test.tsx` 等文件，同批前端 TypeScript 检查实际 exit 0。建议输出最小错误区域、行列以及可识别的语法类别，供维护者定位解析范围。报告位置和类别即可，解析差异的具体原因仍待核实。

## V1-14 路由恢复需要同次交互结果

`v1-14-frontend-targeted-1.log` 的定向运行实际退出 1。Vitest 在 2.19 秒内跑了 9 例，8 例通过。从正常页面进入一个始终抛错的新页面时，路由边界记了两次错误，用例要求一次。FlowGuard 报 0 red、2 not compared，耗时 27.9 秒。未比较范围列出 `AppShell` 和未纳入此次运行的静态检查入口。故障由真实路由、组件生命周期和日志断言共同复现。修复后同一用例随 `v1-14-frontend-green-1.log` 的 2597 例全部通过，FlowGuard 报 0 red、5 not compared。

可以从现有 Vitest 集成读取与约定关联的测试结果。例如为“路由边界只在上一次已经崩溃时复位”登记稳定的场景标识、边界方法位置、测试文件和完整用例名称。用同次运行的源码指纹确认结果仍适用，并列出用例结论、FlowGuard 比较状态和 Vitest 失败位置。用例被过滤、跳过、无法定位或证据过期时，标明缺少当前交互结果。组件仍由 Vitest 渲染，FlowGuard 记录约定及证据归属。

验收可保留一个小型路由用例，分别跑故障、修复后、过滤该用例三种状态。故障时报告实际失败，修复后才显示通过，过滤后的输出看得出缺少证据。这个增量可以先复用现有运行元数据，验证效果后再决定是否需要扩充约定格式。

## V1-15 批量写入需要保留循环变量的来源

`v1-15-impact-hourFrequency.log` 中的 `show CapacityCalendarEntry.hourFrequency` 找到了 `createMany({ data: batch })`，但只列为 `CapacityCalendarEntry.?`，理由是 `batch is not declared in this file`。实际方法内存在 `for (const batch of migrationBatches(capacityResult.creates, ...))`；容量字段由校验阶段构造，经分批后写入，HOURS 写 DAY、PERCENT 写 NULL。这条批量路径因此没有进入该字段的写入清单。工具提供了可核对的入口，但当前清单不能视为完整覆盖，也不能据此断言批量写入的值错误。

建议先识别 `for...of` 的局部绑定及作用域，再保守跟踪直接分批函数返回或产出的元素来源，把可证明的字段构造位置关联到 `createMany`。不执行项目代码；遇到重赋值、未知变换或无法解析的来源时，保留未解析状态，并区分“变量未声明”和“已识别循环绑定、尚未解析批元素字段”。

可用一个小型静态夹具验收：同一字段的 DAY 和 NULL 对象经过本地分批循环写入，应能定位两种构造来源；另放未知变换和重新赋值的反例，要求明确报告未解析原因，不能猜成已验证。这个建议只补批量写入的来源定位，不承诺运行时值、数据库结果或全项目写入覆盖。

## V1-16 未找到创建入口不等于读路径有错

`v1-16-backend-full-1.log` 和 `v1-16-frontend-full-1.log` 都报 0 red，另把 `org-unit-reference-registry.ts:21` 的 `ProjectRequest.count` 列为 `uncreated ProjectRequest` 的 impact，理由是没有代码创建这些行。核对任务基线 `bcde6e1`：`org-unit.service.ts:376` 和 `:1196` 已有同样的计数查询；本次注册表是新的读位置，沿用了既有引用检查，不能仅凭位置变化认定需要补建创建功能。负责人已决定保留该表、暂不实现创建功能，计数仍需保护可能存在的遗留引用。没有查询数据库，也没有据此确认表内是否有数据。

建议将证据措辞收紧为“当前扫描范围内未找到创建入口”，并在可证明时展示旧读入口到新所有者的来源关系。若已有负责人决定说明保留遗留数据，可附该依据，供维护者判断；不自动认定所有无创建者的模型都是遗留数据，不自动豁免读路径，也不建议为了消除提示而补业务写入。无法确认迁移关系或创建来源时应保留明确的未知状态，继续区分 impact 与 red。

小型静态夹具可覆盖三种情况：既有只读计数移到注册表、后来新增真实创建入口、读取未声明模型。前两种分别报告继承来源和新发现的创建者，第三种仍按原有规则检查。这个增量只改善诊断的措辞与来源归属，不执行项目代码，也不推断数据库中的实际行数。

## V1-16 同写字段与条件值约束是两层证据

`v1-16-org-manager-anchor-red.log` 实跑 8 例，3 失败、5 通过，FlowGuard 为 0 red、20 not compared。已有 `together CentralOrgUnit.managerEmployeeId CentralOrgUnit.managerSapNumber` 要求同一次写入包含两列，原代码确实同时写了两个键。但中央经理有效、应用侧没有对应人员锚点时，新增和覆盖都写成 SAP 非空、人员 ID 为空；4.238 要求此时两列都清空，另一个失败用例检查预览警告。这是行为测试发现的条件值缺口，现有 `together` 语义仍然成立，不能称为该约定检查出错。

建议在这类报告中区分“同写字段已检查”和“条件值关系缺少当前证据／尚不能比较”。若登记后者，可关联 `step1-org-import-protection.test.ts` 中新增、覆盖缺锚点的具名场景；仅比较正常路径的固定字面输入，不能证明运行时缺锚点分支。小夹具可保留漏写一列、两列同空、两列都写但值关系不合法三例，分别核对现有结构约定和显式行为测试的结论。未执行的条件用例保持未验证，不把 0 red 扩大为值关系已验证，也不自动为所有成对字段推断同空或相等规则。

## V1-17 错误输出的信任规则应按消费者登记

`v1-17-frontend-full-1.log` 的整轮 Vitest 有 7 例失败，FlowGuard 报 0 red。其中 `ProjectImportWizard.psp-deletion.test.tsx` 的真实 Retry 用例发现，引用影响读取失败时，一个短的内部诊断占位文本经 `ReadFailureNotice` 和 `toUserMessage` 进入了 DOM。通用映射允许看起来安全的后端业务消息，而此消费者需要固定的“无法检查引用”提示。该用例先在禁止泄露的断言处失败，后续 Retry 恢复断言不能算作本次已通过；这也不是 FlowGuard 违反了已检查约定的证据。

可允许维护者为这个消费者登记机器可读的有限输出契约：允许哪些固定文案或错误码映射、由哪个所有者提供，任意响应 `message` 不能直接作为该处输出；再关联上述具名真实组件用例。缺少约定、来源不能解析或用例没有执行时，明确保留未验证状态，不从 0 red 推断文案已满足信任要求，也不靠执行应用代码补证据。

小夹具应同时保留三个边界：短而无技术关键词的后端文本在这个固定输出消费者处仍被拒绝；登记的错误码映射得到受控文案；普通表单继续允许其原有的安全业务说明。这样能检验消费者的信任范围，不必把全局错误映射改成更宽的关键词黑名单或一律丢弃业务消息。

证据来自本地单测、FlowGuard 日志和源代码核对。
