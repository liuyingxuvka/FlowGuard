## Context

The installed suite has clear satellite owners, but the main prompt and several large protocols can cause broad loading before task relevance is known. DevelopmentProcessFlow also embeds current suite-count/install details that belong to distribution ownership.

## Goals / Non-Goals

**Goals:**

- Preserve strict triggered obligations while reducing routine cognitive and execution overhead.
- Make route ownership visible and keep distribution evidence independent.
- Split guidance at semantic trigger boundaries.

**Non-Goals:**

- Removing specialist routes.
- Creating a public “understanding” satellite.
- Raising prompt budgets merely to accommodate larger files.

## Decisions

### One sequence, derived presentation tiers

The main route teaches a stable sequence and exposes the derived tier in the demand summary. Ordinary renders only triggered owners and concise dispositions; standard adds cross-owner details; deep expands related topology and adversarial evidence; release adds frozen identity, distribution, full-validation, and publication gates. All tiers share the same demand compiler.

### Trigger ModelMesh from topology, not count

ModelMesh runs when affected models are related, a parent/child boundary changes, child evidence is stale, partitioning is required, or a whole-flow claim is requested. A repository count is only a discovery hint.

### Split protocols by conditional concern

Keep short routing/kernel files and move partition/reattachment/closure/revision, transition/field/payload, reuse/long/release, and distribution/release guidance into conditional references. Each parent names exact triggers and required references so nothing is silently lost.

### Consume typed distribution evidence

DevelopmentProcessFlow receives a distribution/install evidence identity and status from the owner route. It does not know a fixed skill count or execute installation semantics. SkillGuard/distribution remains the sole owner of maintained-suite identity and clean projection.

## Risks / Trade-offs

- [Conditional file is not loaded] → Parent routing tables state mandatory triggers and tests assert reference reachability.
- [Tier mistaken for permission to skip] → Public types label it `presentation_tier` and tests prove monotonic obligation sets.
- [Responsibility becomes hard to follow] → Demand rows always name the owner route and terminal disposition.

## Migration Plan

1. Land TaskCoverageDemand and receipt/admission boundaries first.
2. Rewrite the main route around the stable sequence.
3. Split only protocol sections with independent triggers and preserve direct links.
4. Replace DPF fixed inventory fields with typed distribution evidence.
5. Validate installed prompt/reference closure and current suite parity through SkillGuard.
