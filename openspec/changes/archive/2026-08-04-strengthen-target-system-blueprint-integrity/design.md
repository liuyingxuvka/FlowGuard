## Context

See `proposal.md` for motivation and the delta specs for required behavior. The current repository already contains one target-system compiler, project and self blueprint builders, implementation and test inventories, model-test alignment, hierarchy and topology reviews, resource and intent inventories, normalized projections, understanding readiness, architecture reduction, model authority, SkillGuard supervision, installation tooling, and release verification. The change must deepen those owners without creating a parallel DNA format.

The present implementation has four architectural weaknesses that shape this design:

1. Some project and self aggregate results do not consume every native child result. A lower-level report can be blocked while a convenience `ok` remains true.
2. The provider core has useful registry and snapshot objects, but the project path can produce the provider result and the authority that certifies it inside the same call. Provider kind and version may also be synthesized instead of supplied by the real adapter.
3. The target-system layer order is globally software-shaped. A non-code workflow can pass only by pretending to have software implementation and test layers.
4. Several compact, cleanup, semantic, and evidence claims use data generated by the same producer they are intended to check. This makes the result structurally circular even when its fields are detailed.

The repository is an active multi-agent workspace. All edits must preserve unrelated peer work, use direct-current formats, and keep source, model authority, consumer projection, local installation, Git identity, tag, and GitHub Release as separate evidence domains.

## Goals / Non-Goals

**Goals:**

- Make one canonical target-system blueprint express software and non-code workflow targets through profile-specific frozen layer plans and provider-neutral core contracts.
- Make whole qualification truthful: every required native layer is visible, ordered, current, and included in the aggregate; later green layers cannot hide an earlier gap.
- Make the model detailed enough to capture target boundaries, behavior, state transitions, interfaces, effects, errors, resources, intent, implementation ownership, tests, and parent-child reattachment at the depth requested by the task.
- Make ordinary maintenance inexpensive by loading only the exact affected model shards, referenced objects, and ancestors.
- Use FlowGuard's self blueprint as a strict consumer and acceptance fixture for the same public path used by external targets.
- Make cleanup decisions come from an independent required-surface universe and current behavior-preservation proof.
- Close the change through OpenSpec, observed model authority, SkillGuard, clean consumer projection, installations, a single frozen full gate, and a patch release.

**Non-Goals:**

- No new `DNA` command, package, skill, authority head, compatibility reader, alias, or fallback path.
- No universal parser for every programming language or workflow format. The kernel defines typed provider contracts; concrete adapters remain replaceable target-facing owners.
- No target-specific global roles. Actors and permissions belong to each target model.
- No claim that passing FlowGuard self evidence alone proves all external targets.
- No automatic run-all fallback when ownership or impact is unknown; ambiguity is a visible planning blocker.

## Decisions

### 1. Keep one canonical blueprint authority and add a frozen target profile plan

Introduce `TargetSystemLayerPlan` in the target-system core with:

- `plan_id`
- `target_profile`
- ordered `layer_ids`
- `claim_boundary`
- schema/version identity
- a canonical fingerprint

`TargetSystemDescriptor` declares the exact profile. The public `qualify_target_system_from_native_reports()` route requires the registered canonical plan fingerprint for that profile, not merely a matching profile string, derives every ordered row from strict native artifacts, and delegates only to a private assembler. A software plan retains the established software layers. A workflow plan uses real workflow concepts such as boundary, target-owned actors, inputs, states, transitions, outputs, resources, intent, and verification. A profile mismatch, shortened or reordered plan, missing layer, duplicate layer, or undeclared substitute row blocks qualification.

The software/project preset may derive a bounded static-manifest consistency
report while assembling those inputs. That report is constructed only by its
private qualifier with a derivation token, stays outside the root and
registered public APIs, and exposes only `static_manifest_status`,
`static_manifest_ready`, layer details, and an exact negative claim boundary.
It has no generic success or completion wording and is never the owner of
whole-target readiness, sufficient understanding, execution, admission, or
release claims.

Why: target-neutral provider payloads are insufficient if the aggregate still imposes a Python/software worldview. A frozen plan lets the same compiler remain canonical without forcing unrelated targets to fabricate irrelevant evidence.

Alternative considered: make every target use one superset layer list and mark most layers not applicable. Rejected because it increases token cost, makes profiles hard to understand, and permits fabricated `not_applicable` rows to resemble proof.

### 2. Separate provider execution from provider qualification

Add strict current-schema load and canonical serialization APIs for provider result, registry, layer plan, and target snapshot. Loading validates required keys, exact identities, canonical fingerprints, and nested capability bindings. A `FrozenTargetSystemEvidence` aggregate may carry these already-created artifacts but never executes a provider.

The project and self compilers will receive frozen provider artifacts. They will not manufacture `provider_kind`, `provider_version`, registry, or snapshot inside the same success calculation. The CLI accepts strict descriptor, frozen-evidence, and native-report-set artifact paths and then invokes qualification. It does not accept caller-authored downstream layer status, gaps, admission flags, or report rows. An explicitly selected adapter stage may run earlier, but its result must be persisted and frozen before this read-only qualification step.

Why: a provider result cannot establish the denominator and currentness authority used to certify itself.

Alternative considered: retain the combined builder for convenience and label it trusted. Rejected because the trust boundary stays circular and external evidence drift cannot be replayed independently.

### 3. Preserve adapter neutrality while making unsupported discovery visible

The implementation inventory keeps generic `ImplementationSurface` identities. Language or workflow adapters own parsing and may emit software, non-Python, generated-interface, or non-code workflow surfaces. An implementation-bearing file or workflow member must have one of:

- current discovery evidence from its declared adapter;
- an explicit typed `discovery_not_applicable` disposition with a bounded reason; or
- a terminal non-implementation disposition such as generated, external, or scoped out.

`requires_adapter=False` cannot turn an implementation-bearing member into a complete empty target. Missing adapters, adapter exceptions, identity mismatches, and zero unexplained surfaces remain in the independent denominator and block upper-layer success.

Native qualification compares independently supplied observation and authority members in both directions. A software target may use a typed external implementation owner and a native verification member instead of a local source surface and ordinary test node, but neither alternative removes the exact per-behavior relation. Workflow targets bind their real boundary, actor, input, state, output, resource, intent, and verification members to exact transitions.

Each native report set is bound to the exact descriptor, boundary, subject revision, frozen evidence, provider capability inputs, and provider payloads. Observation and authority portable models first run their own structural, invariant, progress, and temporal checks. Their behavior members then bind exact portable transition ids and are compared through one fingerprinted refinement binding. This proves bounded structural qualification of the submitted provider evidence; it does not by itself prove that an untrusted provider truthfully observed the outside world. A stronger external-fact claim additionally needs a current validation-owner receipt for the adapter execution and emitted payload.

Why: an unsupported target must be reported as unsupported, not interpreted as having no behavior.

Alternative considered: ship Python, JavaScript, and workflow parsers in this patch. Rejected because parsers are provider implementations, not kernel semantics; synthetic adapters and strict acceptance fixtures are sufficient to prove the extension contract.

### 4. Compute whole success from one typed layer ledger

Create or extend one ordered readiness ledger whose rows contain:

- layer id and native owner
- native report identity and current fingerprint
- static/design status
- executed-evidence status where applicable
- exact gap ids
- downstream admission boundary

Project and self bundle `ok`, deepest proven layer, first gap, and complete gap set are mechanically derived from the longest exact-current successful prefix plus all explicitly required cross-cutting native reports. Convenience fields consume this ledger and cannot independently reimplement success logic.

Static test design and executed evidence remain separate. A complete design can be reported while execution is `not_run`; release qualification requires current terminal execution evidence. A structurally missing behavior/checker/test binding is a static gap and cannot be hidden as merely not run.

Why: a single ledger removes inconsistent hand-written conjunctions while retaining useful partial understanding.

Alternative considered: require `ModelTestAlignmentReport.ok` everywhere. Rejected because its present aggregate mixes design completeness and run freshness; blindly requiring it would make planned-but-not-run evidence indistinguishable from missing design.

### 5. Use an independently observed behavior and supporting-surface denominator

The target boundary produces an observation inventory independently of model declarations. The compiler compares observed behavior-bearing surfaces, workflow steps, state transitions, public entry points, supporting surfaces, tests, resources, and provider capabilities with declared owners and bindings.

Each admitted behavior block binds:

- target boundary member
- function/state transition contract `Input x State -> Set(Output x State)`
- state, effects, errors, and termination/progress obligations
- primary implementation surface or explicit external owner
- supporting helpers/adapters with one primary owner
- source-independent semantic rule and boundary cases
- resource and intent references
- exact child/parent interface edges where applicable
- exact test or native-check design member
- current execution receipt when an execution claim is made

Unobserved declarations and observed-but-undeclared members are both visible. Shrinking the declared set cannot improve completeness.

Why: declaration-derived coverage can only prove internal consistency, not completeness or correct semantics.

Alternative considered: use the behavior model as the inventory because it is simpler. Rejected as circular.

### 6. Reuse hierarchy evidence and strengthen topology rather than inventing a third graph

`BlueprintTopology` will consume current child evidence and reattachment contracts from the existing hierarchy owner. Nodes add typed input/output schema catalogs and state/effect ownership. Relations add exact port mappings, optional portable refinement or transformation contract, child/runtime evidence identities, and loop/progress contracts where feedback is intentional.

Topology review checks:

- producer output and consumer input exist;
- schemas match or an exact current refinement/transform exists;
- current child and runtime evidence are consumed;
- required child outputs are reattached;
- a structural child has exactly one structural parent;
- self, two-node, and longer structural cycles are rejected;
- feedback/data cycles require an explicit progress, repair-token, blocker, or finite-bound contract;
- changed children trigger affected-parent and sibling review.

Why: the hierarchy module already owns detailed child evidence. Topology should compose it and add graph-wide closure instead of duplicating its rules.

Alternative considered: rewrite hierarchy inside `blueprint_topology.py`. Rejected because it would create two authorities and increase migration risk.

### 7. Make semantics and tests falsifiable and exact per owner

Semantic specifications and oracles are derived from target intent, contracts, examples, existing behavior evidence, and explicit change objectives—not copied only from implementation signatures. Required boundary and bad cases distinguish same-shape wrong behavior, swapped outcomes, wrong owners, wrong state transitions, and incorrect errors/effects.

Model-test alignment binds each behavior/checker obligation to a concrete test assertion or native-check member. TestMesh freezes the exact leaf inventory. Parent suite success recomposes child receipts but cannot manufacture, relabel, or copy missing leaf evidence. Zero collection, skip, xfail, not-run, stale identity, wrong owner, or uncovered obligation stays visible.

Why: names and shapes can remain stable while behavior is wrong; suite exit zero is not member-level proof.

Alternative considered: accept aggregate test suite success for every row. Rejected because it creates false coverage.

### 8. Treat resources and intent as first-class bound inputs

Resource inventory records every required file, configuration, external service, data source, executable, schema, and runtime asset with owner, availability/currentness evidence, and consuming behavior/model members. Intent inventory records source identity, target scope, declared objective, accepted/forbidden behavior, and freshness. Existing OpenSpec, Spark/OpenSpark-style idea sources, changelog, and explicit user objectives remain providers; none becomes a global fallback authority.

Every behavior may reference zero or more resources and intent contributions. A required missing resource or stale/contradictory intent contribution blocks only the affected closure and its ancestors.

Why: code and state models are insufficient if their required environment or purpose is absent.

Alternative considered: store resources and intent only as project metadata. Rejected because they would not participate in impact analysis or qualification.

### 9. Add a real normalized affected reader and bounded compact projection

Persist or expose a normalized projection index mapping behavior, model, surface, test, resource, intent, topology, and owner ids to content-addressed shards. `AffectedBlueprintReader` accepts exact affected ids plus `load_shard` and `load_object` readers. It loads only matched shards, referenced objects, and required ancestors; it verifies each fingerprint and never calls the whole builder as fallback.

`BlueprintCompactProjection` produces bounded understanding, self-qualification, and reduction payloads directly from the index/ledger. Tests use spying loaders and `to_dict()` sentinels to prove unrelated shards and whole-object serialization were not touched.

Why: returning a small result after constructing the whole blueprint saves output tokens but not compute, memory, or input tokens.

Alternative considered: keep `bundle.affected_neighborhood()`. Rejected as the ordinary path because the bundle is already fully materialized.

### 10. Make FlowGuard self qualification an ordinary public consumer

The self provider gathers FlowGuard-specific boundary, implementation, model, skill, resource, intent, topology, and test evidence, then passes frozen artifacts through the same target-system compiler and readiness ledger as any other software target. The self wrapper may add display conveniences but cannot omit reports, override gaps, or define a self-only success rule.

The public command surface follows that same single owner: target/project audit derives the current model depth, and explicit project export materializes every typed layer of that same bundle. Model gaps remain content in the export, while raw manifests and repeated caller labels never become a second check or export authority.

The composed self-maintenance command builds one immutable self blueprint instance, passes that same instance to understanding and reduction projections, and rejects identity divergence. Independent fixtures cover:

- external Python software;
- a synthetic non-Python software/provider;
- a genuine non-code workflow profile.

Why: self use detects generic capability weaknesses, while independent fixtures prevent self-specific helpers from licensing broad claims.

Alternative considered: preserve a separate self compiler because FlowGuard is special. Rejected because it would stop being valid dogfood of the public capability.

### 11. Derive cleanup from an independent universe and proof-ready dispositions

Introduce `SelfReductionUniverse`, derived separately from required public entries, exports, provider capabilities, model/check owners, resources, tests, and observed supporting surfaces. Candidate discovery continues to use structure, call, duplication, size, and similarity signals. The universe identity and candidate inventory identity must differ.

Every universe surface receives one disposition:

- `retain`
- `contract`
- `unresolved`

Only candidates with current observable-contract proof, exact callers/consumers, state/effect/error parity, and either equivalence proof or public-facade delegation proof can be contracted. Similarity alone remains `retain` or `unresolved`. `retain` is also an explicit typed disposition with its own current rationale and source identity; the reviewer never converts an unproven or unmatched member to `retain` merely because contraction evidence is absent. Public entrypoint or large structure changes route through StructureMesh; lifecycle and release evidence route through DevelopmentProcessFlow. Before release, all safe unapplied candidates are either applied and revalidated or explicitly retained with evidence.

The reduction entry accepts only the exact typed self-blueprint rebuilt from the current target root and binds both the target subject revision and implementation-inventory fingerprint. Any proof receipt is reloaded from the canonical store and verified against the current contract, input, command, toolchain, environment, proof, result, and child context. Canonical aggregate and child evidence must remain present with the same identity through publication. Caller-supplied verification is comparison data, not authority. Test/parity obligations must resolve to current inventory members, and one proof artifact, result, or execution identity cannot be rewrapped for several candidates.

The full model-regression parent follows the same rule. Its human-readable wrapper references a canonical content-addressed composition receipt whose native contract freezes the original tier, full/scoped claim, current manifest denominator, selected model ids, terminal result, and exact model-child receipts. Rewriting and rehashing a scoped wrapper therefore cannot create full model authority.

Why: a candidate list cannot prove its own completeness, and cleanup must preserve behavior rather than optimize file count.

Alternative considered: compare discovered candidate ids with dispositions from the same list. Rejected as circular.

### 12. Update only the prompts that own changed behavior

The affected author-side skills are expected to be:

- `flowguard`
- `flowguard-existing-model-preflight`
- `flowguard-model-test-alignment`
- `flowguard-architecture-reduction`
- `flowguard-structure-mesh`
- `flowguard-development-process-flow`

Their `SKILL.md`, agent description, relevant protocols, and `contract-source.json` change only when the implementation adds a consumed path. SkillGuard-generated contracts/manifests are produced by the official author workflow and are not hand-edited. The other suite members remain unchanged unless impact mapping proves they consume a changed component.

Prompt language describes the positive routes directly: ordinary affected lookup, explicit whole qualification, external provider gaps, owner-exact evidence, and proof-ready cleanup.

Why: updating every skill would add token cost and stale duplication without changing ownership.

Alternative considered: rewrite all fifteen prompts for consistency. Rejected because unaffected owners should remain reusable and current.

### 13. Use affected validation during development and one frozen full gate before release

Implementation proceeds in ordered phases:

1. target profile/provider/inventory/topology core;
2. semantic, resource, intent, alignment, and receipt exactness;
3. normalized affected reader and compact projections;
4. self consumer and external fixtures;
5. independent reduction universe and approved contractions;
6. prompts, SkillGuard contracts, model revisions, and consumer projection;
7. focused native/model/unit checks after each phase;
8. OpenSpec verification and main-spec synchronization;
9. installation synchronization and parity;
10. freeze source, toolchain, impact plan, model authority, and installation projection;
11. run exactly one final full validation owner;
12. publish patch version and verify source, commit, tag, package/install, GitHub Release, and published identities separately.

Focused checks may run concurrently only when their files and evidence owners are isolated. The final full validation is foreground-owned, not scheduled, resumed, or automatically retried.

Why: repeated full runs waste time and can overlap mutable inputs; one frozen gate gives a reusable terminal identity.

Alternative considered: run full validation after every phase in the background. Rejected because mutable-worktree evidence is not a stable release claim.

## Risks / Trade-offs

- [Risk] Tightening aggregation exposes many existing self gaps at once. → Preserve exact partial layer results, separate static design from execution freshness, and repair blockers by native owner rather than weakening invariants.
- [Risk] Profile-specific plans could fragment into arbitrary target formats. → Keep one canonical plan schema, require frozen profile identity, and ship only bounded software/workflow reference plans in this change.
- [Risk] Provider artifact loading can create stale files and confusing authority. → Content-address every artifact, validate fingerprints on load, bind registry/snapshot/result identities, and surface drift rather than rebuilding automatically.
- [Risk] Independent inventories increase scan cost. → Use the full scan only for explicit whole qualification and maintain a normalized content-addressed index for ordinary affected reads.
- [Risk] Strict adapter requirements block unsupported targets more often. → Return the exact missing capability and boundary so a caller can add or select an adapter; never interpret unsupported as empty success.
- [Risk] Stronger topology checks may reject legitimate feedback loops. → Distinguish structural parent cycles from declared data/control feedback and accept only feedback with explicit progress or termination evidence.
- [Risk] Exact test member binding increases evidence volume. → Store leaf identities and receipts once, use content-addressed references, and project only the affected neighborhood.
- [Risk] Cleanup contracts could collide with peer changes. → Freeze the candidate/universe base, re-scan before applying, stage only owned paths, and move drifted candidates to unresolved rather than overwriting peers.
- [Risk] SkillGuard-generated material and local installations can drift from source. → Treat source validation, consumer compilation, installation, and parity as separate gates with direct-current projection only.
- [Risk] Patch release scope may grow if blockers reveal large legacy gaps. → Keep changes requirement-bound, use exact red tests, and report any irreducible blocker rather than add fallback paths.

## Migration Plan

1. Complete and strictly validate the OpenSpec change before production edits.
2. Add new current-schema types and strict loaders directly; update all repository callers in the same change. No compatibility reader is added.
3. Introduce exact red tests for fabricated authority, profile mismatch, missing adapters, empty discovery, false aggregate success, schema/reattachment gaps, cycles, semantic same-shape errors, receipt relabeling, and whole-materialization on affected reads.
4. Implement the target-system, inventory, topology, readiness, semantic/evidence, affected-reader, self, and reduction changes in isolated owner scopes; run focused checks after each integration.
5. Regenerate and accept the affected observed-model revision set using exact per-owner evidence. Old candidate/discovery heads never become a second authority.
6. Run the self blueprint and independent external fixtures through the public compiler; keep unsupported or unexecuted evidence visible.
7. Apply only proof-ready architecture contractions, then rerun the affected model, structure, and test owners.
8. Update the six affected source skills, supervise them through `unit:flowguard-suite`, compile a clean consumer projection, and synchronize formal/shadow/installed roots without copying author-only evidence.
9. Verify the OpenSpec implementation, synchronize delta specs to main specs, and archive the change before the release candidate is frozen.
10. Bump only the patch component, update changelog/versioned adoption metadata, and perform focused version checks.
11. Freeze source/toolchain/impact/model/install identities and run one final full suite owner. If interrupted, confirm the complete descendant process tree is gone before any new owner starts.
12. Commit only the intended changes, push `main`, create the patch tag and GitHub Release, then verify commit, tag, package/install, release asset/metadata, and published repository identity independently.

Rollback before publication is Git-based and must preserve peer work: revert only this change's owned commit(s) or apply a compensating current-format change. After publication, corrections use a new patch release; tags and releases are not silently rewritten. Model authority rollback follows the repository's accepted ModelRevisionSet compensation path rather than moving the observed pointer without evidence.
