## Why

FlowGuard can deeply model declared behavior and can report how well one task is understood, but it still cannot prove that the whole implementation has been independently inventoried, bidirectionally bound to the model system, and exported with enough code-independent semantics, data, build, dependency, asset, and oracle information for another implementer to reconstruct an equivalent system. Without that closure, a green declared model set remains a deep understanding map rather than a reconstructable software blueprint.

## What Changes

- Define one exact blueprint claim: behaviorally and contractually equivalent reconstruction inside a declared software boundary, not byte-identical source reproduction.
- Independently inventory production files, modules, symbols, entrypoints, helpers, state/effect writers, configuration, schemas, data, assets, migrations, build/runtime inputs, external services, and test oracles before reviewing model coverage.
- Require every inventoried implementation surface to have one explicit disposition and every required model obligation to have one current implementation binding; reject hidden writers, orphan helpers, duplicate primary owners, stale bindings, and missing non-code reconstruction inputs.
- Extend model-code-test alignment with bidirectional source coverage and source-independent implementation semantics rather than treating a path and symbol as sufficient reconstruction detail.
- Join external commitments, model obligations, implementation units, data/build/runtime assets, and verification oracles through the authoritative model system while preserving each existing specialist owner.
- Produce one deterministic content-addressed portable projection from the sole current model-system authority; the projection is a regenerable view, not a second model authority or a new public route.
- Report static blueprint closure separately from optional empirical reconstruction evidence. A reconstruction exercise remains `not_run` unless the user explicitly requests it or a separate qualification gate requires it; ordinary FlowGuard work never scans, exports, or reconstructs the whole repository by default.
- Use FlowGuard itself as the first full blueprint target, then bind the resulting checks, documentation, skill prompts, installation projection, and release evidence to one current patch release.

## Capabilities

### New Capabilities

- None.

### Modified Capabilities

- `authoritative-model-system`: Adds independent implementation/non-code inventory, cross-layer realization closure, blueprint identity, and honest static-versus-empirical claim boundaries.
- `existing-model-preflight`: Adds an explicit whole-software blueprint handoff that consumes an independent implementation inventory while ordinary affected-slice lookup stays lightweight.
- `code-structure-recommendation`: Requires exact model-element coverage and reverse implementation-coverage obligations when a recommendation supports a blueprint claim.
- `structure-refactor-mesh`: Requires an independently derived implementation inventory and exact disposition closure instead of treating a caller-supplied partition as complete.
- `model-test-alignment`: Adds source-to-model reverse coverage, implementation semantics, hidden-writer/orphan detection, and oracle completeness for blueprint claims.
- `hierarchical-model-mesh`: Requires meaningful purpose/consumer/realization relations for whole-system blueprint topology without absorbing code semantics.
- `flowguard-portable-model-ir`: Adds stable verified implementation references and deterministic blueprint projection identities without serializing arbitrary source callables.
- `flowguard-bounded-system-composition`: Carries declared build, runtime, data, asset, service, and verification references needed by the bounded software blueprint.
- `development-process-flow`: Separates static blueprint closure from explicitly requested empirical reconstruction and keeps ordinary work affected-only.
- `flowguard-ai-entry-simplification`: Derives the whole-software blueprint trigger from task facts without adding a user-selectable depth mode or daily reconstruction branch.
- `flowguard-api-registry`: Registers the blueprint inventory, binding, closure, and projection APIs under the existing model-first kernel owner.
- `flowguard-validation-command-surface`: Exposes deterministic inventory/closure/export inspection without automatically running an isolated reconstruction.
- `architecture-reduction`: Requires a model-backed, behavior-preserving contraction review and safe StructureMesh handoff before the FlowGuard release is published.

## Impact

The change affects the authoritative model-system inventory and coverage universe, source inspection, model-code-test binding, StructureMesh and CodeStructureRecommendation evidence, portable model/system schemas, deterministic projection/export, kernel-owned API and CLI surfaces, executable models, regression manifests, skills and SkillGuard contracts, documentation, installation projection, release-time architecture contraction, and release validation. It adds no `DNA` route, no reconstruction depth level, no compatibility reader, and no second authority. The final release also completes and publishes the already in-progress self-understanding work in the same patch version after all affected identities are frozen and verified.
