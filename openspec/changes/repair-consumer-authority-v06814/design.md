## Context

See `proposal.md` for the motivation. The current package authority is
generated from the author projection, but its embedded `flowguard_version`
still names 0.68.12 even though the source package and published tag are
0.68.13. The existing compiler already owns the authority bytes, so the repair
must use that compiler rather than editing generated JSON by hand.

## Goals / Non-Goals

**Goals:**

- Publish one corrective patch, 0.68.14, whose package metadata and generated
  authority carry the same version.
- Preserve the exact fifteen-member clean consumer projection and all existing
  authority hashes except for the version-bound output identity.
- Make the mismatch a tested, visible failure and verify the repaired source,
  installed projection, Git, and GitHub identities independently.

**Non-Goals:**

- No new FlowGuard route or skill member.
- No compatibility reader, alias, fallback, updater, or historical-tag rewrite.
- No edits to the active peer-owned OpenSpec changes or unrelated model work.

## Decisions

1. **Use a patch release.** The defect is release metadata/currentness hygiene,
   not a behavior or schema break; 0.68.14 is the smallest immutable repair.
2. **Regenerate, do not hand-edit.** Run the repository's authority compiler
   after the package version is updated so the generated bytes remain derived
   from the current source projection.
3. **Add a focused identity contract.** A small new OpenSpec capability and
   tests will require `authority.flowguard_version == package_version` and
   reject a stale authority before installation or project adoption.
4. **Keep release domains separate.** Source/package, installed consumer,
   local Git, remote tag, and GitHub Release are each read back and compared;
   one domain's green result does not stand in for another.

## Risks / Trade-offs

- **[A peer changes the author projection during repair]** → Recheck status and
  the compiler's source fingerprint immediately before writing and preserve any
  unrelated changes rather than resetting them.
- **[The old 0.68.13 tag remains stale]** → Never move or rewrite it; publish
  0.68.14 as the corrective authority.
- **[Installed consumers are not refreshed]** → Run the official installer only
  after source validation and verify the installed projection independently.

## Migration Plan

1. Record the clean baseline and active peer boundaries.
2. Create and validate this change, bump package identity to 0.68.14, and run
   the official compiler in write mode.
3. Run focused and affected FlowGuard checks, install the repaired consumer
   projection, and run the read-only currentness checks.
4. Freeze the verified source tree, commit, push, create an annotated `v0.68.14`
   tag, publish a source-only GitHub Release, and perform remote readback.
