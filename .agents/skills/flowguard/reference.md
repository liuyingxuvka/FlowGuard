Start with `new-task`, run ordinary tests and inspect a finding with `show "what it decides"`. Agents that work at the same time use one git worktree each (`git worktree add ../task-b`, then `new-task` there): each worktree has its own `.flowguard/cache`, task baseline and change set, which the agents of one working tree share, so one agent's `new-task` moves every agent's baseline and each agent's uncommitted edits are part of the others' change. `show Model.field`, `show CONSTANT`, `show EnumName` or `show LABELS_TABLE`, after the known.toml entries, rules and agreements that concern it, says how the schemas, SQL files and source declare it, before every other line (a zod line matches an object key by its name, names its schema object (the field's own first, each schema object belonging to the longest model name its camel-case words hold, `lendingAssignmentCreateSchema` to LendingAssignment; the others after a line that says they match by the name only) and is given only to a key whose own chain is a `z.number(` or `z.coerce.number(` schema, also inside `z.optional(`, `z.nullable(`, `z.nullish(`, `z.preprocess(` or a pipe (a pipe into a schema it cannot read keeps the key's bounds and is named, not read); every check of its constant's chain and its own counts, the stricter of two comparable bounds of a side and both when one is a name; a refine on it, or on its object naming the key, is named, not read; a field the known model lacks gets a `not on the map` line instead; a const line comes from a JS/TS module constant only, an object whose values are all literals too (a negative number is one), and one whose value is a call gives its declaration cut to its first call with a zod object's key lines (`const batchAssignSchema = z.object(...) ## Executable two-copy example

In this throwaway example, put this in `policy.txt`:

```text
At most three days.
```

```toml
[tool.flowguard]
authority_docs = ["policy.txt"]
```

In `orders.py`:

```python
# flowguard: same ACCEPT ref(days: day) -> allowed: bool
def accept(days: int) -> bool:
    return days <= 3

# flowguard: same ACCEPT(days: day) -> allowed: bool
def preview_accept(days: int) -> bool:
    return days <= 3
```

In `tests/intent/window.py`:

```python
from flowguard.intent import rule, row

@rule("WINDOW", decides="acceptance window", fields={"days": int},
      source='doc policy.txt "At most three days."', anchor="ACCEPT")
def WINDOW(days):
    return days <= 3

WINDOW.rows(row(days=4, expect=False, why="the fourth day was incorrectly accepted"))
```

Run `python -m flowguard init`, then `python -m pytest`. Change only the preview to allow four days: with a test that calls both functions, its real answer disagrees with the independent rule and the other registered copy, and the run ends with:

```text
FlowGuard 5.0 (since 6765008): 2 red; 0.4 s
red: rule WINDOW: days=4: rule False, code True at orders.py:preview_accept (1 of 6 cells disagree) (+1 more) -> change the code so orders.py:preview_accept follows rule WINDOW
red: same ACCEPT: on days=4: the reference orders.py:accept returns False, orders.py:preview_accept returns True -> make orders.py:preview_accept agree with the reference
```

A newly written document is provisional evidence, not independent confirmation. A rule runs only Python functions: bound to a TS/JS function it is red, and TS/JS copies are compared by `same` alone. The shortest comment is `# flowguard: same ACCEPT`; input and context roles are then read from the parameters.

The rule's `fields` dictionary is the supported API's explicit input schema. It is separate from the `fields name=expression` annotation described below. Keep the predicate independent of the implementation and preserve meaningful regression rows.

## Agreement comments

Use `#` in Python and `//` in TS/JS. These comments normalize to the existing registration; they do not add runtime dependencies to application code.

| Comment | Meaning |
| --- | --- |
| `flowguard: same NAME` | A copy of the named judgment. |
| `flowguard: same NAME ref` | The chosen reference copy; only one per name. |
| `flowguard: together A B,C` | An operation writing A must also write B and C. |
| `flowguard: together A B on=update` | Limit the agreement to update; create is the other supported value. |
| `flowguard: together A B=value` | The partner must be written with that value; `=true` and `=True`, `=false` and `=False`, `=null` and `=None` are the same value, whichever language writes it. |
| `flowguard: together A B except=path:function(reason)` | A documented exception; adding one loosens the agreement, which is the owner's decision. |
| `flowguard: writers A f,g` | Only these functions may write A. |

`together` checks which fields one write holds, and `B=value` one value it writes; a relation of the values under a condition (both fields null when the manager is missing) is a test's job, and no line says it held.

Bare writer names identify functions in the comment's file. A function in another file uses its repository-relative position, such as `src/store.py:reserve` or `backend/src/store.ts:service.reserve`. The source map resolves that file's actual identity. Do not weaken an agreement to clear a finding: loosening an agreement is the owner's decision.

A Python reference can retain its parameter declaration, as in `same ACCEPT ref(days: day)`. TS/JS uses `same ACCEPT ref` above the actual function. Missing targets, mismatched signatures or units, and multiple references remain errors. Different policies should use different agreement names; do not force them to agree.

Python copies with different parameter names make the correspondence explicit: `same ACCEPT(days=overdue_days)`. Nothing is matched by position or type. Copies one of which cannot be given an input another takes (a parameter it lacks; in TS/JS another name at a position the input fills) are red as copies that take different parameters, `same PROJECT_SCOPE: scope.py:can_view(user, project) and scope.py:visible_projects(user, projects) take different parameters -> check whether these are copies of one decision, then correct the code or the marks`: a boolean check and a list projection are not copies of one decision. It is one line, and names the return type each copy declares (`scope.ts:canView(user, project): boolean`). JS/TS copies, or Python copies with value-type annotations (`days: int`), are that line in `check --static` (and so in pytest and vitest); unannotated Python copies, as in the example, are compared when pytest runs them. It is `before` where every copy took these parameters at the task start, marked with that name, whatever else the change edits in their files; otherwise (the change adds or changes a copy's parameters, its mark or its mapping, or there is no baseline) it is red. In the block it gives way by whole return types, then parameter lists. `show --last` adds the mapping a Python copy can write; a TS/JS comment names no parameters, so TS/JS copies, compared by position, are compared once their parameters have the same names. Comments of one name that declare other roles, units or types are red at each comment, naming what differs and where (`conflicting return types (bool at policy.py:first, int at policy.py:second)`); every step is written in the file's own comment syntax. A return projection is written without a colon, such as `-> result[0]` or `-> result.ok`; `-> allowed: bool` remains an output declaration.

FlowGuard 5.0 removed the 4.2 spellings (`sensor`, `owner`): each is red at its line, and its step is the 4.3 comment to write. Written as that step says, it loosens nothing; deleting the line or writing a looser agreement than its step is `loosened`.

## Intent rules and real context

Rules have an ID, decision key, typed fields, source and independent predicate. Literal rows provide inputs, `expect` and `why`; `retired` explains an inapplicable old case. Returning `None` means no opinion. `total=True` makes an uncovered decision an error. `Refused(ValueError, contains="...")` expects a real program exception; a tool error is not that exception.

Boolean and closed-enum domains can be enumerated. Supported numeric, date and duration domains use the current partition reader. Unknown domains remain unverified; a supported result type does not make that type an enumerable input domain.

A Python `same` comment can keep `calibrated_by=tests/test_store.py::test_available`, including a parameter ID, to name the ordinary test that supplies its real context: the call that test made in its ordinary run is the context, and the test never runs a second time. An explicit `fields name=expression` annotation can expose rule inputs missing from the function's parameters. Neither annotation supplies an invented result or proves contexts the test did not reach. Keep real assertions, fixtures and cleanup in ordinary tests.

For an existing scenario binding, the test supplies actual case inputs and production calls; readings must come from the declared source and invocation. Missing or ambiguous evidence stays unverified. A passing setup test does not establish every possible filesystem, database or concurrent state.

## Owner rules and open items

`.flowguard/rules.toml` lists the owner's current rules. Each entry has two keys: one line of `text` and a `source` that quotes stored words or an `authority_docs` sentence exactly.

```toml
[rule.late-fee]
text = "Each late day after the third costs 2."
source = 'R1 "Late days after the third cost 2 each."'
```

An intent rule can then cite `source = 'rule.late-fee'`. When newer owner words replace a rule, delete its entry; Git keeps the history. Two rules that conflict, or a question for the owner, belong in `.flowguard/known.toml`:

```toml
[known.fee-copies]
sites   = ["fees.py:late_fee", "fees.py:preview_fee"]
why     = "The preview charges 3 per late day, the invoice 2"
act     = "ask"
ask     = "Which daily late fee is right, 2 or 3?"
finding = "same:FEE"
```

`sites` are repository-relative `path:symbol` places (a function, `object.method`, a constant or `Model.field`; on a `.sql` file a table or `table.column` its statements name, or the Prisma `Model.field` mapped to one). `act` is `leave` (left as it is on purpose), `ask` (a question only the owner can answer, not fixed in passing; add `asked = "YYYY-MM-DD"` once asked), `fix` (a plain error: fix it when you change a site and say so) or `ignore` (a false finding of an automatic structure check, only counted). `sites`, `why` and `act` are required; an optional `fix` key holds the intended correction, which only `show` prints, and `source` quotes where the question comes from, as a rule's does. `finding` names a finding FlowGuard can judge, such as `same:FEE`; with it the run can say `known fixed?`. An invalid entry is red and counts for nothing. A new `act = "ask"` entry is quiet; changing or removing an entry, or adding one with another `act`, is a `loosened` line. Once the owner decides, store the answer with `req add`, write it into `rules.toml` and delete the entry. `python -m flowguard known add FINDING --act leave --why TEXT` (any `act`; `--ask`, `--id`, `--site path:symbol`) appends an entry, its sites the places of the last run's lines of that finding (of a `copies:` finding, every copy's site, also after a run whose line named one); `show --last` names each line's finding. Whether resembling same-named functions must stay separate (a build script that must not import the app) is the owner's decision; `known add copies:NAME --act ignore --why TEXT` records it and takes the finding out of the brief's count, which a `leave` entry keeps it in. `known add -` with `--site` (a `path:symbol` or a Markdown file's path) records a matter no check finds. `python -m flowguard show rules` lists both files with each source's state, and `python -m flowguard check --static` checks those sources without running the suite. `show NAME`, `show PATH` and `show RULE_ID` (with its anchors) begin with the entries whose sites or finding name it (a site's symbol, the model or object holding it or a Prisma field's `table.column`, in any letter case; a site's last dotted part, and then the line names that site; for a path, a site in that file or folder or a `source` quoting a document there; also an entry whose why or ask holds, as the code spells it, an exact `Model.field`, a constant a non-test file declares or the path), in the brief's words with `(python -m flowguard show known.<id>)`, then the Markdown texts whose about marker names it, its file or a folder holding it (`described by docs/x.md:3 (about backend/src/services/)`), then the intent rules anchored there, the `rules.toml` rules they cite, the flowguard comment agreements that name the function or field (`Model.*` its table's columns too), sit right above the function or are written in that file (one found through a last dotted part names that function), and the last run's lines at that function or file (`before (last run): ...`, five without `--full`). A site copied from `show known.<id>` (`path:symbol`) prints that symbol's facts; a bare id (`show percent-scale`) prints the entry; words (`show "percent scale"`) also list the entries whose why or ask shares one. A Markdown file's view is headed `document` and lists its about markers and generated regions with their lines, each region with whether it is up to date; a file the map does not read, or a folder without one, says so in one line.

## Sources and fallback reasons

The owner is the person who sets the requirement. `source='owner R1: ...'` cites that person's archived words; `req add` stores their exact bytes. Never archive this guide or an AI plan as the owner's words. Document sources require quoted text and an `authority_docs` entry. An archive proves bytes, not an interpretation; provisional or assumed sources do not create owner authority.

When the owner picks one of the options the agent offered, the pick is his original choice and is stored too, without making the options his words: `python -m flowguard req add reply.md --id R2 --offer options.md --picked "A. Keep one version"`. The reply file holds his answer as it reached the agent (`A`, `the first one`); the options file holds the question and options exactly as the agent showed them; each `--picked` is the whole text of one option he picked, as the options file spells it, and must occur there exactly once (compared after CRLF and CR become LF; repeat it for a multi-select). `--selected` says he picked without typing: the reply is then what the interface returned. A `--picked` or `--selected` without `--offer`, an `--offer` without `--picked`, an empty options file, a picked text that occurs there 0 or 2 or more times (the count is named) and a stored id are refused with exit 2, and nothing is written. The record is a `choice`: his reply in `.flowguard/requests/R2.md`, the options in `.flowguard/requests/offers/R2.md`, each written once and checked against its original bytes as a request is, and its sidecar names the options' digest and size, the picked texts and `reply = "typed"` or `"selected"`. `show R2` prints his reply (or that he selected with no words of his own), then the options marked as the agent's words, then each pick, read as the checks read them (UTF-8, or UTF-16 by its byte order mark); `req list` shows it as `choice`. A source in `rules.toml`, `known.toml` or an intent rule cites words of a picked option as `R2 picked "Keep one version"`: they must occur exactly in an option he picked, words of an option he did not pick are refused, and while they hold a line prints them as `owner R2 picked "..." (the agent's option, the owner's pick)`; a picked source that does not hold is printed as the rule writes it, its red saying why. A picked source whose id is not stored names the choice route, `req add REPLY --id R2 --offer FILE --picked "TEXT"`: a plain request under that id would close it, the archive being written once. `R2 picked` without its words between double quotes is refused with where they go, and with its words there and text after them with that text. Two rules backed by the owner's records that disagree name each side by what it holds, his typed words by their id, a pick by its words and `owner R5` on a selected answer as `R5 selected`: `(owner R1 picked "Three days.", R2 picked "Four days."; the agent's options, the owner's picks) -> the owner's choices behind the two rules disagree; only the owner can settle which holds`. The `(owner ...)` list names only sides whose source holds; one that does not hold is named outside it as the rule writes it, `FOUR cites R2 picked "Three days.", which does not hold`, and called `the pick FOUR cites` (`the words FOUR cites` for words quoted as his, `owner R5` with `quote=` named with its words). The conflict's steps say that only the owner can choose which rule holds, and store his decision by either route, his typed words with `req add - --id R<n>` or his pick with `req add REPLY --id R<n> --offer FILE --picked "TEXT"`, before the rule changes; the last step of every other rule red names the same two routes. A stored reply, request or options file whose bytes are no UTF-8 or UTF-16 text is the problem of each source that quotes it, naming the file and the decoder's text (`R1: .flowguard/requests/R1.md is no UTF-8 or UTF-16 text: ... -> store his words again as UTF-8 text: python -m flowguard req add - --id R<n> --supersedes R1`), judged as a request not stored. `R2 "words"` quotes his typed reply as for any request and is refused for a selected one, whose reply holds the agent's option. `R1 picked "..."` on a request that holds no options is refused. Which option his reply means is the agent's statement, shown beside his reply. FlowGuard 5.0 reads a choice's sidecar as invalid: a project requires 5.1 before it stores one.

`.flowguard/ledger.toml` lists handlers that can end without raising, with their counts, reasons and supporting written rules. `python -m flowguard ledger init` records existing handlers as legacy; `python -m flowguard ledger check` checks the record. Legacy entries may only shrink. The finding explains a form that cannot be listed or a source sentence that no longer matches. Keep errors visible rather than adding an unexplained fallback.

## Existing frozen capabilities

Existing finite flows and their node/read/relation bindings remain supported; their state transitions (`Transition`, `flow(..., transitions=)`) were removed in 5.0. Their path and source identities matter: an attempted call is not a completed effect, an unobserved edge is not a successful path, and separate invocations cannot be joined into one witness. These capabilities are frozen; ordinary setup does not require a new flow model. Existing deep checks are also frozen. A top-level command of FlowGuard 0.70 to 1.4 exits 2 with the release that removed it and its replacement (`flowguard: read was removed in 1.0 -> python -m flowguard show "words"`), as a command 5.0 removed does.

The base installation reads Python. The `languages` extra adds TS/JS, Prisma, SQL and frozen C/C++/C# readers. Vitest with ESM has an execution adapter; Jest has static checks. Unsupported readers and observations remain explicit. Keep each project's ordinary tests as the primary execution path. A file `[tool.flowguard] exclude` lists (globs from the project root) is never read, now or at the task start, and is no change of the task, so a Qt `.ts` catalogue needs no TypeScript reader; a change that adds a file there makes each `same`, `together` and `writers` agreement its baseline version held a `loosened` line (`same RATE removed from app/b.py:rate (its file is now excluded by [tool.flowguard] exclude)`), a JS/TS file's read from its `//` comment lines as text; a baseline pyproject.toml that does not decode or parse, or whose `tool` table, `[tool.flowguard]` or `exclude` has another TOML type than FlowGuard reads, makes those files one `not compared` item in the decoder's or parser's words or naming the key and the type found (`baseline pyproject.toml: tool.flowguard.exclude is an integer (not an array of strings)`). Every reader of the baseline's pyproject.toml judges only the keys it reads: another key of another type at the baseline leaves the loosened lines, a baseline `authority_docs` that cannot be read leaves a document source `not compared` (an intent rule unverified), and the project's own such pyproject.toml is refused with that text naming the file (`flowguard: pyproject.toml: ...` or `flowguard: pyproject.toml does not parse: ...`, exit 2; pytest `ERROR: ...`, exit 4), never a traceback. An included file whose reader is not installed stops `check --static` with exit 2 and its text, and in pytest is one red line after pytest's own summary: `red: map checks: web/a.ts: typescript reader unavailable: missing tree-sitter -> pip install "flowguard[languages] @ git+https://github.com/liuyingxuvka/FlowGuard.git", or list it in [tool.flowguard] exclude`.

## Documents, generated files and data files

`<!-- flowguard: about path:symbol -->` (or a path alone) above a Markdown text ties it to code: a change that edits the site and not the text names the text with an `impact` line, in pytest as in `check --static`. The path may be any file of the repository, a data file or a checked-in generated one too, which cannot hold a marker itself: list the generated files in a Markdown text, each line under markers for the function that produces it and for each file it is made from (markers stacked above one line all describe that line), with the command that regenerates it, and a data file such as `src/app/resources/model.json` under a marker for itself and one for the function that reads it. A change to that file names the line; nothing else follows from it, since the map records no file a function reads. A file the map leaves out (`build/`, `dist/`, `[tool.flowguard] exclude`) is never this change. A text about a file or folder is a module contract: a change to a function connected to it through a call the map holds now names it; a change in another file that removes its call into the module names nothing, and no agreement says that one function calls another, so that a route uses its owner function is a test's job.

A SQL file kept in the repository, such as a database package installed by hand, describes the tables it creates and is compared with the Prisma schema; one that only alters a table describes none. A `columns:` finding's place is a folder or file, no site: record a description left out of date on purpose by naming a table of one of its files, `python -m flowguard known add columns:prisma/migrations/~prisma/schema.prisma --site prisma/migrations/20240101_init/migration.sql:central_employees --act leave --why TEXT`.

## Inspecting a result

Read the FlowGuard block after the tests. Its first line counts each kind and FlowGuard's own time, and names what the run compared with; a pytest session that ended before its selected tests had all run says so there (`0 red; run ended early (exit 3): 2 of 3 selected tests ran, the rest not checked; 0.1 s`). Each further line is `kind: what -> step`:

| Kind | Meaning |
| --- | --- |
| `red` | This change broke an agreement, an intent rule, a quoted source, the ledger or an entry of the two files. The only kind that fails the run. |
| `before` | Something this change touches was already broken at the task start. |
| `known` | This change edits the text of a `known.toml` entry's site, comments and spacing included; the line names the sites it touches (`(1 of 12 sites)`) and an `ask` entry's question; when the change also touches the entry's `finding`, it names that finding's places it touches (`(1 of 2 places)`), every place when it touches none. |
| `known fixed?` | A `known.toml` finding is gone. |
| `changed` | A function this change edited, or one importing a constant it altered, returns something else for an input a test used; plain `check` runs no ordinary tests, so this comes from a test run or `check --all`. A call its task-start version takes as other parameters (`(record)` that became `(kind, record)`) is `not compared` (`parameters differ from the baseline`), not changed. A dict result, or a list of dicts as long as before, names the keys that changed (`now adds demandPeriodConvention='legacy-half-open' (3 other keys equal)`, `removes KEY`, `changes summary.total from 3 to 4`); `show --last` prints each differing input once, with its full values. |
| `impact` | A changed function writes another set of fields, or an automatic structure check found something new. A field line counts the other writers of its first field and its readers: a database model's (`2 readers of Entry`), or the functions that read a Python class's field as `show Class.field` lists them (`5 readers (untyped reads not counted)`). A field it no longer writes reads as the code shows it: `writes AbsencePhase.? where it wrote endDate (fields not visible: ...)` while it writes that model with data whose fields are not visible, `set_default's writes of Prefs.model moved to _apply, which it calls (model.py:7)` when a function it calls through a resolved call on every path writes it now on every path of its own (one line for both, whose block line keeps each clause of what changed, at least as a count, while the other callers and counts give way; a call or helper write that is unresolved, under a condition or a suppressing `with`, or not placed by the path queries keeps two), else `no longer writes`, with `now deletes Assignment (...)` for a new delete of that model. A new `uncreated` reader says `no creator found` in the files FlowGuard reads and whether the model was read so at task start; its step names `known add` for a creator outside the repository. |
| `loosened` | An `except=`, a removed or narrowed agreement, a changed or removed `known.toml` entry or a removed rule. |
| `not compared` | A comparison was due but could not run in the closed environment, or the function's file was saved during the run (`source of PATH changed on disk after import`); unverified, not success. A vitest run whose static test did not report has its own line, `not compared: flowguard.static.test.mjs (map checks did not report to this vitest run)`: the map checks did not run. |

The step after `->` says what is known and who decides; you choose when to raise an open question with the owner. A `copies` line's step says how its copies resemble (`they resemble (structural similarity 0.87)`), what makes them agree and the entry that records copies meant to stay separate; a before line keeps that step in its detail. When a change adds every copy of a two-file finding, one impact line names both (`app/psp.py:display_ancestry and web/psp.py:display_ancestry differ`); its detail lists each copy's signature and resolved callers and the first line where the bodies differ (`first difference: app/psp.py:5 break | web/psp.py:5 raise ValueError("cycle")`), which locates the difference; what each copy answers is for the tests. `python -m flowguard show --last` prints every line of the last run with its details: the last run of each vitest package and the one of pytest, `check` and `check --static`, newest first, with the full version, pytest's own outcome (`pytest: exit 1, 1 failed, stopped early (-x)`), a vitest run that started and did not report, and the failed tests the brief counts (`1 test failed when last run and has not run since: tests/test_a.py::test_x`, never called red), each with when it ran and whether the last pytest run selected it. Runs on one repository may go at the same time (two packages' checks, vitest beside `check --static`): each waits only for another's short write to the cache, and a wait longer than 5 s prints `flowguard: waiting for .flowguard/cache/map.sqlite (another FlowGuard run is writing it; ...)` on stderr; a vitest run's first line says its preparation's wait instead (`0 red; waited 9 s for .flowguard/cache/map.sqlite (another FlowGuard run was writing it); 9.4 s`). Use `python -m flowguard show "what it decides"` for registered functions, fields, copies and rules; use `python -m flowguard check --static --all` for a deliberate structure review.
