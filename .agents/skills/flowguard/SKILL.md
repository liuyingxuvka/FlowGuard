# FlowGuard

## Purpose
Select the smallest current owner, derive task-required understanding, and deepen only for a triggered owner or open native gap. Lightweight use remains available; claim strength determines evidence depth.

## Entrypoint Scope
Route id: `model_first_function_flow`; role: `kernel`; native owner: `model_first_function_flow`. Decide `use_flowguard`, `skip_with_reason`, or `needs_human_review` through `behavior_flow`, `argument_flow`, or `decision_flow`.

## Local Material Routing
- Before route selection, read only `references/route_index.md`.
- After the kernel route is selected, read `references/modeling_protocol.md`; it routes the smallest needed part of `references/modeling_core_protocol.md` and `references/modeling_evidence_protocol.md`.
- When kernel maintenance or adoption is in scope, read `references/skill_kernel_protocol.md`, `references/adoption_protocol.md`, `references/framework_upgrade_protocol.md`, or `references/long_check_protocol.md` only for the named boundary.

## Entrypoint Acceptance Map
- Use one clear satellite directly; zero or multiple candidates stay visible.
- Keep the kernel for ordinary modeling, unclear/cross-route work, portable composition, risk, maturation, and closure.
- On a broad-claim, prediction, Model Miss, ambiguity, high-impact, or addressable-gap trigger, load the mapped reference and continue to native closure or an explicit external/scoped/stalled/bounded terminal.

## Use When
- Use when behavior, state, order, retry, side effects, or progress need `Input x State -> Set(Output x State)` modeling and no satellite already has clear ownership.

## Do Not Use When
- Do not force the kernel before a clear satellite, use it for trivial copy/format/direct-command work, or treat check-engine helpers as independently triggerable Codex skills.

## Required Workflow
1. Freeze provenance-bound `TaskFacts` from the request, observed model, public surfaces, and lifecycle/process change. Preserve unknown, omitted, contradictory, unmapped, and scoped facts; compile the independent `TaskCoverageDemand`. Callers may add facts or narrow claims, never erase observations. Add independent implementation-inventory and binding owners only for an explicit whole-software blueprint/export/qualification—not ordinary work, model count, or a depth label.
2. Resolve every demanded owner exactly once as `satisfied|not_triggered|unresolved|blocked`; TaskCoverage and maturation share its identity. `ordinary|standard|deep|release` describes work depth, not weaker correctness.
3. Build the smallest faithful executable model for triggered owners, including protected failures, state, side effects, completion evidence, and representative known-bad paths.
4. Run declared checks and mature counterexamples until each demanded row has current evidence or an explicit external/scoped/stalled/bounded terminal. Publish and independently verify one canonical receipt binding task, demand, candidate, resolutions, inputs, obligations, result, evidence, and gaps. Never accept self-rated understanding or caller-authored current/digest/receipt fields.
5. When code is requested, preserve the verified maturation decision and ask DevelopmentProcessFlow for a separate `ready`, `ready_scoped`, `no_code_requested`, `blocked`, or `stale` implementation admission. Permission may bound an attempt; it cannot upgrade understanding.
6. `risk_evidence_ledger` alone decides full/scoped/blocked confidence. Closure checks exact identity, material presence, and terminal integrity without rescoring risk. Preserve failed, skipped, stale, scoped, and not-run evidence.
7. Summaries use the read-only understanding projection and separate sufficiency, implementation admission, and user execution choice. It never runs/resumes owners, writes evidence, or grants admission.
8. Whole-software blueprints report static `complete|incomplete|stale|blocked` separately from reconstruction `not_run|pass|fail|blocked`; static complete plus not-run never means reconstruction ran.

## Hard Gates
- Model-purpose gate: pre-build/change freeze task-specific failure(s)/boundary; bind the candidate to native good/bad-per-failure/oracle/current evidence. Reusable types are not fixed-purpose: no mode/fallback; only FlowGuard-declared checks may support completion claims.
- Require the real FlowGuard check engine and AGENTS.md managed record; never create a fake mini-framework.
- Existing-model currentness comes only from the sole observed snapshot. Targets and experiments remain separate until one accepted whole `ModelRevisionSet` updates authority.
- Do not weaken invariants, invent alternate success paths, or use missing/stale/skipped/`not_run`/progress-only evidence for broad confidence.
- Target-product people, roles, permissions, and transitions belong inside the target software model. FlowGuard supplies modeling and evidence owners; it does not invent a global catalog of application roles.
- Portable composition, UI/payload proof, replacement, evidence lifecycle, WorkContext, diagram semantics, release freshness, and template harvest closure remain mandatory when their route trigger fires; their unique rules live in the selected references.
- Paths/symbols are traceability, not reconstruction semantics. Blueprint closure also requires independent implementation inventory, reverse coverage, source-independent behavior, resources, and current oracles; it never auto-reconstructs.

## Output Requirements
- Return evidence, failures, blockers, skipped checks, residual risk, claim boundary, typed next actions, route/reference decisions, model snapshot, counterexamples, sufficiency, admission, user choice, validation status, and—only when triggered—static and reconstruction status.
