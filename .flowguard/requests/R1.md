# FlowGuard 第 0 阶段方案清单（第十一轮：0.70.14 → 0.71.0）

## 这份清单要达到什么（方案总览）

第十一轮把 FlowGuard 改成 1.0：代码自己生成骨架、九个通用检查不用 AI 写一行、挡下来的东西 AI 没法悄悄绕过（设计说明 §0.1）。这一大块在第 1、2 阶段做。**第 0 阶段先做两件小而确定的事，并发一个次版本 `v0.71.0`**：把第十轮验收和 realaudit11 找到的、AI 照着 FlowGuard 自己的输出走却走进错误状态的地方修掉；给第 1、2 阶段和四个使用方准备好它们要用的入口（请求原样存一次、目标里的改动行、`--json` 判定、一个没有歧义的项目规则块）。第 0 阶段的代码仍在旧的模型运行时上，第 2 阶段整体替换（设计说明 §0.2）；所以这里只改设计说明点名的地方，不加新的手写模型（设计说明 §6）。

**AI 照着 FlowGuard 的话做，却走进错的状态（F1、F21）。** realaudit11 用一份按 SKILL 文字写的生命周期声明，在真实的 FlowGuard 命令上找到六个这样的地方，FlowGuard 自己 2,264 行的自测模型带着它们全部通过（规划阶段证据（不在包里）：findings/realaudit11.md §3、§4）。这一轮修掉其中五个：

**给后面的阶段和使用方准备入口（F2、F21 的 `--json`、F5）。**
- **主人的话原样存一次（F2）。** 新动词 `req`：`req add` 把请求的字节原样存进 `.flowguard/requests/`，记下摘要和状态；被改过就是 ERROR `owner_text_edited`。`target start --request` 把目标挂到请求上，promote 把它标成做完。目标里新的 `.flowguard/target/changes.txt` 一行写一条改动了的规则，理由要么是请求里一字不差的引文（工具查），要么是 `because "<理由>"`；引文必须和规则共有一个词。改了的规则在旧代码上打印 NO GAP（“代码已经满足它”）时，过去有一句“写在提交信息里”的邀请，第一轮试验里 AI 就是这样悄悄放宽规则的；现在它变成挡 promote 的 TO-DO `rule_changed_without_line`，直到 `changes.txt` 点名它。promote 最后打印一个“主人块”，AI 原样贴进最后的消息。
- **`--json` 判定（F21）。** `map check`、`map lint`、`target check`、`target promote`、`release` 加 `--json` 时只打印一行 JSON（判定、码、下一步）；每条 `next:` 行带一个稳定的建议编号 `next[<编号>]:`。第 1 阶段的命令一致检查和执行者的测试工具读它们，不再解析文字。
- **尺寸只作建议（F3）。** `large_file`、`large_component`、`too_many_responsibilities`、`high_fan_out` 变成 `info` 建议：永不挡门，也不用为它记债。接受的债要有理由和到期（`expires`），到期由 `release` 执行。职责只是换了说法不再是 `owner_dropped`。
- **一个导入路径（F4）。** 模型和绑定测试的子进程先看项目自己的包，再看一个只露出 `flowguard` 包的位置，永远看不到 FlowGuard 仓库根目录（第十轮的 `examples/` 遮挡和 `src/` 布局问题）。
- **入口文字（F5）。** 技能描述写明什么时候用、什么时候不用（转给另外四个技能）；`template adoption` 在项目没有 `CLAUDE.md` 时写一个只有 `@AGENTS.md` 的 `CLAUDE.md`；项目规则第 2 条点名技能的出口（`EXPECTED GAP`、`moved rules only`、`no rule change`、带 `changes:` 行的 NO GAP）和 `req add`。四个使用方在各自第 0 阶段原样复制这一块并钉到 `v0.71.0`。

**版本。** 这一轮加一个动词（`req`）、一个目标文件（`changes.txt`）、`--json` 判定，还让以前能过的输入失败（新的 ERROR），按“一条规则管五个仓库”是次版本：`v0.71.0`（设计说明 §0.3）。

### 0.1 路线（每个条目的标题和“路线”字段都写了用哪条）

先定位：`python -m flowguard read --find <路径:函数 | 几个词>`，只打开它指出的那个模型。条目写的模型就是规划阶段在 v0.70.14 上 `read --find` 的结果（`read --find` 指出的拥有者为准；不同就记进日志，按 `read --find` 做）。

**路线 (b)：目标（v0.70.14 的写法，第十轮 `00_先读我.md` §3）。** 改任何模型文件（规则、已知坏、conformance、`OUTPUTS`、`HANDOFF`、`TESTED_BY`、`IMPLEMENTED_BY`、`USES` 等），加或删模型文件，或改地图结构（组件、文件归属、`depends_on`、层），都走这条。`.flowguard/models/` 里的当前模型从不原地改。

1. `python -m flowguard target start "<编号>: <条目写的英文目标>"`，再对条目点名的每个模型各跑一次 `python -m flowguard target add <模型 id>`（一次一个 id）。下划线开头的帮手文件（如 `_target_fixture.py`、`_gap_cases.py`）没有 id，不能 `target add`：要改它就 `cp .flowguard/models/<帮手>.py .flowguard/target/models/` 再改那份副本。
2. 只改 `.flowguard/target/` 里的副本。
3. `python -m flowguard target check`：先修掉每一条 `ERROR`（那是目标设计本身错了）。再看缺口行，原样抄进日志：新加或改了规则的模型，写代码之前打印 `EXPECTED GAP <模型>: ...`；只缺锚点符号时这一行写成 `EXPECTED GAP <模型>: only the missing anchor symbol '<符号>' in <文件> for <规则>; conformance did not run, ...`，意思是先按今天的行为把这个符号写出来，再 check 一次，才看得到规则真正的缺口。`no rule change: <模型> ...`、`moved rules only:` 不需要缺口。写代码之前打印 `NO GAP` 的新规则只是把代码今天已经在做的事写下来：不为它写代码，提交信息正文写一行 `records existing behaviour: <规则名>`。
4. `git add .flowguard/target && git commit -m "<编号>: target"`。这个提交只含 `.flowguard/target/`，先不推送。
5. 写代码、加测试、改文档。`target check` 想跑几次就跑几次，直到没有 `TO-DO`：写了代码以后打印 `GAP CLOSED <模型>: ...`（做完）或 `GAP OPEN <模型>: ...`（还没做完），并跑目标模型自己的绑定测试（`bound tests: ran for <模型> ...`）。
6. `python -m flowguard target promote`：唯一一次完整检查。成功以后运行它打印的 `python -m flowguard map confirm <ids>`（先读每个组件的描述，行为变了就改 `summary`、`responsibilities`）。

### 0.2 请求怎么存（`req add`，`00_先读我.md` 和 PKG11 3.9，设计说明 §0.6）

- **从 FG-614 起**，一条在旧代码上打印 NO GAP 的改了的规则，要在 `.flowguard/target/changes.txt` 写一行：

### 0.7 数字怎么用（主人的说明 H，本清单处处适用）

- 没有一个尺寸数字或秒数是通过/不通过的标准：条目、第 5 节的行、你新加的测试都不用它们。秒数和字符数写成“规划阶段实测”或写进 FG-618 的成本表，只作报告；一条路径变慢、一段输出变长时，写出多出来的部分去了哪里。
- 仍然是数字的只有已经强制的拆分触发（每个模型 8/12 条规则、2,000/10,000 个探索序列，每个测试文件 40/60 个测试函数）：主人要求强制的拆分信号，到第 2 阶段换成设计说明 F10 的功能触发。本清单给模型加规则时都算过：做完以后没有一个自测模型超过 8 条规则（第 4.2 节）。条目加的用例让一个模型的探索序列超过软上限时，照 `SKILL.md` 路线表的 `large_model` 一行拆，不为它记债。
- `owner_dropped` 判断“只是换了说法”用 `map lint` 今天判断 `possible_duplicate` 的同一个相似度下限（FG-604）：这是一个语义判断的门槛，不是尺寸或时间的上限。

### 0.8 卡住怎么办（只在真的失败时用）

照 `00_先读我.md` 的卡住规矩做（自查两次、撤掉没推送的改动、不发布、不改写历史、不放松断言、按定义判断、以清单为准）。本清单补几条：

1. **自己的新闸挡住自己。** 本清单好几个条目让 FlowGuard 自己的仓库多出 ERROR（FG-603 的 `expires`、FG-606 的已提升目标、FG-607 的原地修改、FG-612 的 `owner_text_edited`）。条目的要求已经写了 FlowGuard 自己要跟着改的东西（例如 FG-603 给自己的债补 `expires`）；还有别的被挡住，就在同一个条目里修，不放松新闸。已经推送的提交留下了一个已提升的目标：单独提交 `<编号>: Fix <问题>` 把删除提交上去。
2. **`defect_repro.py` 打印 `SCENARIO INVALID`**：先看它说的原因（多半是 venv 缺 pytest、种子项目不干净）。种子项目或脚本本身错了是方案包的错：记进日志和最终报告，按脚本开头写的判定条件自己手工核对那一行，不改产品代码去迁就它。
3. **FlowGuard 自己的检查发现了 FlowGuard 代码的问题**：在代码里修（设计说明 §0.6），不接受、不记债。一个“设计好的拒绝”（例如新的 ERROR 照写明的那样挡下了东西）算进展，不算卡住。
4. **按定义判断，不按预计行。** 本清单“应看到”里新建的信息原文是要求，必须一字不差；规划阶段对旧行的预计（例如某个模型多出几个用例、某条命令打印几行）对不上时，按条目写的定义判断，把预计、实际和依据写进日志。
