# FlowGuard 方案清单（第十一轮 第 1 阶段：试点 1a、1b，中间闸和试点闸；FlowGuard `v0.71.0` 之后的 `main`，不发布）

## 这份清单要达到什么（方案总览）

第 0 阶段发完 `v0.71.0` 以后，FlowGuard 在 `main` 上建一个**不发布的试点**：子包 `flowguard/behave/`，只能用 `python -m flowguard.behave <动词>` 运行。它要回答设计说明 0.5 里还没有证据的两件事：

- **不用任何人开口，工具自己就有用。** 不写一行声明，工具从代码生成软件的骨架（有哪些操作、状态值、设置和出厂默认值、界面的屏幕和按钮、怎么存盘），在出厂设置下把所有操作的顺序都走一遍，跑九种通用检查（设计说明 F22 的 GC1–GC9）。规划阶段的原型在 3,000 行的审查主体上这样找到了 11 个埋藏问题里的 6 个，没有误报，0 个 AI token（设计说明 1.1、F22 “Prototype result”）。
- **结果关不掉。** 拦下的项只从 AI 在改动里改不了的输入算出来（旧代码、新代码、出厂设置、存着的请求）；只能用改代码或一行引用主人原话的说明放行，每行都打印给主人（设计说明 F11）。第十一轮的改需求链里，引擎的正确输出被 AI 忽略、改窄规矩让它闭嘴、或从被截断的搜索里读出假的 “HOLDS”（包里的 `findings/chains11.md`）。

这一阶段分两段，中间有一道闸（设计说明 0.2、0.5）：

- **1a 试点核心（FG-620–FG-632）。** 按设计说明 0.2 的八步顺序建：骨架 → 探索和诚实输出 + GC1、GC3 → GC4 → GC2、GC5 → GC6（生成的文件输入）→ GC8 → `audit --base` → 推不出骨架时点名要哪种世界。每一步在验收材料上跑出规定的结果，记一行工作日志。两条独立的线 F16（派生视图，`flowguard/map/derived.py`）和 F17（文字规则报告，`flowguard/map/rules.py`）也在 1a 做完，因为试点不管过不过，它们都要发（设计说明 0.5 的三条路都带它们）。然后是**中间闸**（G1、G2、G9）。过不了就停，走 FG-698 的路。

### 0.3 路线（第 1 阶段只有一种改代码的路线：(b)）

第 0 阶段已经把这一轮的路线规则写进 `00_先读我.md` 第 3 节（`v0.70.14` 的 (b)、(a0)、(c)，加上 `v0.71.0` 新加的 `req add`、`changes.txt`、F1 的暂存行和 F21 的拒绝）。本清单只用其中的 **(b) 目标**，落在三个新组件上。**规划阶段在 `v0.70.14` 的副本上试过**：一个组件只要不列承诺（`entrypoints`、`state`、`side_effects` 都是空的），目标里加它或改它就不需要旧式模型规则；列了承诺，`target check` 打印 `ERROR target: target_goal_untied: the target changes a promise ... but adds or changes no model rule or known-bad`。设计说明不许给试点写旧式模型，所以：

- **三个新组件都不列承诺**：`behave`（`flowguard/behave/*.py`）、`map-derived`（`flowguard/map/derived.py`）、`map-rules`（`flowguard/map/rules.py`）。它们的 `entrypoints`、`state`、`side_effects` 在第 1 阶段始终是 `[]`；职责写在 `summary` 和 `responsibilities` 里；测试文件一个一个列在 `tests` 里（不用通配符：每个条目往 `tests` 里加它的测试文件，这正是这个条目在目标里改的地图结构）。

**【路线 (b) 试点】**（每个改代码的条目都照这个做；条目的“步骤”只写它自己特有的部分）：

1. `python -m flowguard target start "<编号>: <条目标题的英文>" --request R<清单11>`（`R<清单11>` 是 FG-620 第 1 步存的本清单原文的编号）。
2. 第一次碰某个组件时，在 `.flowguard/target/map.json` 的 `components` 里新建它（FG-620、FG-630、FG-631 写了组件的原文）；以后 `python -m flowguard target add <组件>`，再改 `.flowguard/target/map.json` 里的副本：在 `tests` 里加本条目的测试文件；条目写了新职责句的，加进 `responsibilities`。承诺三项保持 `[]`。
3. `python -m flowguard target check`。写代码之前应看到 `goal rules: none (no promise changes: structure and descriptions only; system rules apply)`，以及 `WARN  component <组件>: test_missing: tests pattern '<文件>' matches nothing`（测试还没写）。有 `ERROR` 就是目标设计错了，先修。
4. `git add .flowguard/target && git commit -m "<编号>: target"`，先不推送。
5. 写代码和测试；`target check` 想跑几次就跑几次，直到退出 0、最后是 `target check: 0 error(s), 0 to-do, 0 warning(s)`。
6. `python -m flowguard target promote`；照它打印的 `next:` 行运行 `python -m flowguard map confirm <组件>`，再按 `v0.71.0` 的暂存行（F1：代码、`.flowguard/` 和 `.flowguard/target/` 的删除一起 `git add -A .flowguard <代码路径>`）提交 `<编号>: <标题>`。两个提交一起推送。
7. 推送后跑【历史检查】（0.4）。

不改代码的条目（闸、会话、试点运行、核查）没有路线，只写工作日志，没有提交；它们的标题写【闸】、【试点运行】或【核查】。
