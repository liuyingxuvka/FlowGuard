# FlowGuard 方案清单（第十一轮 第 2 阶段：FlowGuard `v1.0.0`；以及试点闸的两条退路 `v0.72.0`）

## 这份清单要达到什么（方案总览）

试点闸（清单 11 的 FG-658）在 `../worklog_gate.md` 末尾 `## path` 写下了三条路之一。本清单管其中三种结果：

- **全过（G1–G9）→ 第 2 阶段：FG-660–FG-674、FG-696、FG-699，发 FlowGuard `v1.0.0`。** 试点证明了两件事：工具不用任何人开口就有用（G1、G2、G5、G9），结果关不掉（G3、G4、G6），升级能核对（G7），成本按功能判是好的（G8）。第 2 阶段把试点变成 FlowGuard 本身：一个命令行 `python -m flowguard`，九条任务路线（设计说明 F13），格式闸和强制、可核对的升级（F14），旧的手写模型运行时整块删掉（设计说明 §6），技能文字、参考文字和 README 一次写好（F18）。然后四个使用方各自走第 3 阶段（PhysicsGuard → ResearchGuard → WorldGuard → LogicWriting）。
- **部分过（G1、G2、G5、G9 过，G3、G4、G6、G7 或 G8 有没过的）→ FG-697：发 `v0.72.0`，带 F16、F17 和不要声明的 `flowguard audit`。** 旧运行时留着，1.0 和使用方第 3 阶段挪到下一轮。
- **没过（G1、G2、G5 或 G9 有没过的，或者中间闸没过）→ FG-698：一个提交撤回试点，发 `v0.72.0`，只带 F16、F17。** 使用方第 3 阶段跳过。

不问主人，照 `## path` 那一行机械地走（设计说明 0.5）。

**1.0 是什么（设计说明 0.1、1.1）。** 工具从代码生成软件的骨架，在出厂设置下把真实动作的各种顺序都走一遍，跑九种通用检查（GC1–GC9），AI 一行不写。AI 只写工具推不出的保证（规则），每条带出处，放在它所属的功能下；改动里每个有意改变、退休、预期或接受的项目写一行，引用存着的请求原文。拦下的项只从 AI 在改动里改不了的输入算出来，只能用改代码或一行引用放行，每一行都打印给主人。派生视图、自然连接、生成的流程图、文字规则报告、九条任务路线。没有向后兼容：格式闸拒绝 0.x 的模型系统，一个可核对的升级把旧东西逐条映射以后，删掉旧的模型运行时（PLAN11 “NO backward compatibility”）。

**第 2 阶段难在哪里，本清单怎么做。** 第 1 阶段的试点在 `flowguard/behave/` 里，只能用 `python -m flowguard.behave` 跑；主命令行还是 0.x，FlowGuard 自己的 45 个自检模型还在旧运行时上跑，CI 用它们判每个提交。1.0 只能有一个命令行、不能留旧运行时（主人的决定），所以 0.x 到 1.0 的切换只能一次完成（设计说明 F14：“The switch commit is `upgrade finish` plus the deletion of the legacy runtime plus schema v2”）。本清单分三段：

1. **切换以前（FG-660–FG-664）。** 在试点空间（`flowguard/behave/`，以及没有旧式模型锚点的新模块 `flowguard/map/derived.py`、`rules.py`、`upgrade.py`）里把 1.0 的命令、格式闸、升级路线、路线 (h)、F16 的接线建完整。每个提交照第 1 阶段的办法，用 checkout 自己的 0.x `python -m flowguard` 走路线 (b)，CI 每次都判（PKG11 3.3）。主命令行、旧模块、45 个自检模型一个字节都不动。
2. **定稿、演练和切换（FG-665–FG-670）。** 技能文字从试点文字出发一次写好（FG-665）；在一次性副本上把切换演练完：搬家、删旧运行时、重接命令行、Python 3.12、格式 v2，再按设计说明 F14 的承载表给 45 个自检模型写 1.0 声明、填完整的升级报告（FG-666–FG-669）；最后在 `main` 上用一个提交完成切换，FlowGuard 自己走路线 (i)（FG-670）。
3. **切换以后（FG-671–FG-674、FG-696、FG-699）。** FlowGuard 自己用 1.0 的路线改自己（FG-671）；改过而且试点会话用过的技能规则在一条 G4 链上重跑（FG-672，设计说明 0.4）；跑 1.0 才有的验收行（FG-673）；换 README（FG-674）；总清扫（FG-696）；发 `v1.0.0`（FG-699）。

**(4) 切换以后（FG-671–FG-699）：1.0 的路线（设计说明 F13）。** 用 FlowGuard 自己（`.venv` 里可编辑安装的当前代码）：

【路线 1.0】
1. `python -m flowguard read`（开会话先读摘要）。
2. 只改代码或文字、行为不变：`python -m flowguard change --run`；它报 `behaviour_changed_without_target` 就改走第 3 步。提交 `<编号>: <标题>`，推送，【历史检查】。
3. 行为改动：`python -m flowguard target start "<编号>: <英文目标>" --request R<清单12>`（重构加 `--refactor`）；新功能先 `python -m flowguard add function <id>`；在 `.flowguard/target/behave/<功能>.py` 写新保证的规则（只写规则，出处用 `src=owner("R<清单12>", "<逐字引用>")`、`imported(...)`、`derived(...)` 或 `decision(...)`，设计说明 F7）。
4. 写代码之前 `python -m flowguard target check`：新规则打印 GAP，再列 IMPACT。`git add .flowguard/target && git commit -m "<编号>: target"`（先不推送；保留“规则先于代码”的历史证据，历史检查读它）。
5. 写第一版照字面的代码，`target check`：看“交织”列表、流程图和对比。每个拦下的项要么改代码清掉，要么在 `.flowguard/target/changes.txt` 写一行设计说明 F11 允许的放行行，引用本清单原文（`R<清单12>`）。本清单每个这样的条目都在“要求”里写了**可引的原文**：引用必须逐字、和它放行的东西共有词。LOST、STUCK、矛盾、owner 规则、出厂默认值、新排除的动作永远不用 `because`。
6. 写完代码，`target check` 退出 0。
7. `python -m flowguard target promote`；把主人块原样贴进 `../worklog_flowguard.md`；照它最后一行暂存：`git add -A .flowguard <代码路径>`；提交 `<编号>: <标题>`；两个提交一起推送；CI 绿；【历史检查】。
